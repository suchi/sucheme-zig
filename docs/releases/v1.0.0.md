# sucheme v1.0.0

sucheme-zig の6つ目のリリースである。Zig で作る R7RS-small 準拠の Scheme インタプリタの、段階6(準拠検証)にあたる。取り込んだ R7RS 準拠スイート(`r7rs-tests.scm`)の不合格がなくなり、準拠スイートの走らせ方が、1件でも落ちれば非0で終わる形になった。R7RS 準拠の達成を v1.0.0 とする規則([ADR-0010](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0010-ci-cd-and-release-strategy.md) と [docs/roadmap.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/roadmap.md) の段階6の完了条件)に従って、この版を v1.0.0 とする。

ここでいう準拠は、範囲が限られている。準拠スイートの全形式が通ることと、R7RS 付録Aのライブラリの必須識別子がすべて束縛されることを指す。スイートの外の振る舞いと、下の「既知の制限」は、準拠を保証しない。結果の正は生成物の [docs/status/conformance.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/status/conformance.md) で、`zig build test-conformance` が同じ結果を出す。ここには数を書き写さない。

このリリースは、リポジトリにアクセスできる人だけが取得できる(リポジトリは private である。[ADR-0020](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0020-repository-visibility-private.md))。ライセンスは付与していない(UNLICENSED、全権利保留。[ADR-0022](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0022-unlicensed-proprietary.md))。

## v0.5.0 からの変更

準拠スイートの不合格を直したもの:

- `(expt 0.0 0)` は、不正確な `1.0` を返す。以前は正確な `1` を返した(R7RS 6.2.6)。
- `(sqrt -1.0-0.0i)` のように、虚部が負の0の複素数の平方根の分岐の向きを直した。
- 指数の印 `s`、`f`、`d`、`l`(大文字も)を、`e` と同じ倍精度の指数の印として読む(`1s2` は `100.0`)。R7RS 6.2.5 が受け付けてよいとしている綴りで、精度の区別はしない。`write` は `e` で書く。v0.5.0 の既知の制限だった。
- 準拠スイートが使う `(chibi test)` の互換の実装(`lib/chibi/test.scm`)が、不正確な数を、上流と同じ規則の近似で比べる。処理系の振る舞いは変わらない。

そのほか、利用者に見える変更:

- `write` は、ASCII でない識別子(`λ` など)を縦棒なしで書く(`(write 'λ)` は `λ`)。読み戻すと同じシンボルになる。空白を含む綴りなどは、縦棒で囲んだままである。v0.5.0 では `|λ|` と書いた。
- REPL で、`#!fold-case` が、それを書いた行より後の行にも効く。`#!no-fold-case` で戻る。Web UI も、評価をまたいで効き、リセットで戻る。v0.5.0 の既知の制限だった。
- `environment`、`scheme-report-environment`、`null-environment` を繰り返し呼んでも、常駐のメモリが一定に収まる。v0.5.0 では伸び続け、ヒープの上限で止まらなかった。v0.5.0 の既知の制限だった。
- ファイルを読むときのリーダの、未閉じの括弧ごとの枠が、ヒープの上限に数えられる。ヒープの上限を下げた設定では、閉じていない `(` だけが続くファイルは `heap limit exceeded` で止まる。既定の上限(256 MiB)では、1 MiB までのファイルの枠は上限に届かず、`unexpected end of input` で終わる。
- 多くの値を返す `values` や継続の多値での起動が、ヒープの上限の余りに収まらないとき、確保の前に回収を要求してから呼び直す。以前は、回収できるごみがあっても `heap limit exceeded` で終わることがあった。

開発の仕組み:

- `zig build test-conformance` は、準拠スイートに落ちた形式、誤りになった形式、実行不能の形式が1件でもあるか、解決できない `import` があれば、非0で終わる。
- 評価器のファジングの対象と、リーダの初期入力を増やした(`zig build test --fuzz=<N> -Doptimize=ReleaseSafe`。手動と定期の実行だけ)。手元の実行では、失敗する入力は見つからなかった。

## 取得の確認

ダウンロードしたファイルが壊れていないことは、`SHA256SUMS` と同じディレクトリで次を実行して確かめる。

```sh
sha256sum -c SHA256SUMS
```

`SHA256SUMS` は成果物と同じ場所から配るので、破損や取り違えには効くが、改ざんには効かない。署名と attestation は行っていない([ADR-0034](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0034-release-shape.md))。

## 使い方

```sh
tar xzf sucheme-v1.0.0-x86_64-linux-musl.tar.gz
./sucheme-v1.0.0-x86_64-linux-musl/sucheme --version         # sucheme 1.0.0
./sucheme-v1.0.0-x86_64-linux-musl/sucheme                   # REPL
./sucheme-v1.0.0-x86_64-linux-musl/sucheme prog.scm a b      # ファイルのプログラムを、引数 a b を渡して実行する
./sucheme-v1.0.0-x86_64-linux-musl/sucheme -I lib prog.scm   # ライブラリの探索ルートを足す
```

引数なしで起動すると、標準入力が尽きるまで REPL が動く。終えるには、標準入力を閉じる(Linux と macOS の端末では Ctrl-D)か、`(import (scheme process-context))` のあとで `(exit)` を呼ぶ。

REPL とファイルのプログラムの最初の環境は、`(scheme base)` である。`display` と `write` は `(scheme write)`、`sqrt` や `exp` は `(scheme inexact)`、`exit` と `command-line` は `(scheme process-context)` にあるので、使う前に `import` する。

```scheme
(import (scheme base) (scheme write))
(display (/ 1 3)) (newline)                       ; 1/3
(write-string "warning\n" (current-error-port))   ; 標準エラーに出る
```

ファイル名を渡すと、そのファイルのプログラムを先頭から評価する。式の値は出力せず、プログラムが現在の出力ポートに書いたもの(`display`、`write-string` など)が標準出力に、現在のエラーポートに書いたものが標準エラーに出る。プログラムの `read` や `read-char` は標準入力から読む。終了ステータスは、最後まで実行すれば 0、実行時エラーで止まれば 1(stderr に `error: ` と説明を出す)、ファイルを読めなければ 66、プログラムが `exit` を呼べばその引数から決まる値である。標準入力のプログラム(`-`)は未実装で、69 で終了する。コマンドラインと終了ステータスの契約は `src/main.zig` の doc コメントが正である。

`-I <dir>` と `include` の探索の規則は v0.5.0 から変わっていない。`load` も、同じ探索ルートの規則でファイルを開く(名前は、いつも作業ディレクトリを基準にする)。プログラムが開くファイル(`open-input-file` など)は、探索ルートに制約されない。

Web UI は、アーカイブを展開したディレクトリで `node serve.mjs` を実行し、表示された `http://127.0.0.1:<ポート>/` をブラウザで開く。`file://` で開いても動かない([ADR-0021](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0021-no-github-pages-defer-hosting.md))。Web UI には、選んで実行できるサンプルが6個あり、入力したソースを URL のフラグメント(`#code=...`)に入れた共有リンクを作れる。Web UI では、`display` などの出力も、エラーポートへの出力も、結果と同じ欄に出る。ファイルは開けず(`file-error` になる)、標準入力は最初から終わりにある。

v0.5.0 で動いたものはすべて動く。機能の一覧は、段階ごとの [v0.4.0](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/releases/v0.4.0.md)(数の塔と Unicode)と [v0.5.0](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/releases/v0.5.0.md)(ポートと入出力、`eval`、`load`、`exit`、R7RS 付録Aのライブラリすべて)のリリースノートにある。

## 既知の制限

結果は決めた形で返るもの、または後の段階で直すものである。v1.0.0 の後に直すかどうかは、[docs/roadmap.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/roadmap.md) と [docs/design/open-questions.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) が正である。

後の段階で入るもの:

- 実行時のエラー(展開のあとのエラー)には、位置が付かない。`load` が読み込んだ形式と、`eval` に渡したデータの展開のエラーにも、位置は付かない。段階8で扱う。
- 標準入力のプログラム(`-`)。
- REPL の行編集(カーソル移動、履歴、補完)。

R7RS が実装に委ねている範囲で、直していないもの:

- マクロが導入したトップレベルの `define` と `define-syntax` は、衛生的でない。利用側の同じ綴りのトップレベルの変数を書き換える。R7RS 4.3 は、トップレベルの変数の定義が束縛を導入するかを実装に委ねていて、準拠スイートの 4.3 の節は通る。直すには識別子の解決の規則([ADR-0019](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0019-denotations-and-identifier-resolution.md))を変える新しい ADR が要り、時期は決めていない。
- `#!fold-case` の畳み込みは単純な畳み込みで、`ß` のように完全な畳み込みでだけ変わる文字は畳み込まない。単純な畳み込みのままにすると決めた。
- `string-downcase` は、語末のシグマを特別に扱わない(`(string-downcase "ΑΣ")` は `"ασ"`)。

性能とメモリ:

- パラメータの読み出しは、`parameterize` の入れ子の深さに比例して遅くなる。毎段、別のパラメータを `parameterize` する深い再帰で、束縛していないパラメータを読むと、深さの2乗になる。結果は正しく、メモリは有界である。受け入れた制約で、準拠テストの後の性能の見直しと同じ時期に見る([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「パラメータの読み出しの費用」)。
- GC の閾値と性能は暫定である(下の「暫定の値」)。
- ヒープの上限は、すべての確保を覆っていない。ファイルを読むときのリーダのラベルの表と、読み取りの内側の一時的な確保(トークン、文字列の作業用のバッファ)は、計上の外にある。ラベルの表は入力の大きさに比例し、一時的な確保は1つのトークンの長さで抑えられる。ファイルは 1 MiB までで、これを超えると読まずに断る。ライブラリの表と `import` の作業領域も、ヒープの上限の外にある([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「ライブラリの表と `import` の作業領域が、ヒープの上限の外にある」)。展開の作業も、最初のマクロの適用までは計上されない。`quote` が特殊形式に束縛されていない場所の循環したデータを展開器が辿り続けること、共有ラベルを重ねたコードで展開の作業が入力の大きさの指数になること、共有した `quote` を何度も置くとその数だけデータ全体を辿ることがあり、いずれもヒープの上限の誤りにならずにメモリや時間が伸びる([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「展開の作業を、最初のマクロの適用より前からヒープの上限に計上するか」)。
- 非常に多くの値を `values` で返すと、時間がかかる。原因の切り分けは行っていない。回収しても上限の余りに収まらない多値は、これまでどおり `heap limit exceeded` になる。
- `environment` の繰り返しのメモリの伸びは、`Heap.residentAllocator` の 4096 バイト以上の確保を `page_allocator` に回して止めた。原因は、計上の不足でなく、`smp_allocator` を裏にしたときの RSS の伸びである。その機序は仮説で、実測していない。直した代わりに、`environment` の繰り返しは時間がかかるようになった(増え方は [docs/plans/0019-phase5-ports-and-io.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/plans/0019-phase5-ports-and-io.md) の「環境の表の GC の圧力の割り当て」の「実装した対処」)。`mmap` の呼び出しも増えるが、同時に持つマップは増えない。4096 バイト未満の小さな確保の繰り返しが、同じ性質を持つかは確かめていない。
- 正確な数として読む綴り(整数と、`#e` を付けた小数など)の大きさに上限がある。桁は 100,000 個まで、指数の絶対値は 1,000,000 までで、超えると数として読まない(`unreadable token`。`string->number` は `#f`)。不正確な数として読む綴りは、上限を超えても読み、`+inf.0`、`-inf.0` か `0.0` になる。上限の内側でも、`#e1e1000000` のような綴りは1つ読むのに時間がかかり、その値を `write` で十進に書くのは非常に遅い。多倍長整数の演算そのものには、時間の上限が無い。桁数に対して、乗算は約1.6乗、有理数の加算(通分と約分)は2乗以上、`expt`、`rationalize`、`number->string` の十進の書き出しも桁数のべき乗で時間がかかる。因数の桁数が偏った積は、ヒープの上限の近くで、黙って遅い方法に切り替わることがある(結果は正しい)。測定と直し方の案は [open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「巨大な bignum の演算の時間」にある。
- 複素数の演算で、R7RS が結果を規定していない場合がある。正確な0の部分が無限大に掛かると `+nan.0` になる(`(* +i +inf.0+1.0i)`)。不正確な0の複素数での除算は `+nan.0` を含む結果になる(`(/ 1+2i 0.0+0.0i)`)。除算は分母の共役を掛ける素朴な式なので、分母の大きさが倍精度の範囲を超える場合も NaN になる見込みである([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「複素数の演算の、R7RS が規定しない結果」)。
- `exp` などの初等関数は、最後の桁が1だけずれることがある(`(exp 1)` は `2.7182818284590455`)。複素数の初等関数と2引数の `log` も同じである。符号つきの0の扱いは、C99 の複素数の関数と違うことがある。各部が倍精度の範囲の端に近い複素数では、`asin` などが有限の答えを失うことがある。

ライブラリと構文:

- `(scheme base)` や `(sucheme derived)` など埋め込みの標準ライブラリは、最初の `import` で読み込む。その前に利用者が同じ名前の `define-library` を評価すると、利用者の定義がその名前を取る(`import` の後なら「すでに定義されている」誤りになる)。R7RS はライブラリ名の予約を定めていない([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「埋め込みの標準ライブラリの名前を、最初の `import` の前に `define-library` で定義できる」)。
- 構文キーワードの名前のトップレベルの定義は、R7RS 5.4 が誤りの例に挙げる `(define define 3)` も受け付ける。値の式が実行時に失敗する定義(`(define if if)` など)のあとは、その特殊形式がそのセッションの間、未束縛の変数になる([open-questions](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「構文キーワードの名前への `define`」)。

入出力と REPL:

- 標準エラーが閉じているか書けないとき(`sucheme prog.scm 2>&-`、`2>/dev/full`)、プログラムが `current-error-port` に書いた時点で実行が打ち切られ、終了コード 1 で終わる。診断の書き先も標準エラーなので、何も出ない。REPL でも同じである。
- Web UI では、コンソールの入力は最初から終わりにある。`(read-char)` は EOF を返す。
- コンソールから `read` で読むとき、REPL の読み手のバッファ(1行 65536 バイト)より長いデータは読めない(`datum longer than the input buffer`)。`read` が読めない入力で失敗したあと、ポートはそのデータの頭に留まる。そのため、REPL で `(read)` が `)` で失敗すると、REPL が同じ `)` を読んで、誤りが2回出る。

## 動作保証の範囲

- 実行して確かめた: x86_64 Linux の実行ファイルは、リリースの成果物そのもの(`ReleaseSafe`)を、組み立ての直後に実行して `--version` と階乗の計算を確かめている。テストは Linux x86_64 で、プルリクエストへの push のたびに自動で走る。Windows x86_64 のテストと、規模を試すテストは、プルリクエストを ready にしたときに走る。
- ビルドだけ確かめた: Windows の実行ファイル、macOS(x86_64、aarch64)、Linux aarch64、Windows aarch64。リリースの成果物そのものは、これらの環境で実行して確かめていない。aarch64 の実行は、どこでも確かめていない([ADR-0033](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0033-aarch64-built-but-not-tested.md))。macOS は、署名も公証もしていない。
- Web UI: ブラウザ自動化のテストは無い。wasm のエクスポートを Node.js から呼ぶラウンドトリップのテストと、サンプルの評価と共有リンクの符号化のテストだけが自動で走る。ブラウザ固有の問題は検出されない。
- 問題が見つかった場合は、issue で知らせてほしい。

## 暫定の値

GC を起動する閾値(割り当ての倍率と最小値)は暫定である。性能は測っておらず、遅い。起動のたびに `(scheme base)` を展開するので、空の入力でも数ミリ秒かかる。ベンチマークは未実施である。準拠テストが通った後の性能の測定は、段階6の外に置いてあり、v1.0.0 には含まれない([docs/design/open-questions.md](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/design/open-questions.md) の「段階を定めずに保留しているもの」)。ヒープの上限に届くと `heap limit exceeded` で止まる([ADR-0031](https://github.com/suchi/sucheme-zig/blob/v1.0.0/docs/adr/0031-gc-at-machine-step-boundaries.md))。
