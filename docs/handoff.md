## 1スライスの流れ(実際にやってきた形)

1. 計画書の該当のスライスを読み、最初の失敗するテストを書く(TDD)。
2. 作業ツリーを分ける。`git worktree add /home/user/wt-<名前> -b feature/phaseN-slice-<id>-<内容> origin/main`。ブランチ名は英語の kebab-case で、段階とスライスが分かる形にする。主の作業ツリーは、コマンドの足場にだけ使い、書き換えない。
3. 実装する。編集のたびに、書き換えたファイルの `zig test src/<ファイル>.zig` と `zig fmt`。コミット前に、AGENTS.md の検証コマンド表の「全コミット」の行(`zig fmt --check .`、`zig build test`、`test-scheme`、`wasm`、`test-wasm`、`check-docs`、`check-extract`、`check-report`)を通す。`zig build test-scheme` は実行ファイルを作り直さない。`--version` などで実行ファイルを見るときは、先に `zig build` を打つ。
4. ミューテーションテストで、テストの強さを確かめる。コミットしてから、1か所を壊し、`zig build test test-scheme` が落ちるかを見て、`git checkout -- <ファイル>` で戻す。次の点に注意する。編集が当たらなかった場合(置換が0件か2件以上)と、コンパイルエラー(使われない引数など)は、テストが落ちたのではない。落ちた理由がコンパイルエラーでないことを確かめる。`zig build test` だけでなく `test-scheme` も走らせる。生き残ったら、テストを足して、同じ壊し方で落ちることを確かめる。
5. ドラフトの PR を作り(タイトルは英語、本文は日本語)、`subscribe_pr_activity` で購読する。本文には、変更内容、ユーザーに見てほしい点、確かめた事実、確認できていない点を書く。確かめていないことを確かめたと書かない。
6. 設計の意図を渡さないサブエージェントで、敵対的レビューを行う(下の「サブエージェントの使い方」)。指摘は、実物で再現してから直す。直しは1回の push にまとめる。
7. 自前のレビューが収束し、ドラフトの CI が緑で、main と競合しないときに、PR を ready にする(AGENTS.md に、エージェントが行ってよいとある)。ready にすると層2(`full.yml`)が走る。起動を確かめて、ユーザーに報告する。文書だけの PR では、層2 は起動しない(AGENTS.md と [ADR-0046](adr/0046-skip-slow-tier-for-docs-only-prs.md))。
8. 層2の結果を確かめ、緑なら、マージ依頼の報告を1つにまとめて出す(AGENTS.md の項目)。文書だけの PR では、層2 は走らないので、層1 の結果で出し、層2 の項目には「層2 は走らない(`paths-ignore` による)」と書く。マージはユーザーが行う。マージ後に、マージコミットの CI を確かめる。
9. 次のスライスは、前のスライスのマージを待つ必要がなければ、並行に始める。

## 報告の運用

- 言語は日本語。時刻は JST で書き、`date` で確かめる。送る前に、文面が日本語であることを確かめる。コマンド、識別子、貼り付けた外部のログは、そのままでよい。
- ユーザーのチャットの文を、コミットメッセージ、PR、文書、サブエージェントへの依頼文に写さない(AGENTS.md)。出来事と結論を、自分の言葉で書く。
- 報告するのは、状況が変わったときと、判断を求めるときだけである。結果を待つ間は、予約(`send_later`)を10分ごとに入れて確かめ、変化が無ければ報告しない。1時間ごとの保険の定期ルーチンが別にある。ユーザーの判断だけを待つ間は、10分ごとの予約を入れない。
- 「待ち」は、誰の何を待っているかを主語をつけて書く。ユーザーが今すぐ動けるものだけを、ユーザーの判断待ちに載せる。
- 判断を求めるメッセージは、何を求めているかが、そのメッセージから辿れる形で書く。おすすめを添える。
- 版をリリースの次の開発版(`0.3.0-dev` など)に移すときは、「戻す」ではなく「進める」「上げる」と書く(英語では bump)。過去の PR とコミットの表現は直さない(ユーザーが 2026-10-15 に判断した)。

## 環境の癖

- R7RS の原文(errata 訂正版)は、[docs/spec/](spec/README.md) の PDF にある(2026-10-16 から)。`pdftotext -layout docs/spec/errata-corrected-r7rs.pdf <出力先>` でテキストにして、`grep` で引く。仕様を書くときは、記憶でなく原文で確かめる。段階3の 3a と 3b と 3g は、原文を取得できない間に、記憶で書いた(3g の手続きの定義は、原文で確かめた。`member` と `assoc` の比較の呼び方の順は、原文が定めていない)。
- GitHub の操作は MCP のツール(`mcp__github__*`)で行う。`gh` の CLI は使えない。ツールは、セッションの途中で切れ、また現れる。切れたら `ToolSearch` で `select:<ツール名>` を打って読み直す。
- タグの push は、この環境からは HTTP 403 で拒否された(2026-10-15)。ブランチの push は通る。タグはユーザーが手元で打つ。承認を得たコマンド(`git tag -a vX.Y.Z <コミット> -m "sucheme vX.Y.Z"` と `git push origin vX.Y.Z`)を示して頼む。<コミット> は、リリースの準備の PR のマージコミットを、ハッシュで指定する。並行のレーンのマージで、main の先頭が先に進んでいることがある。
- main の push の CI は、同じ ref の古い実行を取り消す(`ci.yml` の `cancel-in-progress`)。マージが続くと、途中のマージコミットの CI は最後まで走らない。そのコミットの CI の緑が要るときは、同じ木の PR の先頭の CI を根拠にするか、取り消されたことを報告に書く。
- ガード用のフック(`.claude/hooks/`)は、2026-10-23 の suchi/sucheme-zig#183 から実際に働く。コマンドの文字列に、シークレットのファイル名やガードレールの設定のパスの綴り、`zig build --build-file` があると、確認か拒否になる。コミットメッセージのヒアドキュメントやスクリプトの引数の中の綴りも対象である。別の作業ツリーでビルドするときは、その作業ツリーに `cd` してから `zig build` を打つ。こうした綴りを含むスクリプトや試験の入力は、Write でファイルに書いてから使う。
- 手元の検証で、コマンドの出力を `tail` などに通すときは、`set -o pipefail` を付けるか、終了コードを別に確かめる。通した先の終了コードで緑と読み、赤のまま push したことがある(段階3の 3s)。
- この環境の git の作者は `Claude` である。コミットの末尾に、システムが指定する `Co-Authored-By` と `Claude-Session` の行を付ける。
- 主の作業ツリーは、古いコミットで切り離されている。作業は、`git worktree` で作った別の作業ツリーで行う。作業ツリーを元に戻す操作(`git checkout -- <ファイル>`、`git restore`、`git stash`、`git reset`)の前に、未コミットの変更が無いことを確かめる。ミューテーションは、先にコミットしてから行う。
- シェルのループで識別子を回すとき、`*` がファイル名に展開される。`set -f` を打つか、引用する。
- 作業ツリーごとに `.zig-cache` がある。ビルドは並行の作業ツリーで衝突しない。初回は遅い。
- `ruff` は、Python のファイルを触るときに `ruff check <ファイル>` で確かめる(AGENTS.md)。設定は根の `ruff.toml` で、規則は既定のままである。既存の警告は、触れるときに、そのファイルの分を直す。
- Zig の実行ファイルが無い環境では、`.zigversion` の版を Python の `ziglang` パッケージで入れられる(この環境ではそうしていた)。版が `.zigversion` と一致することを確かめる。
- サンドボックスの `/tmp` ではなく、セッションの作業用ディレクトリ(スクラッチパッド)に一時ファイルを置く。
- リモートのブランチの削除は、この環境からは HTTP 403 で拒否される(2026-10-29)。ブランチの作成と push は通る。削除はユーザーが手元で行う。ユーザーの環境は Windows なので、コマンドは1行で示す(行末の `\` による継続は使えない)。削除の前に、`git cherry origin/main origin/<ブランチ>` で固有のパッチが無いこと(または内容が main にあること)を確かめて、表で示す。閉じた PR の先頭は `refs/pull/<番号>/head` に残るので、ブランチを消しても、そのコミットは取り出せる。
- 別セッション(`create_session`)の VM に、zig が無いことがある(2026-10-29 の PR #209 の査読のセッション)。ziglang.org へは繋がらず、PyPI から取った zig の展開と実行は、自動承認の分類器に拒否された(外部から取得したコードの実行にあたる)。査読のように zig を走らせる用事は、zig を使える環境(親の環境のサブエージェント、または zig を持つ子のセッション)に任せる。起動の前に、`zig version` が通る環境かを確かめる。
- 子のセッションの Bash が、`cd <作業ツリー> && ... git commit ...` の形で、main にコミットすると判定されて止まる(2026-10-29)。`git -C <作業ツリー> ...` の別々の呼び出しにする。`zig build --build-file` も確認になる(上のフックの項)ので、子への指示に使わない。

## サブエージェントの使い方

- 使う場面は、独立した読み取りの調査と、敵対的レビューである。着手前に、範囲を狭く書く。依頼文に、範囲、読む文書、禁止すること(追跡されたファイルの編集、`git checkout`/`stash`/`reset`)、書き込み先、期限を書く。設計の意図は渡さない。
- 結果は、依頼したファイルに「実験ごとに」追記させる。最後の報告だけに頼らない。止まったかどうかは、そのファイルの更新時刻で見る。更新が15分止まったら、止めて、そこまでの結果で判断する(レビューが何も書かずに止まることが何度もあった)。
- 完走したレビューのうち、欠陥を見つけたのは、テストの強さの担当(ミューテーション)が多かった。挙動を広く試す担当は、見つけた件数が少なかった。小さな変更では、ミューテーションの担当だけにするのが効率的かもしれない(ユーザーへの確認事項に入れた)。
- 報告は、事実(再現した入力と出力)と疑いを分けさせる。報告の「一致する」「通る」は、私が再現するまで、事実として書かない。
- 走っている間は、`ListAgents` で状態を見る。完了通知が来ないことを、実行中の根拠にしない。

## 決まった進め方

段階2の終わりに確認した、製品でなく進め方についての9件。2026-10-15 に、ユーザーが、9件すべてで勧める案を採ると回答した。「勧める案」と書いた行が、採用した案である。反映先は、1・2・3・4・5・7・8・9が [AGENTS.md](../AGENTS.md)(1は [.agents/skills/watch-subagent/SKILL.md](../.agents/skills/watch-subagent/SKILL.md) も)、6が上の「環境の癖」である。経緯は [review/process-lessons.md](review/process-lessons.md) の「状況報告が、変化のない回も文脈を使った(段階2)」にある。

1. 状況報告の頻度。今は、待っている間、変化がなくても10分ごとに報告する規則である。同じ内容の報告が文脈を使う。
   - 勧める案: 変化があったときと、判断が要るときだけ報告する。1時間ごとの保険は残す。
2. 敵対的レビューの形。今は、2本のサブエージェントを、全スライスに走らせる。
   - 勧める案: コードの変更には、ミューテーションの担当1本を基本にする。挙動を広く試す担当は、変更が大きいか、入力の大きさに比例する確保を入れたときだけ足す。文書だけの変更には走らせない。
3. 層2の CI の順序。今は、レビューが終わって ready にしてから走り、逐次に待つ。
   - 勧める案: 今のまま。Actions の分数([plans/0015-ci-minutes-reduction.md](plans/0015-ci-minutes-reduction.md))を節約する方針と合う。急ぐスライスだけ、レビューと並行して手動で起動する。
4. 見積りの単位。今は「半日」「1日」である。
   - 勧める案: 時間単位に改め、段階3の計画書から、スライスごとに「ready まで」と「マージまで」を分けて見積る。補正は、[0012](plans/0012-schedule-estimates-and-actuals.md) の方法で続ける。
5. ユーザーの判断を求める範囲。段階2では、「合意を求める点」の勧める案がほとんど承認された。
   - 勧める案: 設計の選択、データ形式、依存関係、破壊的操作、公開するもの(リリース、タグ)は、今までどおり判断を求める。範囲が小さく戻せる選択(文書の構成、テストの足し方、内部の名前)は、勧める案で進めて、PR に書くだけにする。
6. タグの push。この環境からは拒否される。
   - 勧める案: ユーザーが手元で打つ今の形を続ける。リポジトリのルールセットや権限を変えて、この環境から打てるようにするのは、セキュリティ設定の変更なので勧めない。
7. セッションの区切り。段階2は、1つのセッションで、文脈の圧縮を何度も挟んで進んだ。
   - 勧める案: 段階の終わりごとに、新しいセッションで始める。引き継ぎは、この文書と roadmap と計画書で足りるようにしておく。
8. 夜間の作業。段階2は、夜間にもマージされた。
   - 勧める案: 今のまま。ただし、ユーザーの判断が要る場面で、夜間に止まった場合は、翌朝に判断をまとめて求める。
9. Copilot のレビュー依頼。AGENTS.md は、自前のレビューが収束した後の任意の依頼として定めている。段階2の最後の6スライスを進めたセッションでは、依頼しなかった。
   - 勧める案: 依頼は、段階の終わりに、変更が大きいスライスに限る任意の手順として残す。依頼しなかったことを、毎回の報告に書かない。
