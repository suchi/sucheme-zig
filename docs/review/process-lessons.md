# 進め方の学び

段階0で実際に起きた失敗と、その対処を記録する。原因と対処だけを書き、件数や所要時間の実測値は書かない。巡ごとの指摘は [stage0-findings.md](stage0-findings.md) が正である。

この文書は、新しいセッションや別の実行環境で同じ失敗を繰り返さないために置いてある。判断の根拠を持つものは ADR にあり、ここはその入口である。運用の規則そのものは [AGENTS.md](../../AGENTS.md) が正で、ここに複製しない。

## レビューの巡回が終わらなかった

段階0の自己敵対的レビューは20巡を超えた。製品コードは増えないまま、検査ツールと文書だけが育った。

原因は4つあった。停止条件を出力の側(新規指摘ゼロ)に置いたこと。重要度を帰結ではなく種類で決めたので、検証が黙って止まる件と帳簿の数え上げの食い違いが同じ重さでマージの門を塞いだこと。成果物の寿命を区別せず、段階が終われば用済みの計画書と何年も効く ADR に同じ労力をかけたこと。帳簿が導ける数を2箇所に持っていたので、食い違いが毎巡湧いたこと。

対処は [ADR-0027](../adr/0027-severity-by-consequence-and-a-cost-side-stop.md) にある。重要度を帰結で定め、収束の判定をその巡の必須の中身で行い、頻度を寿命で分け、導ける列を落とした。

止め方は巡の数で決めない。終わらなさそうなら、品質基準を変えるか、いったん機能を減らして次に進む。[ADR-0018](../adr/0018-incremental-vertical-slices.md) の漸進的な進め方そのもので、新しい規律ではない。段階0で実際に2回これをやったが、どちらも10巡遅く、この2手が選択肢として名前を持っていなかったので、巡を足すことが既定の行動になっていた。

## 検査ツールが製品より大きく育った

「巡をまたいで再発した類型は検査として足す」というルールの適用先を限定しなかった。コードの振る舞いに適用すれば有限だが、文書の書き方に適用すると終わらない。同じ意味を書く Markdown の綴りは有限集合ではない。

対処は [ADR-0026](../adr/0026-verify-facts-about-code-not-prose.md) にある。検査の対象をコードと生成物についての事実に限り、文書の書き方を見る検査を撤回した。

同じ構造が後にリンク検査で再発した。リンク切れはファイルの実在についての事実だが、リンクがどこにあるかを見つける作業は Markdown の解析であり、そこが無限集合である。ADR-0026 に線を引いた。

## 穴は綴りで閉じるより不変条件を双方向にする

検証コマンド表と CI の照合は、表から CI への一方向では表の読み取りを正確にする必要があり、綴りの防御が必要になった。CI から表への照合を足すと、読み取れない行は CI の段に対応が無い形で現れる。綴りを1つも知らずに閉じる。

ただし双方向だけでは足りない。互いにしか照合していない2つは、両方を同時に弱めると成立する。対の外に点が要る。`build.zig` が宣言する step から一覧を作って渡すのがそれで、要求を消すには step を消すことになり、その瞬間にコマンド自体が動かなくなる。

## 守りは「実行されるか」だけでなく「結果が聞かれるか」を見る

step が run を依存に持つことだけを確かめていたので、`run.stdio = .{ .check = .empty }` の1行で終了コードが読まれなくなり、検査が診断を出しながら成功した。テスト step でも、意図的に失敗するテストを置いて成功した。

存在の確認と結果の確認は対である。片方だけを持っていた。対になる2つの判定のうち片方しか直していない形は、段階0で繰り返し現れた類型である。

## configure 段の守りは同じファイルの編集に勝てない

`build.zig` の中の守りは `build()` の実行中に状態を読むので、その後に書き換えれば通る。Zig 0.17 には make 段にコードを差し込む経路が無い。守りが閉じるのは1箇所の編集で検証が黙って止まる形だけで、`build.zig` 自身への変更に対する防壁は差分のレビューである。ADR-0026 に限界として記録した。

## 帳簿に「訂正した」と書く前に実物を見る

修正の一覧と帳簿の更新を同じスクリプトにまとめ、スクリプトが途中で中止したのに帳簿だけ先に書いた。2巡続けて「訂正」と書いて直っていない項目が出た。

先に修正を適用し、該当行が変わったことを1件ずつ確認してから状態欄を書く。状態欄は「直したと思っていること」ではなく「確かめたこと」を書く欄である。

## 実測値を散文に書かない

ADR に書いた行数が、どのコミットとも一致しない作業ツリーの途中の値だった。しかもその ADR は「実測値を散文に書かない」という規則の根拠になった文書である。

導ける数を2箇所に書かない。見つけたら検査を足すのではなく片方を消す。

## レビュアに実機確認をさせるときの形

サブエージェントに「シェルで複製を作ってシナリオごとにリセットしろ」と指示すると、`git clean -f` が承認の判定に当たり、シナリオごとに承認待ちが入る。1巡で数十回になり、何時間も止まる。

シナリオを1つのスクリプトにまとめ、複製の作成・リセット・検証コマンドの実行をそのスクリプトの中(Python の `subprocess` など、Bash ツールを通らない経路)で行わせる。承認はスクリプトの起動1回だけになる。同じ指示に変えた巡で、所要時間が1桁縮んだ。

実機確認の形そのものも記録しておく。使い捨ての複製を毎回作ると、空のビルドキャッシュから検査ツールを再コンパイルするので1シナリオに数秒かかる。複製を1つ作って git 管理し、シナリオごとに戻し、ビルドキャッシュを複製の外に置いて共有すると、1シナリオが1秒未満になる。穴のシナリオと、正当な記述が緑のままであることの対照を必ず両方入れる。

## 判定関数を足したらテストで固定する

純粋な判定関数を足すコミットで、その関数のテストも足す。テストが実際にその関数を固定しているかは、関数の挙動を機械的に変えてテストが落ちるかで確かめる。段階0では、足した関数をどれもテストで固定しておらず、レビュアが6つを壊して全部緑だった。

## 待たせるときは状況を報告する

長時間走るサブエージェントやバックグラウンドのコマンドを抱えると、黙って待つ時間が生まれる。待っている側からは、進んでいるのか詰まっているのか、自分の承認を待っているのかが見えない。10分以上待たせるときは、作業状況と各エージェントの状態、ブロックしている事項を報告する。報告だけで終わらせず、判断が必要なら選択肢を示して求める。

ファイル活動の有無を「止まっている」の根拠にしない。読解中は活動がゼロになる。この指標でハングと誤判断し、進んでいたレビュアを停止したことがある。

## 承認はまとめて聴き、現在地を示す

作業ブロックに入る前に、そこで打つ予定のコマンドを列挙して1回でまとめて許可を得る。コマンドを打つ度に確認を求めると、文脈なしに判断を求める形になって負担が大きい。

報告と承認依頼には「全体計画のどの手順の、何件中の何件目か」を書く。現在地が見えないと、終わりが見えないという不安が生まれる。

## 止められたサブエージェントを実行中と思い込んだ

敵対的レビューをバックグラウンドのサブエージェントに任せたところ、ユーザーの操作で止められていたのに、完了通知が来ないことを「まだ実行中」と受け取って、長い間待った。止められたサブエージェントは通知を返さない。ファイルの更新時刻も手掛かりにならなかった。出力ファイルは完了まで一度も変わらないことがある。

原因は、通知の不在を状態の根拠にしたことと、生存を確かめる手順が無かったことである。AGENTS.md の「10分以上待たせるときは報告する」は、いつ報告するかを決めていても、待っている相手が生きているかを確かめる手段までは決めていなかった。

対処は [.agents/skills/watch-subagent/SKILL.md](../../.agents/skills/watch-subagent/SKILL.md) にある。起動時に自分への通知を予約し、通知で起きたときに状態を直接確かめる。サブエージェントは `ListAgents` と `SendMessage` で、別セッションは `get_session` の状態で見る。長く走る用事は、起動したセッションの寿命に縛られない別セッションに任せる。止まっていれば理由を添えて報告し、承認待ちなら代わりに承認せずにリンクを渡す。打ち切りの時刻を過ぎたら選択肢を示す。

## 検証が遅いまま並行にしても速くならない

スライス 1h で、ミューテーションテストを3つのサブエージェントに並行して任せたが、40分を超えても終わらなかった。原因は、ミューテーション1件ごとに全体のユニットテスト(Debug ビルドでは検査用のアロケータが遅い深い再帰のテストが数個あり、それで大半を占める)とスキームのテストを丸ごと走らせていたことである。並行にしても、1件の遅さは変わらず、台数が4コアを取り合うだけだった。待つ側は、進行を見る手段が無く、完了通知が来ないまま待った。

見るべきだったのは、並行にする前の1件あたりの時間である。書き換えたファイルのテストだけを走らせれば足りるのに、全体を走らせていた。`zig test src/<ファイル>.zig` は、全体の `zig build test` よりずっと速い。測り方は次のとおり。両方を実行して時間を比べる。

- 全体: `zig build test`
- 1ファイル: `zig test src/char_syntax.zig`

ミューテーションテストは、ファイル単位の `zig test` で捕まるかを先に見て、生き残ったものだけ全体で確かめる。実行する作業ディレクトリが正しいことを、スクリプトが自分で確かめる(複製の作成に失敗したとき、メインのリポジトリのファイルを書き換えかけた)。

待ち時間が想定より長いと気づいたら、待ちを延ばす前に、1件あたりの時間を測る。

## 症状を消して真因を調べなかった(CI のキャッシュ)

Windows の CI が `maker.exe: FileNotFound` で落ち続けたとき、最初は「壊れたキャッシュを消してください」とユーザーに頼んだ。同じ日にキャッシュ領域が上限の 10 GB に達していたと、ユーザーが指摘した。削除では、同じ状態に戻る。症状への対処で終え、なぜ壊れたキャッシュが作られ、なぜ選ばれ続けたのかを調べなかった。

調べると、原因の連鎖があった([ADR-0032](../adr/0032-ci-zig-cache-saved-only-by-successful-runs.md))。展開の途中で取り消されたジョブが、不完全なキャッシュを保存し、検証なしに最新として復元され、失敗したジョブがそれをまた保存した。ログの読みで確かめられる事実だった。

CI が同じ形で2回落ちたら、再実行や手作業の削除の前に、なぜを5回たどる。

- 失敗の最初のログに戻る。どのランが最初に落ちたか、その直前のランは何だったか。
- 「壊れたもの」を作った箇所を、そのジョブのログで探す。作られた時刻と、保存や書き込みの記録を見る。
- 壊れたものが残り続ける仕組みと、自力で抜け出す道があるかを確かめる。
- 対策は、症状を消す手作業でなく、真因を設計から除くものにする。復旧の手順も設計に含める。

外部のアクションを使うときは、その後処理が何を保存するかを、固定した版のソースで読む。ジョブの成否を見ずに保存するアクションは、取り消しと失敗をキャッシュに持ち込む。

## 同じ種類の過ちを繰り返した(原因への対策を別に打つ)

2026-10-11 の1つのセッションで、同じ形の過ちを繰り返した。ユーザーから、原因への対策も別に打つよう求められた。復旧だけでなく、原因への対策を規則にした。規則は [AGENTS.md](../../AGENTS.md) の「進め方」にある。

過ちと、原因と、対策を並べる。

| 過ち | 原因 | 原因への対策 |
| --- | --- | --- |
| 「N点の回答をお待ちしています」と書いたが、N点が何で、どこに書いてあるかを示さなかった(「問い11件」と「合意を求める点9点」で2回) | 求める点への道筋を相手が辿れるかを、送る前に確かめない。件数だけを書く癖があった。規則も確認の手順もなかった。(当初は「中身を全部書く」規則にしたが、ユーザーが、場所を指すリンクがあれば中身の繰り返しは要らないと指摘したので、規則を軽くした) | 判断を求めるメッセージには、求める点の場所を節まで指すリンクと、おすすめの要点を添える規則を足した。送る前に、相手が迷わず辿り着けるかを確かめる |
| 「マージ待ちは #37、#40、#42 です」と書いたが、ユーザーの判断を待つものと、私が CI の結果を待つものが区別できなかった | 「待ち」の主語(誰が誰の何を待つか)を書く習慣がなかった。ユーザー側とエージェント側の待ちを同じ語で書いていた | 「待ち」には主語をつけ、ユーザーの判断待ちとエージェント自身の待ちを分けて書く規則を足した |
| 「#40 は他と触るファイルが重ならず、順序の制約はない」と報告したが、#37 のマージで #40 が競合した(ユーザーに指摘された) | 開いている PR 同士の変更ファイルの重なりを、報告の前に確かめなかった。マージのたびに残りの PR の競合を確かめる手順もなかった | 順序の報告の前に重なりを確かめ、マージのあとに残りの PR の競合を先に解く規則を足した |

## ユーザーの判断を待つ間に、何も動かしていなかった

2026-10-11 に、ユーザーから、タスクが止まったまま気づかない状況が繰り返されている、と指摘された。確かめると、動いているものが何もなかった。K1 から K5 の実装と敵対的レビューがすべて完了し、PR のマージ判断をユーザーに報告したあと、独立して進められる作業を起動せずに待っていた。生存確認の予約も、発火したあとに作り直していなかった。

| 過ち | 原因 | 原因への対策 |
| --- | --- | --- |
| 判断待ちの報告を出したあと、動いているものが 0 件になった | 生存確認は「動いているエージェントを見張る」手順で、動いているものが 0 件になる状態を見る手順がなかった。待つ対象が変わるたびに、独立した作業があるかを確かめなかった | 待つ報告を出す前に、動いているものを数え、0 件なら独立した作業を起動してから報告する規則を足した。規則の条件と例外は [AGENTS.md](../../AGENTS.md) の「進め方」にある |
| 生存確認の予約が、発火したあとに作り直されなかった | 予約を「1回ごとに作り直す」運用で、作り直しを忘れたとき気づく手順がなかった。エージェントが走っているのに予約が 0 件の状態は、数えなければ見えない | 同じ規則に、エージェントが走っているのに予約が 0 件なら先に予約する条項を足した。「私が待っています」と書くときは、起こす仕組みがあることも確かめる |

同じ形の指摘が繰り返されたのは、前の対策が「止まっているものを見つける」に偏り、「動かすべきものが動いていない」を見る目がなかったためである。

同じ日に、もう1つ指摘を受けた。「あなたの判断待ち」の欄に、「取り込み後の CI とレイヤー2の結果が出てから、あらためて報告します」という項目を載せていた。ユーザーから、エージェントの結果待ちは判断待ちの欄に載せないよう、指摘された。これは、上の「同じ種類の過ちを繰り返した」の表の2行目(「待ち」に主語がない)と同じ形の再発である。前の対策は主語を書く規則で、その主語が正しい欄に載っているかは決めていなかった。

| 過ち | 原因 | 原因への対策 |
| --- | --- | --- |
| エージェントが CI の結果を待つ項目を、ユーザーの判断待ちの欄に載せた | 「ユーザーの判断待ち」に載せる条件を決めていなかった。ユーザーが関わる案件であることと、ユーザーが今動けることを区別していなかった | 判断待ちに載せるものの条件を、既存の「待ち」の規則に足した |

## ユーザーの中断でサブエージェントが止められていた

2026-10-12 に、ユーザーから、サブエージェントが止まったまま待ち続けた件の原因は、ターンの中断である、と指摘された。中断すると、動いているバックグラウンドのサブエージェントが止められる。「止められたサブエージェントを実行中と思い込んだ」の節の事例は、中断が引き金だった可能性がある。「ユーザーの判断を待つ間に、何も動かしていなかった」の節の事例と中断の関係は、記録から確かめられていない。

「なぜ」を繰り返した経緯は次のとおり。

1. なぜ長く待ち続けたか: 動いていると思っていたサブエージェントが、止まっていたから。
2. なぜ止まっていたか: ユーザーがターンを中断すると、バックグラウンドのサブエージェントが止められるから(ユーザーの観察による。公式文書では確かめていない)。
3. なぜユーザーは気づけなかったか: ユーザーから、中断がバックグラウンドのサブエージェントに影響することを知らなかったと説明された。

5. なぜ手順で防げなかったか: 手順が、中断を「動いているものの状態が変わる契機」として扱っていなかった。生存確認は予約した時刻に起きる仕組みで、中断の直後に確かめる決まりがなかった。

| 過ち | 原因 | 原因への対策 |
| --- | --- | --- |

## 検証の数え方が、シェルの展開で狂った(段階2)

## マージを求める報告に、「待機でかまいません」と書いた(段階3)

- [handoff.md](../handoff.md) の「環境の癖」に、`zig build --build-file` がフックで確認になると書いてあるのに、子への指示にその形を使い、子が止まった。親が、指示の前に handoff.md を読み直していなかった。
- 「残す」と報告した内容を、ユーザーが削除した。報告の中で、削除してよいものと、残すものの区別が、表の上で並んでいて、取り違えやすかった。handoff.md の旧い記述が、その表の作り方を勧めていたことも、原因の1つである。

違反ではなく、環境の制約として扱ったものが1つある。10分を超える査読を、別セッションでなくサブエージェントに任せた件である。別セッションの VM に zig が無く、取得したコードの実行が自動承認の分類器に拒否されたため、親の環境のサブエージェントに移した。この例外は、[handoff.md](../handoff.md) の「環境の癖」に、注意点とともに記録した。

原因は、点検の項目が、巡回の予約の文面に入っていなかったことである。規則は文書にあるが、毎回の巡回で照らす仕組みが無く、夜間の「報告しない」という判断を、昼の巡回でも引き継いだ。同じ形の違反は、段階2の「状況報告が、変化のない回も文脈を使った」と、段階3の「待機でかまいません」の事例にもある。

対処は次のとおりである。

- 巡回の予約の文面に、規則の確認(報告に関する規則)を入れ、間隔を10分に戻した。AGENTS.md に、タイトル、記録の置き場所、巡回の文面の規則を足した。
- 委任の及ぶ範囲を、AGENTS.md の規則にした。示していない操作は、委任があっても、実行の前に確認を取る。
- 子への指示を書く前に、handoff.md の「環境の癖」を読み直す(handoff.md に書いた)。
- 削除するものと残すものを、別の表で示す(handoff.md に書いた)。
- 最初の push で計画書の骨組みを残す項目を、0017 の依頼文の一覧に足した。

再発したら、点検を巡回の予約でなく、報告の送信の直前の手順にすることを検討する。

## 完了した作業を、古いセッションが重複してやり直した(段階4)

2026-10-29 に、段階4のスライス 4u1 の古い子セッション(2026-10-27 に、UCD の取り込みをやり直す目的で起動したもの)が、動き出して、UCD 18.0.0 の5ファイルを取り込み直し、`feature/phase4-slice-4u1-unicode-generator` に push した。同じ取り込みは、別のセッションの [suchi/sucheme-zig#201](https://github.com/suchi/sucheme-zig/pull/201) が先に完成させ、2026-10-28 08:22 UTC にマージされていた。子は、ローカルの検証が通ったあとに PR の状態を調べて重複に気づき、PR を作らずに止まって、親に報告した。誤った内容が `main` に入ることはなかった。残ったのは、古い土台の上に載った重複のブランチ1本で、この環境からは削除できないため、ユーザーが手元で削除した。

起きたことの経緯は次のとおりである(確かめたもの)。

- 4u1 は、ネットワークの許可が反映されず、取り込みに失敗するたびに、起動し直したセッションが複数あった。その後、別のセッションが取り込みを完成させ、PR がマージされた。
- 古いセッションに、完了の連絡や停止の指示を送った記録は、親の履歴の範囲では見つからなかった。ボードでは、止まったセッションを「待機」として残す扱いだった。
- 古いセッションは、起動時の依頼文の前提(取り込みが未完了であること)のまま作業を進め、検証を通してから、初めて PR の状態を調べた。

何が古いセッションを動かしたかは、確かめられていない(セッションの記録の範囲では、動き出した時点の直前の入力が見つからなかった)。環境側の再開か、通知による起動かは、推測にとどまる。

原因は、手順に2つの欠落があったことである。

- 親の側: 作業が別のセッションで完了したとき、元のセッションに停止を伝える手順が無かった。止まったセッションを「待機」のまま残す扱いで、あとで動き出しても害が出ないようにする歯止めが無かった。リモートのブランチの一覧を巡回で見ていなかったので、重複の push に、報告より前に気づく仕組みも無かった。
- 子の側: 中断のあとで動き出したときに、前提が変わっていないかを確かめる手順が、依頼文の項目に無かった。そのため、作業を続けてから、完了後の確認で初めて気づいた。

対処は次のとおりである。

- 復旧: 重複のブランチを、ユーザーが削除した(削除後に、リモートの一覧から消えていることを確かめた)。古いセッションには、以後の作業と push をしないよう伝えた。
- 原因への対策: [docs/plans/0017-parallel-lanes.md](../plans/0017-parallel-lanes.md) に、3つを足した。(1)「担当を終えるとき」の節: 完了・引き継ぎ・やり直しのとき、元のセッションに停止を伝え、ボードで「完了」にし、終了(アーカイブ)は段階の終わりにユーザーの確認を取る。(2)「子セッションへの依頼文に必ず書くこと」に、再開したときの確認(`git fetch`、PR の一覧、計画書の状態、`git cherry`)を足した。(3) 親の巡回に、リモートのブランチの一覧の比較を足した。

同じ形の問題が再び起きたら、再開したときの確認を依頼文の項目でなく、ブランチの push を止める検査(フックなど)にすることを検討する。ただし、フックの変更はユーザーの承認が要る。

## 開発ボードが、実際の状況より古いまま残った(段階4から5)

2026-10-29 に、ユーザーから、開発ボードが更新されていないことを2回指摘された。1回目の時点で、ボードは、開いている PR を1件と書いていたが、実際は3件あり、「最終更新」は5日前のままだった。ユーザーの待ちの欄は、データが空のときに読み込みに失敗していた。2回目は、1回目の更新から約30分のうちに、ブランチの削除の判断が済んだこと、PR を1件開いたこと、層2 の進み具合が、ボードに反映されていなかった。完了済みの査読の担当が、「作業中」のまま数時間残っていた行もあった。更新の時刻を、書いた時刻でなく推定した時刻にしていた(数分先の時刻を入れた回があった)。

原因は次のとおりである(確かめたもの)。

- ボードの更新は、親が手で行う作業で、1回に6回以上の呼び出し(JSON の作成、アップロード、データの更新)が要る。更新を、巡回の予約の文面の一項目としてしか位置づけておらず、別の依頼や通知への対応が重なると、更新が後回しになった。
- ボードの中身は、GitHub の表示を取り直した値でなく、親が手で書き写した値で、書き換えが漏れても誰も気づけなかった。画面にも、いつ更新されたものかが分かる表示が無かった。そのため、ユーザーが、合っているかを自分で確かめるしかなかった。
- 読み込みの失敗(空のファイル)は、ユーザーの画面にだけ出て、親は気づかなかった。

対処は次のとおりである。

- 復旧: ボードを、取り直した値で更新した。空のファイルで失敗する問題は、「該当なしを表す1行」を置いて直した。
- 原因への対策: [docs/plans/0017-parallel-lanes.md](../plans/0017-parallel-lanes.md) に「開発ボード」の節を足した。更新を、巡回でなく、状態が変わる出来事に結びつけること、報告より前に更新すること、時刻は実際の時刻を取ること、終わった担当を残さないこと。ボードには、最終更新からの経過を表示し、30 分以上たつと古い可能性を示すようにした。
- 手作業が残る限り、漏れは完全には防げない。PR の部分を GitHub から自動で読む案は、依存関係の追加にあたるので、ユーザーの判断を待っている。

同じ形は、2026-10-31 に再発した。ボードは、11:28 JST を最後に更新されず、約 1 時間 40 分後に、ユーザーから、古すぎると指摘された。この間、更新を止めていたのは、書き込み(`db_write`)がユーザー側の承認の確認を毎回要すると分かり、更新の方式を決めるまで保留していたからである(経緯は「原因を調べずに、迂回策や現状維持を勧めた(段階5)」の節にある)。保留の間、代わりの画面は用意しなかった。

原因は、前の対策が、更新の「タイミング」だけを直して、「親が手で書き写す」構造を残したことである。この構造は、(1) 更新が親の行動に依存する、(2) 書き込みのたびに承認が要る、という2つの弱点を持つ。2回目の指摘で、2つが同時に表に出た。保留の間に代わりの画面を用意しなかったことは、運用の穴だった。

対処は2つである。復旧は、ユーザーの了承を得て、古いボードを削除し、代わりの画面を GitHub のラベル `needs-user`(PR と Issue)にしたことである。ユーザーの作業のうち PR でないものは、Issue にした。原因への対策は、状態の正を GitHub に置き、画面を手で書き写さないことと、ラベルの同期を巡回の固定の手順にしたことである([docs/plans/0017-parallel-lanes.md](../plans/0017-parallel-lanes.md) の「開発状況の画面」)。PR の状態は GitHub が自動で最新にし、ラベルの付け外しは承認の確認が出ない。

## テストが、絶対パスの形を Linux のものと仮定した(段階5)

スライス 5d(suchi/sucheme-zig#160)で足した `src/main.zig` のテストが、層2 の Windows のジョブで落ちた。テストは、一時ディレクトリの絶対パスが `/` で始まると仮定して、誤りの説明の先頭を `error: /` と比べていた。Windows のパスは `D:\...` で始まる。製品のコードは正しく、テストだけの誤りだった。ready にしたあとの push で直したので、層2 をもう一度走らせることになった。

原因は、層1 が Linux でしか走らないことにある。OS ごとに形の違うもの(パスの先頭、区切り文字)を仮定したテストは、層1 を緑のまま通り、層2 の Windows のジョブで初めて見える([ADR-0036](../adr/0036-windows-tests-in-the-slow-tier.md))。テストを書くときの確認に、この観点が無かった。

対処は、テストで絶対パスの形(先頭の文字、区切り文字)を仮定しないことである。一時ディレクトリの下のパスを含む出力を比べるときは、テストが組み立てたパスそのものと比べるか、OS で変わらない部分(ファイル名から後ろ)だけを比べる。`src/sucheme.zig` の `include` のテストは、木のパス(`Tree.path`)から期待値を組み立てていたので、Windows でも通った。

## 日本語で書く規則の取りこぼしが、再び起きた(段階5)

対処は、次の3つである。報告は、直前の文面を写さず、そのときの事実を箇条書きにしてから、日本語で新しく書く。1時間ごとの定期ルーチンの文面にも、言語の確認を足した。送る前に、本文が日本語であることを確かめる。

## 合意済みの範囲が、どのスライスにも割り当てられずに残った(段階3)

計画書 0016 の「合意を求める点」の2で、数値塔を要らない整数の手続き15個を段階3に入れることが、2026-10-16 に決まった。結論は合意を求める点の節にだけ書かれ、スライスの表の完了条件にも roadmap の段階3の作業項目にも写されなかった。どのスライスも実装しないまま段階の最後まで残り、2026-10-23 に、3r の下調べ(main の実行ファイルで、計画書の表の識別子を1つずつ評価した)で見つかった。スライス 3s(suchi/sucheme-zig#178)を足して入れた。

## パイプの最後の終了コードで、検証を緑と読んだ(段階3)

スライス 3s で、push の前の手元の検証を、`zig build test-wasm 2>&1 | tail -1` の形で走らせた。`test-wasm` は失敗していたが、パイプの終了コードは `tail` のもの(0)で、緑と読んで push した。層1 の CI が赤になり、1巡を使った(直しは a94670d)。

原因は、検証コマンドの終了コードを、出力を短くするためのパイプが隠したことである。出力の最後の1行だけを見ると、失敗の行が `tail` の範囲の外に落ちることもある。

## 原因を調べずに、迂回策や現状維持を勧めた(段階5)

親のセッションが、原因を調べずに案を出す形の誤りを、2026-10-30 に1回、2026-10-31 に2回起こした(Zig、コネクタ、ボードの更新)。ユーザーから、迂回策に早く移りすぎるという指摘を受けた。

- Zig が親の環境から消えていた。再起動のあと、`/home/user/sucheme-zig` 以外のファイルが無くなっていた。親は、PyPI の `ziglang` で入れ直す案だけを示し、なぜ消えたかを調べなかった。後で調べると、公式文書は、導入を残すには環境の setup script に書くことを求めていた。手で入れたものは、再起動で失われる。この説明は、再起動後のファイルの状態(作業ツリー以外が無い)とも合う。ただし、setup script の中身はユーザーの環境設定にあり、親は読めないので、script に Zig の導入が入っていたかは確かめていない。
- GitHub のコネクタが、claude.ai の設定では接続済みなのに、親の道具の一覧(`ListConnectors`)に出なかった。親は、出ない理由を調べずに「今のままにするのがおすすめ」と答えた。コネクタはセッションの開始時に読み込まれるという公式文書の記述と、GitHub のアカウント連携は別の仕組みだという記述が、手の届く範囲にあった。新しいセッションで一覧を取り直せば切り分けられた。取り直した結果は、親の一覧と同じ3件(Gmail、Google Calendar、Google Drive)で、GitHub は無かった。このため、接続がセッションの開始より後だったという仮説は否定された。GitHub のツール(`mcp__github__*`)は、リポジトリを付けたセッションにだけあり、リポジトリを付けない調査用のセッションには無かった。現時点の説明は、「GitHub 連携」が、コネクタ(MCP)でなく、アカウントとリポジトリの連携であることである。ページの `mcp` の機能から GitHub を呼べるかは、確かめていない。
- 両方に共通して、AGENTS.md には「原因を特定してから対処する」という規則が既にあった。親は、案を出す手順の中に、この規則を照らす点を持っていなかった。

原因は、案を出す前の手順に、原因の仮説と証拠を書く点が無かったことである。規則は「迂回しない」と書くだけで、迂回や現状維持を勧めるときに何を添えるかを定めていなかった。そのため、調べる手段が手の届くところにあっても、案が先に出た。

対処は2つである。復旧は、Zig を入れ直したこと(ユーザーの許可のもとで、PyPI の `ziglang` 0.17.0 の SHA256 を、PyPI のメタデータの値と照合して入れた)と、コネクタの切り分けを行ったことである。原因への対策は、AGENTS.md の該当の項に、案を勧める前に、原因の仮説、確かめた証拠、確かめていないことと確かめ方を書く規則を足したことである。あわせて、環境の道具が消えたときは、setup script への追記か記録で対策する規則を足した。同じ形がもう一度起きたら、案を出す手順のほうを見直す。

同じ形は、規則を足した同じ日(2026-10-31)に、もう一度起きた。ボードを更新する道具が、`ArtifactData` から `mcp__claude-artifacts__*` に入れ替わったとき、親は、更新できることだけを確かめて、09:56 JST から 11:28 JST まで、状態が変わるたびに `db_write` で書き込んだ。規則の追加(10:05 JST ごろ)より前に始まり、追加のあとも続いた。この書き込みは、ユーザー側で承認の確認が出る操作だった(ユーザーが、`db_write` だと答えた)。親は、承認が出ることを調べず、ユーザーから指摘を受けたあとも、承認が出る操作をユーザーに尋ねてから、ようやく公式文書を調べた。調べると、種別(Dashboard)の手順書に、`db_write` の引数をユーザーが承認できる大きさに保つ、と書かれていた。この記述と、ユーザーが承認の確認を受けた事実から、承認はプラットフォーム側の設計で、書き込みのたびに出ると判断した。手順書の全文は読み切っておらず、承認が出ない書き込みの経路があるかは確かめていない。

原因は、前の節で足した規則の範囲が狭かったことである。規則は、迂回策や現状維持を勧めるときにだけ、証拠を求めていた。道具を入れ替えるとき、使い始めるときの確認と、ユーザーに見える副作用を調べる手順は、規則に無かった。さらに、ボードの目的(ユーザーが何もせずに状況を見られる)と、ユーザーの承認が毎回要る書き込みが、両立しないことを、設計の段階で確かめていなかった。ボードは、種別が勧める live クエリではなく、ファイルをアップロードして URL を書き換える形で作られていた。この形は、更新のたびに書き込みが要る。

対処は、2つである。復旧は、ボードへの書き込みを止め、巡回の予約の文面にも保留を書き、更新の方式をユーザーに諮ったことである(実施済み)。ユーザーは、GitHub Projects のボードとラベルで進める案を選んだ。ラベルの付け外しは確かめた。Projects の作成と自動追加は、ユーザーの作業と確認が残っている。原因への対策は、AGENTS.md の同じ項に、道具を入れ替えるときと使い始めるときに、副作用を使う前に調べる規則と、承認の確認が出る操作を定期的な手順に組み込まない規則を足したことである。同じ形が、規則を足した日に続いたので、前の節の対策は不十分だったとみなした。

## ユーザーの対応待ちの間、変化が無いと何も出ず、何をすればよいかが分からなくなった(段階5)

[suchi/sucheme-zig#212](https://github.com/suchi/sucheme-zig/pull/212) などのマージを待つ間、親は、変化が無い巡回では何も報告しなかった。これは AGENTS.md の規則(変化が無い回は報告しない)どおりだった。しかし、ユーザーが時間を空けて画面に戻ったとき、残っている項目と、それぞれの場所とおすすめが、直前の報告にしか無く、何をすればよいかが分からなくなった。

原因は、報告の規則が、変化の有無だけで出す・出さないを決め、ユーザーの対応待ちが残っているかを見ていなかったことである。「最初の1回だけ報告する」という規則は、ユーザーが最初の報告を見逃す、または戻るまでに間が空く場合を考えていなかった。

対処は、2026-10-31 に、AGENTS.md の「周期」の項に例外を足したことである(ユーザーが承認した)。ユーザーが動く項目が残っている間は、変化が無くても、1時間ごとの保険のルーチンが発火するたびに1回、先頭の固定の1行に続けて、項目ごとの場所とおすすめを書いた一覧を出す。変化が無い巡回の予約からは出さない。1時間ごとの定期ルーチンの文面にも、同じ内容を入れた。

## 層1 で通ったテストの入力が、層2 の Windows の表明に当たった(段階5)

スライス 5m(suchi/sucheme-zig#232)で、ミューテーション査読への対応として足したテストが、層1(Linux)では通り、層2 の Windows のジョブでだけ落ちた。テストは、標準ライブラリの `Environ.Map.put` に、UTF-8 として妥当でない 1 バイトの名前を渡して、環境変数の表を作っていた。Windows の分岐は、名前が WTF-8 として妥当であることを表明で求める。Linux の分岐は、NUL と `=` しか見ない。標準ライブラリのソースでの確認は、この記録の時点で行っていない(担当からの報告による)。テストの名前を、WTF-8 として妥当な別の不正な UTF-8 の列に直し、層2 を走らせ直して緑にした。

原因は、Windows のテストが層2 でしか走らないこと([ADR-0036](../adr/0036-windows-tests-in-the-slow-tier.md))と、標準ライブラリの API に入力を渡すときに、その API の前提(doc コメントの Asserts)をプラットフォームの分岐ごとに確かめる手順が無かったことである。前節の絶対パスの件と同じく、プラットフォームで前提の違う入力を、Linux の前提で作った。

対処は、テストの入力を標準ライブラリの API に渡して作るときは、その API の Asserts の条件を、Windows の分岐も含めて確かめることである。環境変数の名前、パス、引数のように、プラットフォームで前提が違う入力は、全プラットフォームで受け付けられる形で作る。仕組みとしての検査は足さず、規則を書くだけにした(担当の案のうち、費用の小さい案を、親が勧める案として採った。ユーザーへ事後に報告する)。

## 背景のサブエージェントが、実行中のコマンドの応答が無いまま止まった(段階5)

2026-11-01 に、スライス 5m の挙動査読のサブエージェント 2 本が、実行中の Bash の応答が無いまま 40 分以上止まった。止まる直前の実行に `rm -f` が入っていた。`.claude/settings.json` の `ask` に `Bash(rm:*)` があり、背景のサブエージェントには承認する人がいないので、承認待ちで止まった、という仮説を立てた。確かめていない。同じ査読のミューテーション担当は、`ask` に入っている `git checkout --` を使って完了しており、この仮説の反例になりうる。

`rm`、`rmdir`、`git checkout`、`git restore`、`git reset`、`git clean`、`mv` を使わないと依頼文に書いた 3 本目は、4 分余りで完了した。この結果は仮説と合うが、1 件の観察であり、因果を示すものではない。

対処は、サブエージェントへの依頼文に、承認待ちになりうる操作を使わない条件を書くことである。作業ディレクトリは、毎回 `mktemp -d` で新しく作り、消す操作を要らなくする。ミューテーションは、退避したファイルを `cp` で書き戻す。仮説の確認は、承認待ちで止まったサブエージェントの記録を見られたときに行う。

## 親の報告に、不自然な日本語と、件数の食い違いがあった(段階5)
