# ADR-0048: 利用者向けの文書のコードを全コミットで走らせ、出力を変える PR が例を直す

- ステータス: 採用
- 日付: 2026-10-29

## 背景

利用者向けの文書(チュートリアル、ユーザーズガイド、リファレンス、プログラム集)を `docs/manual/` に置くことになった([計画書 0027](../plans/0027-user-documentation.md))。条件は、文書に載せる Scheme のコードがすべて動き、それを機械で確かめられることである。

文書のコードは、インタプリタの変更で黙って古くなる。いまの REPL は `(scheme base)` だけを見るので `display` には `(import (scheme write))` が要り、`write` は段階5の 5j まで無い。後のスライスが、数の書式や誤りのメッセージを変えれば、正しかった例が誤りになる。人が読んで確かめる形では、どちらも見つからない。

計画書 0027 の合意を求める点の1、2、6、9 は、2026-10-29 に、勧める案のとおりに決まった。

## 決定

1. 期待する出力の記法: `scheme` の情報文字列のコードブロックの直後(空行だけを挟んでよい)に、`output` のブロックで期待する出力を書く。出力の形は REPL と同じで、`tests/scheme/` の期待する出力の書き方(値は1行ずつ、書いた出力は書いた順、誤りは `error: ` とメッセージ)に合わせる。`output` の無い `scheme` のブロックは、出力が空であることを求める。同じファイルのブロックは1つのインタプリタで順に走り、`scheme fresh` は新しいインタプリタで走る。走らせない断片は `text` で書く。種類の分からないフェンス、字下げしたフェンス、インデントされたコードブロックになりうる行は、検査が断る。
2. 検査の層: `zig build check-examples` を、全コミットの検証コマンドとして、層1(`ci.yml`)で走らせる。照合の規則により、`full.yml` の `windows` ジョブにも同じ step を置く。
3. 他のレーンとの取り決め: インタプリタの出力を変える PR は、同じ PR の中で `docs/manual/` の期待する出力を直す。所有の外への書き込みだが、期待する出力の置き換えに限って、事前に認める。説明の文の書き換えが要るときは、レーン L9 に知らせ、L9 が直す。

検討した別案と、採らなかった理由:

- REPL の書き写しの形(`> (+ 1 2)` の次の行に `3`)を1つのブロックに書く案。コピーしたコードにプロンプトが混じり、継続行の扱いを検査に足すことになる。
- コードの中のコメント(`; => 3`)で書く案。`display` の出力と値を区別できず、誤りの例が書きにくい。
- 層2だけで走らせる案。文書だけの PR では層2が走らない([ADR-0046](0046-skip-slow-tier-for-docs-only-prs.md))ので、文書の例の誤りが main に入る。
- 出力を変える PR の前に、L9 が文書を直す PR を先にマージする案。差分は分かれるが、順序の調整で待ちが増える。

## 結果

- メリット: 文書の例が、インタプリタのどの変更でも、その PR の中で確かめられる。文書だけの PR でも検査が走る。検査を外れるブロックを、検査そのものが断る。
- デメリット・受け入れたトレードオフ: 層1の時間が延びる。出力を変える他のレーンの PR が、文書の期待する出力を直す手間を負い、その PR の差分に文書が混じる。文書はリストの中にフェンスを書けず、字下げした行も書けない。
- 将来の見直し条件: 層1の時間が目標(1分以内)を大きく超えたとき。文書の量が増え、他のレーンの PR が文書の直しで滞るようになったとき。CommonMark のリストの中のフェンスを書く必要が出たとき。
