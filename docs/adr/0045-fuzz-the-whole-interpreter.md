# ADR-0045: ファジングの対象に、インタプリタ全体を通す対象を足し、別のテストのバイナリに置く

- ステータス: 採用
- 日付: 2026-10-23

> 2026-10-23 追記: スライス 6i-4 で、1回の実行の中で、初期化のあとの確保を1回だけ失敗させる形を足した。失敗させるかと、何回目を失敗させるかは、ファザーが選ぶ。失敗させた実行に限り、`evalPrint` が `OutOfMemory` を返すことを許し、そのあとも定数を評価できることと、漏れが無いことを見る。インタプリタを1回の実行ごとに作り直す決定と、見る性質のうちほかのものは変えていない。経緯は [計画書 0025](../plans/0025-fuzzing-the-evaluator.md) の「残っていること」にある。

## 背景

[ADR-0013](0013-testing-strategy-and-conformance-suite.md) は、ファジングの対象をリーダとしている。展開器、コアIRへの変換、機械、プリミティブ、Scheme で書いた標準の定義は、ファジングの対象に入っていなかった。

対象にできなかった理由は2つあった。止まらない入力(`(let loop () (loop))`)で1回の実行が終わらないことと、確保が際限なく増える入力があることである。`--fuzz` の探索中は `--test-timeout` が効かない。ヒープの上限と、機械の歩数の上限([ADR-0044](0044-machine-step-limit-not-catchable.md))で、どちらも形式ごとに誤りとして打ち切れるようになった。

計画書 [0025](../plans/0025-fuzzing-the-evaluator.md) の合意を求める点で、対象の初期化、置き場所、初期入力、`fuzz.yml` の扱いを決めた(2026-10-23 に決定)。この ADR は、そのうちテストの方針にあたる部分を記録する。

## 決定

インタプリタ全体を通すファジングの対象を、リーダの対象に加えて置く。

- 1回の実行は、`(scheme base)` つきのインタプリタを作り、入力を `evalPrint` で評価し、定数を評価して、片付ける。インタプリタは実行のたびに作り直す。ファイルは読まない。
- 形式ごとの歩数の上限、小さいヒープの上限、大きさの決まった書き出し先を付ける。
- 見るのは、パニックと安全検査の失敗が起きないこと、確保が漏れないこと、`evalPrint` が `OutOfMemory` を返さないこと、誤りのあとも定数を評価できることである。
- 置き場所は `tools/fuzz-eval/fuzz.zig` で、リーダの対象とは別のテストのバイナリにする。1つのバイナリに `std.testing.fuzz` を呼ぶテストを2つ置くと、探索の実行でファザーが進まなくなるからである。`zig build test --fuzz=<N>` は、ファジングのテストを持つバイナリごとにファザーを1つずつ並べて走らせ、それぞれに同じ上限 N を渡す。
- 初期入力は、構文ごとに自分で書いた短い入力にする。取り込んだ準拠スイートの文面は埋め込まない。

選ばなかった案は次のとおりである。

- 標準環境の無いインタプリタ(`initBare`)を作り直す案: 初期化は速いが、Scheme で書いた標準の定義を試さない。
- 1つのインタプリタを実行をまたいで使い回す案: 速いが、前の入力の定義が残るので、ファザーが保存する入力1つでは誤りを再現できない。
- `src/sucheme.zig` にテストとして置く案: 別のレーンが持つファイルを触ることになる。
- 準拠スイートを初期入力に埋め込む案: 1つの形式が入力の上限を超えるものがあり、BSD 3条項の文面をテストのバイナリに埋め込む扱いを決め直す必要がある([ADR-0041](0041-bsd-name-clause-attribution-not-endorsement.md))。

## 結果

- メリット: 評価器、展開器、プリミティブ、標準の定義に、書いた人が思いつかない入力が届く。見つかった入力は `.zig-cache/f/crash` に保存され、`fuzz.yml` の既存の検査が拾う。
- デメリット・受け入れたトレードオフ:
  - 1回の実行ごとに標準環境を読み込むので、リーダの対象より1回が遅く、同じ時間で試せる入力が少ない。`fuzz.yml` の時間の上限に収めるため、`--fuzz` の上限を 500K から 20K に下げた(2026-10-23)。上限は対象ごとに同じ値なので、リーダの対象の回数も同じだけ減る。
  - 書き出し先の大きさで止めるので、循環するデータの印字が正しく止まるかは、この対象では見ない。
  - マクロの展開のうち、入れ子を深くせずに増え続ける形が止まるかは確かめていない。止まらなければ、探索の実行がその入力で止まり、`fuzz.yml` のジョブの時間の上限が止める。
- 将来の見直し条件: ポートや `exit` のように、プロセスの外へ出る手続きが標準環境に入ったとき。その手続きを、この対象から外すか、害の無い形に差し替える必要がある。1回の実行が遅すぎて、`fuzz.yml` の時間の上限に収まらなくなったとき。
