# ADR-0017: レビューは自前の敵対的レビューを主とする

- ステータス: 採用
- 日付: 2026-10-04

## 背景

PR #1 では GitHub Copilot のコードレビューを8巡依頼した。瑣末な指摘はほとんどなく、ほぼすべてが実装時に顕在化する具体的な欠陥だった。1件だけ指摘自体が仕様の誤読だった。レビューの価値は高かった。受領件数と妥当だった件数の内訳は [docs/review/adversarial-review-baseline.md](../review/adversarial-review-baseline.md) にある。件数を本ADRに書かないのは、真実の源を重複させないためである。

一方、1日で Copilot Pro の利用上限の90%に達した。設計フェーズの1つの PR でこれだけ消費するため、段階0から段階8までを同じやり方で進めることはできない。

依存の集中という問題もある。レビューの質が外部サービスの可用性と課金体系に左右されると、プロジェクトの進行がそれに縛られる。

受け取った指摘は、優れたレビューの実例データとして手元にある。これを「どういう検出器があればこれらの指摘が出るか」に逆算して、既知の類型を取りこぼさない下限を作れる。

ただし下限だけに頼ると、レビューの範囲が外部サービスが示した類型に固定されてしまう。土台はレビュー担当者自身の判断とし、カタログはその上に重ねる網として扱う。

## 決定

レビューは自前の敵対的レビューを主とする。手順と検出器は [.agents/skills/adversarial-review/SKILL.md](../../.agents/skills/adversarial-review/SKILL.md) に定め、実例との対応表は [docs/review/adversarial-review-baseline.md](../review/adversarial-review-baseline.md) に置く。

実行にあたって次を守る。

- レビューは、成果物を書いた文脈を持たないサブエージェントに実行させる。与えるのは成果物、一次情報の在処、スキルだけとする。設計の意図や経緯を渡さない。外部サービスが欠陥を見つけられたのは意図を知らない立場だったからであり、自分の文章を自分で読むと意図を補って欠陥が見えなくなる。
- 指摘には具体的な失敗シナリオを必須とする。仕様に関わる指摘は一次情報の原文を引用する。言語や処理系の前提に関わる指摘は固定したバージョンの実機で確認する。
- 検出器カタログは下限として全件適用し、そのうえでカタログ外の探索を必ず行う。カタログを消化して終わりにしない。カタログ外で見つけた類型は検出器に追加する。
- 新規指摘ゼロのルールは緩めない。収束は検出器の調整で行い、基準を下げて収束させない。収束しない場合の手段は [ADR-0018](0018-incremental-vertical-slices.md) が2つ加えている。いずれも基準を下げるものではなく、主張の置き場所と決定の時期を変えるものである。

外部レビューは不要とする。自前の敵対的レビューのみで進める。

この判断はユーザーが行った。自前レビューが外部サービスの指摘を完全に再現できていない時点でも、残る差は後続の設計・実装・テストの各段階で捕まえられる、という判断である。レビューの水準を上げるために収束を無限に延ばすより、現在の水準で前に進む方が得られるものが大きい。

したがって「レビュー完了」の条件は、自前の敵対的レビューで新規指摘ゼロになったことを指す。外部レビューの可否をマージの条件に含めない。`AGENTS.md` の PR 手順もこれに合わせてある。

## 検証の状況

外部サービスの8巡目を比較試験に使った。外部の指摘を読む前に自前レビューを独立に実行し、後から突き合わせた。結果は基準表にある。量と深さでは上回り、再現率では2件を取りこぼした。

取りこぼした2件は、設計が「すべて」や「1箇所に閉じる」と主張している対象集合をレビュー側が数え上げていなかったことによる。この形を一般化して検出器に組み込んだ。強化後のレビューは、自分が直前に書いた修正文の中から、捏造した仕様の引用、仕様の形式の数え違い4件、機構の欠落を含む多数の欠陥を検出した。

完全な同等は実証されていない。それを承知のうえで、残る差を後続の段階で捕まえる前提で本決定を採った。

## 結果

- メリット: レビューの質が外部サービスの可用性と課金に左右されなくなる。検出器が文書として残るため、別のセッションや別の環境でも同じ水準のレビューができる。新しい種類の欠陥を見つけたら検出器を追加して水準を上げられる。一次情報の照合と実機確認を手順に組み込めるため、外部サービスより深い検証ができる。
- デメリット・受け入れたトレードオフ: 自分の成果物を自分でレビューするため、サブエージェントによる文脈の分離という間接的な対策に頼ることになる。完全に独立した視点ではない。レビュー1回あたりのトークン消費が大きい(比較試験では約35万トークン)。カタログを下限として扱う構成にしても、カタログがある分だけそこに注意が偏る危険は残る。
- 将来の見直し条件: 自前レビューが見落とした欠陥が実装段階で見つかった場合、その欠陥を基準表に追加して検出器を強化する。強化しても同種の見落としが続く場合、外部レビューの併用を再開するか、レビューの構成(複数のサブエージェントによる分担など)を見直す。
