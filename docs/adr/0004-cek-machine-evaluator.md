# ADR-0004: 評価器は明示的な継続を持つCEK機械とする

- ステータス: 採用
- 日付: 2026-10-04

## 背景

R7RS は次の2つを必須としている。

- 適切な末尾再帰(3.5)。末尾位置の呼び出しはスタックを消費してはならない。
- 完全な `call-with-current-continuation`(6.10)。捕捉した継続は多重起動でき、再入できる。

加えて、WebAssembly では保守的スタック走査ができないため精密GCが必須である([ADR-0003](0003-precise-mark-sweep-gc.md))。Zig の再帰で Scheme 式を評価すると、Zig のスタックフレームに `Value` が隠れてしまい精密GCが書けない。

選択肢は次の3つだった。

- 再帰的なツリーウォーカー: 最短で動く。しかし完全な継続が実装できず(脱出限定になる)、精密GCも書けない。段階2で作り直しになる。
- 明示的な継続を持つCEK機械: 継続をヒープ上のフレーム列として表す。上記3つの要件が自然に満たされる。
- バイトコードVM: 最も高速。完全な継続にはスタックのヒープ化かセグメントコピーが必要で複雑度が上がる。最初に動くREPLまでが遠い。

## 決定

最初からCEK機械を採用する。状態は制御(コアIRの節点)、環境、継続、直前の値の4レジスタと、動的状態のリストに集約する。

継続フレームは不変とする。引数の蓄積も可変配列ではなく不変の逆順リストで行う。引数評価中に捕捉した継続を2回起動した場合、可変配列を共有していると2回目が1回目の書き込みを観測してしまうためである。

末尾位置の判定は展開器が行い、コアIRの呼び出し節点に印を付ける。機械はその印を信用する。判定の責任を1箇所にまとめる。

Scheme 式の評価を進めるのは機械のステップ関数のみとする。プリミティブ手続きから Scheme 手続きを呼ぶ必要がある場合は、プリミティブの中で機械を起動してはならない。機械にレジスタを書き換えさせて次のステップに進ませる。

R7RS 3.5 が末尾呼び出しを必須とする4箇所(`apply` の第1引数、`call-with-current-continuation` の第1引数、`call-with-values` の第2引数、`eval` の第1引数の評価)は、継続フレームを積まずにプリミティブ自身の継続を引き継ぐ。これらに一律でフレームを積むと、`(apply loop (list (- n 1)))` のような能動的な末尾呼び出しでフレームが積み上がり、仕様が要求する一定のメモリでの実行を満たせない。

## 結果

- メリット: 末尾再帰、完全な継続、精密GCの3つが同じ構造から導かれる。GCルートが少数のレジスタに限定される。Scheme の深い再帰でZigのスタックが溢れない。ブラウザでの歩数制限による中断と再開が可能になり、`read` による対話も実現できる。段階2での作り直しが発生しない。
- デメリット・受け入れたトレードオフ: 素朴なツリーウォーカーより初期の記述量が多い(段階1で300行規模)。フレームが不変なため確保回数が増え、素朴な実装より遅い。実行状態の追跡に慣れが必要。
- 適用範囲の限定: Zig のスタックが溢れないのは Scheme 式の評価についてだけである。GC のマーク、リーダ、プリンタ、`equal?` など、データの構造を辿る処理は別に明示的な作業スタックを持たせる必要がある。これらを Zig の再帰で書くと、長いリストや深い入れ子でスタックが溢れる。詳細は [runtime.md](../design/runtime.md) にある。
- 将来の見直し条件: 準拠テストが通った後に性能を測定する。確保回数が支配的なら、捕捉時にコピーするスタックセグメント方式、またはコアIRのバイトコード化を検討する。いずれも機械の外部仕様を変えないため、ADRの置き換えではなく追加の最適化として扱う。
