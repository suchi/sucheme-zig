# ADR-0026: 機械検査の対象をコードと生成物についての事実に限る

- ステータス: 採用
- 日付: 2026-10-08
- 置き換え: [ADR-0024: closed-spelling-sets](0024-closed-spelling-sets.md) を非推奨とし、本ADRが最新の決定となる

## 背景

[ADR-0024](0024-closed-spelling-sets.md) は、検証ツールが外部の記法を読むとき受理する綴りの集合を閉じ、集合の外を報告すると決めた。綴りを1つずつ潰すやり方に終わりがないことへの対処だった。

その決定のもとで3巡を回した結果が出た。14巡目から16巡目の必須指摘はほぼ全件が「`tools/check-docs` が Markdown と YAML をどう読むか」であって、インタプリタの設計についての指摘は1件も出ていない。必須の件数も下がらなかった。各巡の必須の過半が、直前の巡で書いた修正そのものの欠陥だった。巡ごとの件数は [review/stage0-findings.md](../review/stage0-findings.md) の表が正で、ここに複製しない。

規模が逆転していた。段階0の成果物は足場と設計文書であり、製品コードよりも、それを検査するツールのほうが1桁大きく育っていた。行数をここに書かないのは、書いた時点の作業ツリーの値を残すと、どのコミットとも一致しない数が記録として残るからである。実際に一度そうなった。

原因は [AGENTS.md](../../AGENTS.md) に積み上げたルールの適用先だった。「巡をまたいで再発した類型は、散文の注意書きではなく検査として足す」は、コードの振る舞いに適用すれば有限である。振る舞いの種類は有限で、検査を足すたびに残りが減る。文書の書き方に適用すると終わらない。同じ意味を読者に伝える Markdown の綴りは有限集合ではなく、1つ閉じるたびに次が現れる。ADR-0024 自身が「反例が尽きたとは言えない」と認めていた。

本プロジェクトの大方針は、小さいところから漸進的に育てることである([ADR-0018](0018-incremental-vertical-slices.md))。文書の綴りを追いかける検査を育て続けることは、その方針と正面から矛盾する。

## 決定

機械検査の対象を、コードと生成物についての事実に限る。文書の書き方は検査しない。

### 検査する3つの事実

1. 検証が黙って止まらないこと。`build.zig` が宣言する step から作った一覧、`AGENTS.md` の検証コマンド表、`ci.yml` の段の3つが互いに一致すること。テストが実際に到達して走ること。使ってよいワークフローのキーと、ジョブが走るかを決める値が閉じた集合であること。毎コミットで走るワークフローに Zig を入れる段があること。
2. 生成物が入力とずれていないこと。`zig build check-extract` が抽出プログラムを走らせて生成物と比べること。ベンダリングした入力と生成物のハッシュ、生成物の件数、生成物のディレクトリに余計なファイルが無いこと。
3. 固定した版が一致していること。`.zigversion` と `build.zig.zon` とワークフローのリテラル。

これに相対リンクの到達性を加える。リンク切れはファイルの実在についての事実である。ただし**リンクがどこにあるかを見つける作業は Markdown の解析であり、そこは綴りの無限集合である**。16巡目に撤回した「記録の綴り」と同じ構造が、20巡目にリンク検査で再発した(行内リンクの括弧を2行に割る、引用マーカーの後の空白を省く、字下げしたフェンスを対で置く)。

そこで線を引く。読めない形は報告する。参照形式の定義も、引用や箇条書きの中のものも読む。1行で閉じない行内リンクは「読めない形」として報告する。閉じ忘れたフェンスは以降のリンクを検査から外すので報告する。字下げは CommonMark どおり、箇条書きの本文の桁から4桁以上はコードブロックとして扱う。**ここまでで止める。** これ以降に見つかる「描画されるのに検査されないリンクの綴り」は、必須ではなく段階1の作業項目として記録する。綴りを追いかけ続けることが、この ADR が終わらせた作業そのものだからである。

表を読む検査は、HTML コメントとフェンスを空白化した結果から読む。読者に見えない行は記録ではないという規則は ADR-0024 から引き継いだ。引き継いだのは次の3つである。ワークフローの使ってよいキーを閉じた集合にすること。HTML コメントの開始マーカーは行の途中にあっても開始として読み、コードスパンの中かは判定せず、閉じていないマーカーは報告すること。表の行は列0のものだけを読むこと。ADR-0024 の非推奨理由はこの3つを引き継ぎ先として挙げており、その正はこの節である。

### 検査しないもの

記録の綴りの正規化、字下げされた記録の報告、表のセル数、ADR のステータスと一覧の照合、`- 置き換え:` の双方向、非推奨理由と追記ブロックの形、入口が指す ADR、合計と内訳の算術、見出しの重複、引用の lazy continuation。フェンスの閉じ忘れは当初この一覧にあったが、以降のリンクを検査から外すので報告する側に戻した。ADR の一覧については、一覧の行とファイルが双方向に実在することだけを見る。これはリンクの到達性と同じ種類の事実である。

落とした検査が守っていた性質は、守られなくなる。ADR の一覧が古いステータスを表示することは起こりうる。それは読めば分かる誤りであり、読まずに通る誤りではない。機械に読ませるために必要だった3,000行の特殊ケースの方が、その誤りより高くついた。

### 綴りを追いかける代わりにすること

穴を綴りで閉じるのではなく、不変条件を双方向にして閉じる。`AGENTS.md` の表の行を隠す攻撃は、表から CI への一方向の照合では綴りの防御が必要になるが、CI から表への照合を足すと、隠された行は「CI が表にないコマンドを走らせている」として赤になる。綴りを1つも知らなくても閉じる。

双方向だけでは足りない。表と `ci.yml` は互いにしか照合していないので、行と段を対で落とすと要求ごと消え、4つのコマンドのうち3つまで緑のまま削れた。対の外に点が要る。`build.zig` が宣言する step から一覧を作って渡すのがそれで、要求を消すには step を消すことになり、その瞬間にコマンド自体が動かなくなる。記録ではなくコードが錨になっている。

残る限界を記録する。`zig fmt --check .` は step ではないので、表と `ci.yml` だけが支える。`--requires` の一覧そのものを `build.zig` から削ることもでき、そのときは step が残ったまま要求が消える。3箇所(表の行・`ci.yml` の段・`build.zig` の一覧)を揃えれば任意のコマンドを落とせ、揃えきれば CI が走らせるものを `zig fmt --check .` だけにできる。錨は「同時に直さなければならない箇所の数」を2から3に増やし、うち1つをコードに置くものであって、編集を不可能にするものではない。

そのうえで、検査の step が自分の run step を実行し、その実行の結果が step の成否を決めることを configure 段で確かめる。`check_docs_step.dependOn(&run_check_docs.step)` の1行を消すだけで step が空になり、`zig build check-docs` が `all checks passed` も出さずに exit 0 で終わった。実行されることを確かめるだけでも足りない。`run.stdio = .{ .check = .empty }` は依存も producer もそのままに終了コードを読まなくするので、診断を出しながら成功する。Zig の `StdIo` のうち終了コードを無視できるのは `.check` だけなので、それと `skip_foreign_checks` を拒否する。

この守りの限界は、錨の数ではなく種類である。configure 段の守りは `build()` の実行中に状態を読むので、その後に同じ状態を書き換えれば通る。実際に、19巡目が拒否したのと同じ `run.stdio = .{ .check = .empty }` を守りの呼び出しより1行下に置くと緑になり、`check_docs_step.dependencies.clearRetainingCapacity()` を同じ位置に置くと出力すら出ずに緑になった。Zig 0.17 には make 段にコードを差し込む経路が無い(`makeFn` は無く、グラフは Configuration に直列化される)ので、この順序の問題を `build.zig` の中では解けない。

したがって次を決定の一部として記録する。**`build.zig` の中の守りは、`build.zig` を編集する相手には勝てない。** 守りが閉じるのは、1箇所の編集で検証が黙って止まる形だけである。`build.zig` そのものへの変更に対する防壁は、差分のレビューであって機械検査ではない。この類型の指摘は以後必須として扱わない。安く閉じられる綻り(出力の捕獲、`skip_foreign_checks`、同じ artifact の2本目以降の run、`check-extract` の引数の数)は閉じてあるが、網羅は主張しない。

同じ理由で、抽出プログラムの `check_only` の既定値や、比較 run が依存する書き込み run も `build.zig` と抽出プログラムの編集で作れる。「引数を足す側が唯一の経路」と書いたのは誤りだった。

同じ形が使えるかを先に考える。使えないなら、その検査は落とす候補である。

### ルールの書き換え

AGENTS.md のルールを次に変える。再発した類型のうち、コードまたは生成物についてのものを検査に足す。文書の書き方についてのものは足さない。文書の誤りは、読んで直す。

## 結果

- メリット: 検査の総量が減り、各巡の指摘が検査器自身の欠陥ではなく成果物に向く。段階1以降、レビューの対象が製品コードになる。一個流しに戻る。
- デメリット・受け入れたトレードオフ: 文書間の不一致が機械では見つからなくなる。ADR の一覧のステータス、置き換えの双方向、追記の位置は人が読んで保つ。過去の巡で段階1へ回していた推奨のうち、落とす検査に属するものは作業項目ごと消える。
- 将来の見直し条件: 落とした検査が守っていた種類の誤りが実際にマージされ、読んでも気づかれなかった場合、その1つについてだけ検査を足すことを検討する。「文書の書き方を一般に検査する」側に戻す場合は本ADRを非推奨にして新ADRを書く。
