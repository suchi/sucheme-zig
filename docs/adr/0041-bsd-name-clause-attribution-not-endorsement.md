# ADR-0041: 取り込んだ準拠スイートの著者名は出典としてだけ使い、推奨や認定と読める形では使わない

- ステータス: 採用
- 日付: 2026-10-20

## 背景

段階6で、chibi-scheme の準拠スイート `r7rs-tests.scm` を `tests/vendor/` に取り込む([ADR-0013](0013-testing-strategy-and-conformance-suite.md))。許諾は、chibi-scheme のリポジトリの根の `COPYING` で、BSD 3条項の形である。

[ADR-0022](0022-unlicensed-proprietary.md) は、2つのことを段階6に送った。

- 取り込む版の許諾文そのものを読んで、条文を確かめること。名前の利用の制限が誰の名前に及ぶかは、変種によって違う。
- 出典として事実を述べることと、推奨や宣伝として用いることの線を、段階6で引くこと。ADR-0013 の本文は運用ルールにより書き換えられないので、新しい ADR に書く。

あわせて、roadmap の段階6は、記録の形式が2つ併存すること(仕様から抜き出した入力の記録と、第三者のコードの取り込みの記録)を、同じ ADR で定めるよう求めている。

取り込んだ版(コミット `b2087f3a320a56f79ede5c546fd45fdde582c4ed`)の `COPYING` を読んで、次を確かめた(2026-10-20)。

- 著作権表示は「Copyright (c) 2009-2021 Alex Shinn」である。
- 第3条項は「The name of the author may not be used to endorse or promote products derived from this software without specific prior written permission.」である。対象は著者(the author)の名前で、寄稿者とソフトウェアの名前は挙げていない。
- 第1条項は、ソースコードを再配布するときに、著作権表示、条項、免責の文を残すことを求める。第2条項は、バイナリを再配布するときに、同じものを配布物の文書や資料に載せることを求める。

この線は、計画書 0020 の「合意を求める点」の2として、選択肢つきで検討し、勧める案に決めた(2026-10-20)。

## 決定

### 対象

この ADR が扱うのは、`tests/vendor/` に取り込んだ版の `COPYING` の第3条項である。名前の利用の制限が及ぶのは、著者の名前である。条文は著者を名指ししていないが、同じ許諾文の著作権表示が挙げる唯一の人(Alex Shinn)を、著者と読む。取り込む版を更新して `COPYING` の文面が変わったときは、この ADR の前提を確かめ直す。

### 書いてよいもの(出典として述べること)

次は、名前の利用の制限の外とする。製品を推奨も宣伝もせず、事実を記録するだけだからである。

- `tests/vendor/` に同梱した許諾文と、`tests/vendor/README.md` の取得元と著作権表示。
- 設計文書と ADR の中で、スイートの出典と維持している人を、事実として述べること。[ADR-0013](0013-testing-strategy-and-conformance-suite.md) と [r7rs-coverage.md](../design/r7rs-coverage.md) にある既存の記述は、これに当たる。
- 準拠マトリクスの見出しや表に、スイートのファイル名(`r7rs-tests.scm`)と上流のリポジトリの名前(chibi-scheme)を書くこと。
- 「`r7rs-tests.scm`(コミット `b2087f3`)の、この節のテストに合格した」のように、取り込んだコミットを添えた、合格の事実の記述(下の「書かないもの」の後の段落)。

### 書かないもの(推奨・宣伝・認定と読める形)

次は、著者の書面の許可なしには行わない。

- 著者が、この処理系を認めた、推薦した、検証した、と読める文。
- リリースノート、README の紹介文、Web UI の表示のように、利用者に処理系を紹介する場所に、著者の名前を出すこと。
- 合格の事実を、「認定された」「準拠と認められた」のように、第三者の認定と読める語で書くこと。

合格の事実を述べるときは、スイートのファイル名と、取り込んだコミットを添える。どの版のどのテストに合格したかを書けば、第三者の判断を借りずに事実だけを述べられる。

### 記録の形式は2つ併存する

テストと検証の入力として取り込んだものの記録は、許諾の種類に合わせて2つの形を併存させる。一方に寄せない。

| 記録 | 対象 | 依る許諾 |
| --- | --- | --- |
| [tools/extract-r7rs-required/SOURCE.md](../../tools/extract-r7rs-required/SOURCE.md) | R7RS の仕様から取得し、抜き出した入力(付録A の HTML) | R7RS 自身の、全文または一部の複製の許諾 |
| `tests/vendor/README.md` | `tests/vendor/` に取り込んだ第三者のテストスイート | 同梱した許諾文(BSD 3条項の形) |

配布する成果物に入る第三者のコードの表示(`THIRD-PARTY-NOTICES.txt`)は、[ADR-0034](0034-release-shape.md) が扱い、この ADR の対象外である。

前者は仕様の文の複製で、仕様自身の許諾に依る。後者は、再配布の条件と名前の利用の制限を持つ。依る許諾が違うので、記録する項目も違う(後者には、同梱した許諾文と、根の `LICENSE` が覆わないことの明記が要る。[ADR-0022](0022-unlicensed-proprietary.md))。

### 検討した選択肢

- 著者の名前を `tests/vendor/` の中にだけ置き、リポジトリのほかの場所には一切書かない: 判定が機械的で誤る余地が小さい。しかし、[ADR-0013](0013-testing-strategy-and-conformance-suite.md) の本文の既存の出典の記述と食い違い、その本文は書き換えられない。採らなかった。
- 著者に書面の許可を求める: 曖昧さは消える。しかし外部への連絡と返事の待ちが要り、出典と事実の記述には、もともと許可が要らないと読めるので、得るものが小さい。採らなかった。

## 結果

- メリット: 出典の表示と、合格の事実の記述ができる。何を書いてよいかが、文の種類(出典か、推奨・宣伝・認定か)で決まり、各レーンの書き手が迷わない。2つの記録の形が、なぜ違うのかが残る。
- デメリット・受け入れたトレードオフ: 「推奨や認定と読める」の判定には、読む人の判断が残る。機械では検査しない([ADR-0026](0026-verify-facts-about-code-not-prose.md) の線引きにより、文書の書き方は検査に足さない)。
- 将来の見直し条件: 取り込む版の `COPYING` の文面が変わったとき。リポジトリを公開に転じるとき([ADR-0022](0022-unlicensed-proprietary.md) の見直し条件と同時に見直す)。著者の名前を紹介文などで使いたくなったときは、許可を求める判断をやり直す。
