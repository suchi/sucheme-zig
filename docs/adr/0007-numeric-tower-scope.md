# ADR-0007: 完全な数値塔を実装する

- ステータス: 採用
- 日付: 2026-10-04

> 2026-10-20 追記: 多倍長整数に `std.math.big.int` を使う決定は変えない。ヒープに置く形を具体化した。bignum のオブジェクトは `Managed` を持たず、作ったあとに変えない限界値列(`limbs` と符号)をペイロードとして持つ。演算の途中だけ `Managed` を、上限に計上する作業領域で使い、結果の限界値列を写す。「結果」の節の「GC の sweep で解放する仕組み」は、文字列のバイト列と同じペイロードの解放(`src/heap.zig` の `Heap.free`)で満たす。理由は、`Managed` が割り当て器を持つので走査の分類(`src/trace.zig`)を通らないことと、演算のたびに伸びて上限の照合を受けないことである。判断の記録は、段階4の計画書 0018(`docs/plans/0018-phase4-numeric-tower-unicode.md`)の合意を求める点の5にある(2026-10-20 に合意)。

## 背景

R7RS は数値塔の一部を省略することを許しており(6.2.3)、処理系は `cond-expand` のフィーチャで対応範囲を表明する。しかし本プロジェクトの要件は「R7RS 準拠」であり、`(scheme complex)` は付録Aの標準ライブラリに含まれている。

実装量の観点では、多倍長整数、有理数、複素数のそれぞれが相当の作業になる。特に多倍長整数の演算と基数変換は誤りが入りやすい。

## 決定

完全な数値塔を実装する。fixnum、bignum、ratnum、flonum、compnum の5種を持ち、`exact-closed` `ratios` `exact-complex` `ieee-float` のフィーチャをすべて真にすることを目標とする。

多倍長整数は Zig 標準ライブラリの `std.math.big.int` を使う。0.17.0 に存在し、演算と基数変換が動作することは実機で確認した。自前で多倍長演算を書かない。

実装は段階4にまとめる。段階1から段階3では fixnum と flonum のみを扱い、範囲外の演算は「段階4で対応予定」と明示したエラーを返す。黙って精度を失わせない。

演算結果は常に最も単純な表現に正規化する。bignum が64ビット整数に収まるなら fixnum に、分母が1の ratnum は整数に、虚部が正確な0の compnum は実数にする。正規化を怠ると `eqv?` と `=` の整合性が崩れる。

不正確な数の表示は読み戻して同じ値になる最短表現とする。Zig の `{d}` と `{e}` は最短往復表現を与えるが Scheme の記法とは異なるため、桁列の供給源としてのみ使い、小数点の配置と指数表記への切り替えは自前で行う。

## 結果

- メリット: 要件を満たす。`std.math.big.int` を使うことで最も誤りやすい部分を標準ライブラリに委ねられる。
- デメリット・受け入れたトレードオフ: 段階4の作業量が大きい。`std.math.big.int.Managed` は `std.mem.Allocator` で確保するため、GC の sweep で解放する仕組みが必要になり、GCヒープ外の資源を持つオブジェクトという例外的な扱いが生じる。限界値列の大きさはヒープ上限の計上に含める([runtime.md](../design/runtime.md) の計上の対象)。含めないと、本体が小さくペイロードが大きいオブジェクトで上限が効かない。成果物のサイズが増える。
- 将来の見直し条件: 複素数の実装が段階4の完了を大きく遅らせる場合、`(scheme complex)` のみを段階5以降に繰り延べる。その場合も数値塔の他の部分は段階4で完成させる。範囲を縮小する判断はユーザーの承認を得て行う。
