# ADR-0024: 検証ツールは受理する綴りの集合を閉じ、知らない綴りを報告する

- ステータス: 採用
- 日付: 2026-10-08

## 背景

`tools/check-docs` は YAML(ワークフロー)と Markdown(文書と記録)を読む。どちらも本格的なパーサを持たず、行単位の文字列マッチで読んでいる。

段階0の自己敵対的レビューで、同じ類型の必須指摘が4巡続けて出た。いずれも「文字列マッチが別の綴りに負ける」ものである。閉じるたびに次の綴りが現れた。経緯は [docs/review/stage0-findings.md](../review/stage0-findings.md) にある。

綴りを1つずつ潰すやり方には終わりがない。YAML と CommonMark はどちらも、同じ意味を複数の綴りで書ける言語である。受理する側を広くとると、意図しない綴りが意図しない意味で読まれる。

## 決定

検証ツールが外部の記法を読むとき、受理する綴りの集合を閉じる。集合の外にある綴りは、黙って無視せず報告する。

### ワークフロー

使ってよいキーを列挙し、それ以外のキーを報告する。列挙は `tools/check-docs` の `allowed_workflow_keys` が持つ。

`if:` と `continue-on-error:` は意図的に列挙に入れない。`.github/workflows/ci.yml` の冒頭コメントが「条件分岐も『段があれば走らせる』も置かない」と禁じており、飛ばされた検証と許された失敗は走っていないのと同じである。ジョブ階層か段階層かで区別しない。どちらも検証を止める手段になる。

`run:` のブロックスカラーも報告する。ブロックスカラーの行はキーではないので、隣のキーの値と区別する手がかりが行の形に無い。コマンドは `run:` の行に書く。

段階が進んで新しいキーが必要になったときは、それが検証に対して何を意味するかを決めてから列挙に足す。赤になることが、決める契機である。

### Markdown の記録

記録は列0の行からだけ読む。字下げされた行は、何として描画されるかに関わらず読まない。

4スペースの意味は包含ブロックで変わる。最上位ではコードブロックだが、箇条書きの中では項目の続きか入れ子の箇条書きである。CommonMark は「箇条書きマーカーの後の本文の位置が、以降のブロックに必要な字下げを決める」と定めているので、絶対的な桁数では判定できない。

そのうえで、記録に見えるのに字下げされている行を報告する。読まれない場所に記録を書けないようにするためである。

この2つは「読者に見えて機械に見えない記録」を狭めるが、消しはしない。字下げの判定と記録の綴りの判定が、どちらも有限の規則でできているためである。実際に反例が4種類見つかった。全角コロンと強調で書いた記録、全角空白で字下げした記録、記録として認識していなかった表のラベル、行の途中に書いた HTML コメントで囲んだ記録である。いずれもその時点の規則を広げて閉じた。規則を広げるたびに同じ形の反例が出なくなるが、「もう存在しない」とは言えない。この節が約束するのは、見つかった反例を規則の側で閉じることであって、反例が尽きたことではない。

### コードスパン

`<!--` のようなマーカーがコードスパンの中にあるかを判定するときは、閉じるバッククォートが同じ行にあることを要求する。対応の取れていないバッククォートは文字どおりの文字として扱う。

すべてのバッククォートがスパンを開くとみなすと、1つ閉じ忘れた行の残りがコードとして読まれ、その後のマーカーが効かなくなる。逆にコードスパンを一切考慮しないと、記法そのものを説明する散文が文書を黙らせる。

## 結果

- メリット: 知らない綴りが穴ではなく診断になる。検査が「この綴りだけを読む」と宣言し、その宣言を自分で守る。綴りを追いかける巡回が終わる。
- デメリット・受け入れたトレードオフ: 正当な綴りが赤になることがある。ジョブ階層の `if:` と `run:` のブロックスカラーは YAML として正当だが拒否する。記録を箇条書きの中に書けない。新しいキーを使うたびに列挙を更新する手間がかかる。列挙が実態から遅れると、作業が止まる方向に遅れる。
- 将来の見直し条件: 列挙の更新が作業の妨げになるほど頻繁になった場合、または本格的な YAML パーサを依存に加える判断をした場合、本ADRを非推奨にして新ADRを書く。パーサを加える判断は依存関係の追加なので、[AGENTS.md](../../AGENTS.md) の進め方に従ってユーザーの確認を得る。
