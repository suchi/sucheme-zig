# ADR-0024: 検証ツールは受理する綴りの集合を閉じ、知らない綴りを報告する

- ステータス: 採用
- 日付: 2026-10-08

## 背景

`tools/check-docs` は YAML(ワークフロー)と Markdown(文書と記録)を読む。どちらも本格的なパーサを持たず、行単位の文字列マッチで読んでいる。

段階0の自己敵対的レビューで、同じ類型の必須指摘が4巡続けて出た。いずれも「文字列マッチが別の綴りに負ける」ものである。閉じるたびに次の綴りが現れた。経緯は [docs/review/stage0-findings.md](../review/stage0-findings.md) にある。

綴りを1つずつ潰すやり方には終わりがない。YAML と CommonMark はどちらも、同じ意味を複数の綴りで書ける言語である。受理する側を広くとると、意図しない綴りが意図しない意味で読まれる。

## 決定

検証ツールが外部の記法を読むとき、受理する綴りの集合を閉じる。集合の外にある綴りは、黙って無視せず報告する。

### ワークフロー

使ってよいキーを列挙し、それ以外のキーを報告する。列挙は `tools/check-docs` の `allowed_workflow_keys` が持つ。

`if:` と `continue-on-error:` は意図的に列挙に入れない。`.github/workflows/ci.yml` の冒頭コメントが「条件分岐も『段があれば走らせる』も置かない」と禁じており、飛ばされた検証と許された失敗は走っていないのと同じである。ジョブ階層か段階層かで区別しない。どちらも検証を止める手段になる。

`run:` のブロックスカラーも報告する。ブロックスカラーの行はキーではないので、隣のキーの値と区別する手がかりが行の形に無い。コマンドは `run:` の行に書く。

段階が進んで新しいキーが必要になったときは、それが検証に対して何を意味するかを決めてから列挙に足す。赤になることが、決める契機である。

### 記録の綴り

記録は、読者に同じに見える文字を1つに正規化してから読む。対象は全角コロン、Unicode の空白文字、ゼロ幅文字、強調記号、コードスパンのバッククォート、コロンの直前の空白である。集合は `tools/check-docs` の `colon_spellings`・`space_spellings`・`invisible_spellings` が持つ。

報告する側ではなく正規化する側を広げる。記録語を含む行をすべて報告すると、記録について書いた散文が報告されるからである。正規化すれば、読者が記録として読む行を機械も記録として読む。

### 記録の位置

記録は列0の行からだけ読む。字下げされた行は読まない。そのうえで、記録に見えるのに字下げされている行を報告する。読まれない場所に記録を書けないようにするためである。

字下げをコードブロックとみなすのは、空行の後に始まり、かつ箇条書きの外にある、4スペース以上の行に限る。CommonMark は「箇条書きマーカーの後の本文の位置が、以降のブロックに必要な字下げを決める」と定めており、字下げコードブロックは段落を中断できない。絶対的な桁数だけで判定すると、表の途中に字下げした行と箇条書きに入れ子にした記録が、どちらも描画されるのに読まれも報告もされなくなる。

フェンスの内側とみなすのは、開いたフェンスと同じ深さ以上に字下げされた行だけである。この規則は記録を読む側(`visibleMarkdown`)と報告する側(`checkNoIndentedRecords`)の両方が同じに持つ。片方だけを直すと、字下げしたフェンスに挟まれた列0の記録が、一方には潰され他方には飛ばされて、どちらも読まないという穴になる。

### HTML コメント

HTML コメントの開始マーカーは、行の途中にあっても開始として読む。CommonMark はインラインの raw HTML をそのまま出力し、ブラウザはブロックのコメントと同じように隠す。位置で区別すると、隠れた値が記録として読まれて可視の値が無視される。

マーカーがコードスパンの中にあるかは判定しない。判定にはインラインパーサが必要で、2度試して2度失敗した。すべてのバッククォートがスパンを開くとみなすと、1つ閉じ忘れた行の残りがコードとして読まれ、その後のマーカーが効かなくなる。バッククォートの連なりを長さで対応させると、2連のスパンが「空のスパンと開始マーカー」として読まれる。

したがって、本リポジトリの Markdown の散文に開始マーカーそのものを書けない。閉じていないマーカーは報告されるので、代償は沈黙ではなく診断として現れる。

### この節が約束しないこと

ここに書いた規則は「読者に見えて機械に見えない記録」を狭めるが、消しはしない。実際に見つかった反例は、全角コロンと強調で書いた記録、全角空白で字下げした記録、記録として認識していなかった表のラベル、行の途中に書いた HTML コメントで囲んだ記録、ゼロ幅空白を挟んだキー、コードスパンで囲んだキー、箇条書きに4スペースで入れ子にした記録、字下げしたフェンスに挟んだ記録である。いずれもその時点の規則を広げて閉じた。

規則を広げるたびに同じ形の反例は出なくなるが、「もう存在しない」とは言えない。本ADRが約束するのは、見つかった反例を規則の側で閉じることであって、反例が尽きたことではない。

## 結果

- メリット: 知らない綴りが穴ではなく診断になる。検査が「この綴りだけを読む」と宣言し、その宣言を自分で守る。綴りを追いかける巡回が終わる。
- デメリット・受け入れたトレードオフ: 正当な綴りが赤になることがある。ジョブ階層の `if:` と `run:` のブロックスカラーは YAML として正当だが拒否する。記録を箇条書きの中に書けない。Markdown の散文に HTML コメントの開始マーカーを書けない。新しいキーを使うたびに列挙を更新する手間がかかる。列挙が実態から遅れると、作業が止まる方向に遅れる。
- 将来の見直し条件: 列挙の更新が作業の妨げになるほど頻繁になった場合、または本格的な YAML パーサ・CommonMark パーサを依存に加える判断をした場合、本ADRを非推奨にして新ADRを書く。パーサを加える判断は依存関係の追加なので、[AGENTS.md](../../AGENTS.md) の進め方に従ってユーザーの確認を得る。
