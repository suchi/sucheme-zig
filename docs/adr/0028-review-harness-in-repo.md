# ADR-0028: 実機確認のハーネスをリポジトリに置き、Python で書く

- ステータス: 採用
- 日付: 2026-10-09

## 背景

検査ツールの指摘は、実機で再現してから直す。穴のシナリオが赤になることと、正当な記述が緑のままであることの対照を両方取る。段階0でこの形が有効だったので、巡ごとのシナリオを積み上げてきた([review/process-lessons.md](../review/process-lessons.md))。

その道具がリポジトリの外、作業マシンのユーザ領域にあった。実行環境を移すと消える。クラウドで開発を続けるときに、ハーネスとシナリオの蓄積が分断される。

シェルで同じことをすると承認待ちで止まる。`git clean -f` がフックの確認判定に当たるので、シナリオごとに確認が入り、1巡で数十回になる。ハーネスの中(`subprocess`)で行うとフックを通らないので、承認はスクリプトの起動1回だけで済む。この差で巡回の所要時間が1桁変わった。

## 決定

ハーネスとシナリオを `tools/review-harness/` に置く。言語は Python とする。

### 検証コマンドには入れない

`AGENTS.md` の検証コマンド表に行を足さない。CI でも走らせない。レビューのときに人とエージェントが使う道具であって、成果物の正しさを守る検査ではない。したがって Python は開発の前提ではなく、レビューを実機で行うときの前提である。

この線を引くのは、[ADR-0026](0026-verify-facts-about-code-not-prose.md) が検査の対象を絞った判断と同じ理由である。道具を検証の鎖に入れると、道具自身の正しさを守る検査が要る。段階0でそれをやって、検査ツールが製品より大きく育った。

### Zig で書き直さない

リポジトリの言語が1つ増える。それでも Python を選ぶ理由は3つある。

ハーネスがやっているのは、複製の作成、ファイルの差し替え、外部プロセスの起動と終了コードの読み取りである。Zig で書くと同じことに数倍の行数がかかり、その行数は製品の役に立たない。

シナリオは1巡ごとに書き捨てる。レビュアが差分を読んで20〜30件の改変をその場で書く用途なので、書く速さが効く。

Zig で書くと `zig build test` の対象になり、この道具自身が検査の対象になる。良い面もあるが、段階0の経緯からは、道具を検証の鎖に入れないほうを選ぶ。

### 置き方

`tools/review-harness/harness.py` が複製の作成・リセット・検証コマンドの実行を持つ。`tools/review-harness/scenarios/roundNN.py` が巡ごとのシナリオで、1回の呼び出しで全件流す。作業ディレクトリは `_work/review-harness` で、`.gitignore` が `_work` を無視する。

過去の巡のシナリオは残す。後の巡で閉じた穴が再び開いたかを、同じ入力で確かめられる。閉じた穴の対象が消えた場合は、その旨を注記して残す(削除すると、なぜ消えたかが分からなくなる)。

## 結果

- メリット: 実行環境を移してもハーネスとシナリオの蓄積が残る。レビュアへの指示文が安定する。承認待ちが出ない形が既定になる。
- デメリット・受け入れたトレードオフ: リポジトリに Zig 以外の言語が1つ入る。レビューを実機で行うときに Python が必要になる。ハーネス自身は検査の対象にならないので、壊れていても検証コマンドは緑のままである(壊れていればシナリオのベースラインが赤になるので、使えば分かる)。
- 将来の見直し条件: ハーネスが育って製品の一部を模倣し始めた場合、または Python が開発の前提に広がった場合、本ADRを非推奨にして新ADRを書く。
