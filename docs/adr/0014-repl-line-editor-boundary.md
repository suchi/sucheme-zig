# ADR-0014: 行編集は抽象境界のみ先に定め、実装方式は段階7で決める

- ステータス: 採用
- 日付: 2026-10-04

> 2026-10-15 追記: 決定の意図は変えない。決定の第1項の `LineReader` の union は、段階1から段階2の実装では置いていない。スライス 1l の計画([0010](../plans/0010-slices-1k-1l-primitives-and-repl-continuation.md) の合意を求める点の7)で、変種が1つだけの union は使われない構造になるので作らないと合意した。いま境界として保っているのは第2項の完結判定の共有である。リーダが不足を表す `Incomplete` を返し、`sucheme.isIncomplete`(定義は `reader.isIncomplete`)が入力の完結を判定し、REPL(`src/main.zig` の `repl`)は `*std.Io.Reader` から行を読んで、この関数が偽になるまで継続行として保留に足す。union は、`rich` を入れる段階7で作る。それまでの `dumb` に当たるものは、`repl` が `*std.Io.Reader` を直接読む形である。

## 背景

要件として、最終的に REPL で複数行編集と Emacs バインディングによる編集ができることが求められている。一方、初期の段階ではこの機能は不要とされている。

実装方式には次の選択肢がある。

- 自前で Zig で実装する。依存が増えない。生モードの設定、キー列の解釈、キルリング、履歴検索、文字幅の計算、複数行の再描画を自分で作る必要がある。
- C のライブラリをリポジトリに取り込む。Zig は C を容易にビルドできる。Windows に対応し、複数行編集と Emacs バインディングを備えたものが存在する。取り込むコード量が大きい。

この判断は段階7の作業内容に関わるが、段階1から段階6の設計には影響しない。一方、境界を決めずに段階1を作ると、素朴な行読み取りの前提がREPL全体に染み出す危険がある。

## 決定

抽象境界のみを設計段階で定め、実装方式の選択は段階7まで延期する。

- `LineReader` という union を置き、`dumb`(行単位。端末でない入力でも使う)と `rich`(生モードでの編集)の2つの実装を持てる構造にする。段階1から段階6では `dumb` のみを実装する。
- 入力が完結したかどうかの判定はリーダに委ねる。リーダは不足を表す専用の結果を返し、REPL はそれを見て継続行を促す。括弧の数を数える方式は、文字列やブロックコメントの中の括弧で誤判定するため使わない。この判定関数は `dumb` と `rich` の両方が共有する。

`std.Io.Terminal` は色付き出力のための書き込み側の抽象であり、入力の生モードは提供しないことを実機で確認した。生モードの設定はいずれの方式でも自前のプラットフォーム別コードが必要になる。

## 結果

- メリット: 段階1を素朴な実装で早く立ち上げられる一方、後からの差し替えが局所に収まる。完結判定を共有することで、素朴な実装と本格実装で挙動が食い違わない。段階7の判断を、実際のコード規模を見た上で行える。
- デメリット・受け入れたトレードオフ: 判断を先送りするため、段階7の作業量が確定しない。抽象境界が実際の要求に合わない可能性があり、その場合は境界自体の見直しが必要になる。
- 将来の見直し条件: 段階7の開始時に、自前実装と取り込みのそれぞれの作業量を見積もり、選択肢とトレードオフを提示してユーザーの判断を得る。その結果を新しいADRとして記録する。
