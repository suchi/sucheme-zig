## 背景

[ADR-0003](0003-precise-mark-sweep-gc.md) は、確保量が閾値を超えたとき、確保の内部で GC が走ると定めている。そのため、確保をまたいで保持する値は一時ルートに登録する規約と、確保しうる関数に `GCを起動しうる` と書く規約を置いた。

スライス 1g で GC ヒープを作るとき、この形には次の問題が見えた。

- 登録漏れはメモリ破壊になり、コンパイラでは見つからない。確保する箇所はリーダ、機械、プリミティブ、展開器に散らばっていて、箇所ごとに「ここで GC が走っても、持っている値は残るか」を確かめ続けることになる。
- 上限超過は Scheme のエラーで、その送出は機械の実行を要する。確保の内部で走る GC は機械を再帰的に起動できない([runtime.md](../design/runtime.md) の計上の対象)。
- 精密 GC を現実的にしているのは、機械の状態が少数のレジスタに集まっていることである([ADR-0004](0004-cek-machine-evaluator.md))。ステップの境目では、確保の途中の値が存在せず、持っている値はレジスタと大域環境とコードの定数だけになる。

## 決定

GC は機械のステップの境目と、`Interpreter` が1行の中の各フォームを読む前でだけ実行する。どちらも、持っている値が文脈のものだけ(前者はレジスタを加えた3つ)になる境目である。確保は計上量を増やし、閾値を超えたかどうかを `Heap.shouldCollect` で答えるだけで、GC を走らせない。機械はステップの先頭で `shouldCollect` を見て、真なら `Heap.collect` を呼ぶ。`Interpreter` は、フォームを読む前に同じことをする。

ルートは次の3つである。

- 機械の4レジスタのうち、環境・継続・値(制御は節点を指し、節点はヒープの外にある)。
- 大域環境の値。
- コードの定数。節点がヒープの外にあって走査されないので、展開器が、ヒープを指す定数(`quote` したデータ)を `Context` の表に登録する。コードをヒープに移すスライスで、この表は要らなくなる。

一時ルートは、この決定の間は要らない。`GCを起動しうる` の規約も要らない。確保の途中で GC が走らないからである。確保の失敗に巻き戻す単位は、1回の確保呼び出しである(ペイロードを先に確保し、所有者の確保が失敗したらペイロードを返す)。

計上の上限に達したときは `error.HeapLimit` を返し、`Context` が `heap limit exceeded` の条件に変える。境目の GC のあとも、生きているものが上限に近いとき(上限の16分の1の余裕がないとき)は、境目で同じエラーにする。条件オブジェクトは 1g ではヒープに置かず、上限の外のアリーナに作る。上限に達していてもエラーを報告できる。

選ばなかった案は次の2つである。

- ADR-0003 のとおり確保の内部で走らせる案。ルートの登録漏れが散らばる。ストレスモードで検出できても、確保するすべての箇所に規約が要る。
- 確保が失敗したときだけ GC して再試行する案。確保の内部の GC と同じ問題を抱える。

## 結果

- メリット: ルートが3つに固定され、登録漏れの類型が機械の境目の1箇所に集まる。境目ごとに GC を走らせるストレスモードで、ルートの漏れを即座に検出できる。
- デメリット・受け入れたトレードオフ: 1つのステップの中や1回の読み取りの中で大きく確保すると、GC が間に合わずに上限へ当たる。1g のプリミティブは数値演算だけで、読み取りの大きさは行の長さで抑えられるので、実害は無い。大きく確保するプリミティブが入る段階で見直す。閾値を超えたあとステップの境目まで確保が続くので、計上量は閾値を少し超える。
- 将来の見直し条件: 1ステップで大きく確保するプリミティブ(文字列やベクタの生成)が入るとき。ハンドラと `guard` が入る段階2で、条件オブジェクトをヒープに置き、送出のための予約領域([runtime.md](../design/runtime.md))を実装するとき。
