# ADR-0027: 指摘の重要度を帰結で定め、レビューを費用の側で止める

- ステータス: 採用
- 日付: 2026-10-08
- 置き換え: [ADR-0023: mandatory-zero-convergence](0023-mandatory-zero-convergence.md) を非推奨とし、本ADRが最新の決定となる

## 背景

ADR-0023 は収束条件を「必須の新規指摘ゼロ」とし、必須を「検証コマンドが緑のまま穴が開くもの」と「記録された事実が誤っているもの」の2つで定めた。

段階0でこの条件も成立しなかった。巡回は20巡を超え、各巡の必須は下降せず、製品コードは1行も増えないまま検査ツールと文書だけが育った。巡ごとの件数は [review/stage0-findings.md](../review/stage0-findings.md) が正で、ここに複製しない。

原因を4つに分けて書く。レビューの対象を狭めることでは解けないからである。

### 停止条件が出力の側にあった

「新規指摘ゼロ」は、能力のあるレビュアを相手にすると終わらない。どの成果物にも何かは見つかる。終わらせるには、出力ではなく費用と価値の側に条件が要る。ADR-0017 も ADR-0023 もこれを出力の側に置き、ADR-0023 は「基準を下げたのではなく対象を分けた」と書いて同じ形を保った。分けたのは対象であって、停止の仕組みは変えていなかった。

### 重要度が帰結ではなく種類で決まっていた

「記録された事実が誤っている」は巨大な集合である。この定義のもとでは、`zig build check-docs` が問題を報告しながら終了コード0で終わる件と、レビューの帳簿の任意の件数が9と6で食い違う件が、同じ必須になる。前者は将来のすべての検証を守り、後者は何も守らない。マージの門を同じ重さで塞いでいた。

### 成果物の寿命を区別していなかった

段階の計画書は、その段階が終われば用済みになる。ADR は何年も効く。`AGENTS.md` は毎セッション読まれる。3つに同じ労力をかけ、同じ頻度で全面再走査していた。

### 帳簿が指摘を自己生産していた

巡ごとの表に「指摘数」と「内訳」の両方を書いていたので、同じ数が2箇所にあり、食い違うたびに指摘が湧いた。20巡目の必須のうち複数がこれである。削るべきはレビューではなく、導ける数の重複だった。

## 決定

レビューはやめない。文書のレビューもやめない。重要度を帰結で定め、停止を費用の側に置き、頻度を寿命で分ける。

### 重要度は帰結で決める

必須は次の3つに限る。

- 検証が黙って止まる。1箇所の編集で検証コマンドが緑のまま検査が走らなくなる、または報告が出なくなるもの。
- 機械が依存している記録が偽である。版の固定、ベンダリングした入力と生成物のハッシュ、検証コマンド表の行のように、プログラムがその記録を読んで動くもの。
- ADR が、実際にしていない決定を書いている。決定の記録が決定と違うことは、後から読む者が前提を誤る。

推奨は、人が依存している記録が偽または誤解を招くものである。`AGENTS.md`、`docs/onboarding.md`、`docs/roadmap.md` の現在地、設計文書の本文がこれに当たる。

任意は、帳簿の数え上げ、doc コメントの言い回し、節見出しの番号、整形である。**レビュー過程についての記録(`docs/review/`)に対する指摘は、任意を上限とする。** レビュアの手控えを敵対的にレビューすることが、終わらない巡回の主要な供給源だった。

### 収束の判定はその巡の必須の中身で行う

ある巡の必須がすべて推奨か任意の帯に属するなら、収束したとみなす。件数がゼロであることを求めない。

### 終わらなさそうなら、基準を変えるか機能を減らす

巡の数で止めない。巡回に上限を置くことは、品質と費用のどちらについても何も言っていない。収束しそうにないと分かった時点で、巡を1つ足す前に次の2手のどちらかを選び、選んだことを記録する。

1. **品質基準を変える。** その成果物のその段階で必須とするものを狭める。狭めた範囲と、狭めても守られる性質を ADR に書く。
2. **いったん機能を減らす。** 指摘を生んでいる機構そのものを外し、やり残しとして記録して次へ進む。段階が進んで必要になったら戻す。

これは [ADR-0018](0018-incremental-vertical-slices.md) の漸進的な進め方そのもので、新しい規律ではない。段階0で実際に2回これをやった。16巡目に文書の書き方を見る検査を撤回したのが2で([ADR-0026](0026-verify-facts-about-code-not-prose.md))、20巡目に `build.zig` の守りとリンク検査に線を引いたのが1である。問題は、どちらも10巡遅かったことと、この2手が選択肢として名前を持っていなかったことである。名前が無いので、巡を足すことが既定の行動になっていた。

次の兆候が1つでも出たら、巡を足す前にどちらを採るかを決め、ユーザーに諮る。

- その巡の必須の件数が、前の巡より減っていない。
- 指摘の中身が、レビュー自身の記録や検査ツール自身の読み方に移っている。
- 修正が、新しい機構を足す形になっている(足した機構が次の巡の攻撃面になる)。

段階0ではこの3つがすべて14巡目の時点で出ていた。帳簿にその事実を書きながら、巡を足し続けた。

### 頻度は寿命で分ける

ADR と `AGENTS.md` は毎巡見る。長く効き、量が小さく、誤りの代償が大きい。

段階の計画書と `docs/review/` の帳簿は、その段階の終わりに1回見る。段階の途中で全面再走査しても、まだ書き換わる文書を追いかけることになる。

### 導ける数を2箇所に書かない

帳簿の巡ごとの表から「指摘数」の列と、対応欄の件数を落とす。内訳から導ける数を別に書くと、食い違いが指摘として湧く。各指摘の処理状況は、巡ごとの節の状態欄が正である。

この規律は帳簿に限らない。導ける数を2箇所に書いている箇所を見つけたら、検査を足すのではなく片方を消す。

### 引き継ぐもの

推奨と任意を `docs/review/` に記録して該当する段階の作業項目に回すこと、記録せずに閉じないこと([ADR-0018](0018-incremental-vertical-slices.md))、外部レビューの可否をマージの条件に含めないこと、再発した類型のうちコードまたは生成物についてのものを検査として足すこと([ADR-0026](0026-verify-facts-about-code-not-prose.md))、実測値を散文に書かないこと。いずれも ADR-0023 から変えない。

手順の正は `AGENTS.md` の「PR・レビュー・マージ」の節である。本ADRは判断とその理由を記録する。

## 結果

- メリット: マージの門を塞ぐものが、守る対象を持つ指摘に限られる。巡回が有限になる。文書のレビューを失わない。帳簿の自己生産がなくなる。
- デメリット・受け入れたトレードオフ: 帰結の判定にレビュア側の裁量が残る。「人が依存している記録」の誤りがマージを止めなくなるので、読まれないまま残る可能性がある。基準を変えるか機能を減らすかの判断は、そのたびにユーザーの確認が要るので、巡回の自動化は進まない。
- 将来の見直し条件: 推奨の積み残しが段階の完了判定を妨げるようになった場合、または兆候が出ているのに2手のどちらも採られないまま巡が続いた場合、本ADRを非推奨にして新ADRを書く。
