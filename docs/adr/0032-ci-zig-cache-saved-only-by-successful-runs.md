# ADR-0032: CI の Zig キャッシュは、成功した実行だけが、ビルド入力から決まるキーで保存する

- ステータス: 採用
- 日付: 2026-10-11

> 2026-10-12 追記: スライス 1j-1 で足した週1回の定期実行の `fuzz.yml` は、`use-cache: false` で `setup-zig` を使い、`actions/cache` の手順を置いていない。決定の末尾が名指しする「1j のファジング」のうち、キャッシュの保存の形は、保存を行わないので適用していない。置かない理由は、`ci.yml` が保存する `.zig-cache` が単体テストのビルドの結果で、ReleaseSafe のファジング用のキャッシュではないことと、週に1回の実行ではビルド時間の節約が小さいことである。キャッシュを保存する `ci.yml` と `full.yml` の形は、本ADRのとおりで変わらない。成果物とリリースのワークフローがキャッシュを保存する場合の扱いは、そのスライスで決める。

## 背景

2026-10-11、`main` と複数の PR で、Windows の CI が `zig build` の最初の1手で `failed to spawn .zig-cache\o\...\maker.exe: FileNotFound` として落ち続けた。変更の内容とは無関係で、再実行しても直らなかった。同じ日にリポジトリの Actions のキャッシュ領域が上限の 10 GB に達した。

原因は、ログから次の順に確かめた。

1. `zig build` が落ちたのは、復元した `.zig-cache` が不整合だったからである。ビルドの記録は残っているのに、記録が指すビルドランナーの実行ファイルがない。
2. 不整合なキャッシュを作ったのは、`main` への push で取り消されたラン(38122580155)の Windows ジョブである。このジョブは、正常なキャッシュ(圧縮後 351 MB)の `tar` 展開を始めて約2秒後に取り消された。展開は途中で止まった。
3. 取り消されたあとでも、`mlugg/setup-zig` の後処理(`post.js`)は走った。この後処理は、ジョブの成否を見ずに、キャッシュのディレクトリを新しいキー `...-<ラン番号>-<試行番号>` で保存する。半分しか展開されていないディレクトリが、正常なものの約半分の大きさ(195 MB)で保存された。
4. 復元は、キーの前方一致で最も新しいものを取り、中身を検証しない。そのため、不完全なキャッシュが、正常なものより新しいという理由で選ばれた。
5. 復元した次のランは `zig build` で落ち、その後処理がまた同じディレクトリを新しいキーで保存した。これで、最新のキャッシュは常に不完全なものになった。失敗から自力で抜け出す道がなかった。

10 GB に達した原因は同じ設計にある。`setup-zig` は、ランごと・OS ごとに、新しいキーで 200 MB から 350 MB を保存する。ブランチごとの最新の1つしか使われないのに、古いものを消さない。この日は 5 時間ほどで 27 回のランがあり、2 つの OS で 50 を超える保存があった。上限に達すると、最近使われていないものから自動で消える。復元で使われ続ける不完全なキャッシュは「最近使われた」ものなので、残る側に回りやすい(これは推測であり、キャッシュの一覧を取れなかったので確かめていない)。

## 決定

Zig のビルドキャッシュは、`setup-zig` の自動のキャッシュ(`use-cache: false` で切る)でなく、GitHub 自身の `actions/cache` で扱う。

```yaml
- uses: actions/cache@<SHA> # v6.1.0
  with:
    path: .zig-cache
    key: zig-cache-v1-${{ runner.os }}-${{ hashFiles('.zigversion', 'build.zig', 'build.zig.zon') }}
```

- 保存は、ジョブが成功したときだけ、かつ、このキーが無かったときだけ行われる(`actions/cache` の `post-if: success()` と、同じキーを上書きしない仕様)。取り消されたジョブ、失敗したジョブは保存しない。展開の途中で取り消されても、不完全なものが残らない。
- キーは、キャッシュの中身を決める入力(Zig の版、`build.zig`、`build.zig.zon`)で決まる。ソースを変えるたびに新しいキーを作らないので、エントリの数は OS ごとに少数で済む。PR は、`main` が保存したエントリを正確なキーで復元するので、新しく保存しない。
- 古いキャッシュへの復元(`restore-keys`)は使わない。キーが一致しなければ、冷えた状態から始め、成功すれば新しいキーで保存する。不完全なものを前方一致で拾う道を、なくすためである。
- 捨てたいときは、キーの `v1` を変える。手作業でキャッシュを消す必要はない。これが復旧の手順である。
- `ci.yml` と `full.yml` の両方に適用する。以後、Zig を使うワークフロー(1j のファジング、成果物、リリース)も同じ形にする。

検討して選ばなかった案:

- キャッシュをやめる(`use-cache: false` のみ): 不整合は起きないが、毎回ビルドランナーと標準ライブラリを作り直す。速さを優先するので、採らない。壊れたときの緊急の切り替えとして残す。
- `setup-zig` の `cache-key` で分ける: キーの一部を変えるだけで、ジョブの成否を見ずに保存する性質は変わらない。
- `setup-zig` のまま、壊れたキャッシュを手作業で消す: 今回の対処であり、真因を残す。

## 結果

- メリット: 取り消し・失敗で不完全なキャッシュが作られない。保存の数が、ランの数でなくビルド入力の種類で決まるので、10 GB の上限に届きにくい。復旧がキーの文字列を変えるだけで済む。
- デメリット・受け入れたトレードオフ: キャッシュはキーが変わるまで更新されない。ソースの変更ぶんは毎回ビルドし直す(標準ライブラリなど重い部分は残る)。`main` への最初の push が保存するまで、新しい PR は冷えた状態で走る。`check-docs` の許可するキーに `path`、`key`、`use-cache` を足した。`setup-zig` を `use-cache: false` なしで書くことを、機械では見張っていない。検査を足す費用が大きく、[ADR-0026](0026-verify-facts-about-code-not-prose.md) と [ADR-0027](0027-severity-by-consequence-and-a-cost-side-stop.md) の費用側の規則に反するためである。このADRと、Zig を使うワークフローを足す計画書に書いて守る。
- 将来の見直し条件: キャッシュの効果が小さいと分かったとき(ビルド時間の計測で、冷えた状態との差が小さいとき)は、キャッシュをやめる。`use-cache: false` の抜けが実際に起きたときは、機械の検査を足す。
