# ADR-0037: `(sucheme core)` を段階2の間だけ利用者に公開し、段階3で隠す

- ステータス: 採用
- 日付: 2026-10-14
- 一部置き換え: [ADR-0006: library-system-and-scheme-level-stdlib](0006-library-system-and-scheme-level-stdlib.md) の決定のうち、「`(sucheme core)` は利用者に公開しない」を、段階2の間だけ置き換える。Zig が `(sucheme core)` を登録すること、その上に `lib/sucheme/derived.scm` と `lib/scheme/base.sld` を重ねる起動順序、族の一覧は変わらない

## 背景

[ADR-0006](0006-library-system-and-scheme-level-stdlib.md) と [frontend.md](../design/frontend.md) の起動順序の節は、次の順序を決めている。Zig がコアの特殊形式とプリミティブを内部用のライブラリ `(sucheme core)` として登録する。その上で `lib/sucheme/derived.scm` が派生構文を定義し、`lib/scheme/base.sld` が `(scheme base)` を構成する。`(sucheme core)` は内部用なので、利用者には公開しない。

段階2のスライス 2m は、ライブラリの登録表と `define-library` `import` `export` を入れる。ところが `(scheme base)` を作るのは段階3で、`lib/` の埋め込みも段階3で入る。段階2の時点で、次の3つが `(sucheme core)` なしには成り立たない。

- ライブラリの本体は、`import` で得たものしか見えない(R7RS 5.2、5.6.1)。`define` や `lambda` を `import` で得られる手段が無いと、利用者のライブラリを書けない。段階2の完了条件のテストも書けない。
- REPL の初期環境は、段階1から、特殊形式とプリミティブがすべて見える状態である。初期環境を空にすると、既存のテストと利用者の入力が壊れる。
- レコードの低水準のプリミティブ(2h の `%make-record-type` など)は `(scheme base)` に入れない(R7RS 5.6.1 は `scheme` で始まるライブラリに独自の識別子を入れることを禁じる)。段階3の `define-record-type` の展開先だけが使う名前なので、テストから呼ぶ手段が `(sucheme core)` の外に無い。

## 決定

Zig が `(sucheme core)` を登録し、段階2の間は、利用者のライブラリと REPL からも `import` できるようにする。

- `(sucheme core)` のエクスポートは、特殊形式、補助構文(`...` `_` `else` `=>` `unquote` `unquote-splicing`)、Zig が書いたプリミティブである。プリミティブのセルは、名前が初めて解決されたときに1つだけ作り、インポートする側すべてが共有する。`define-library` と `import` は、束縛された名前ではなく、最上位の形式として扱う(R7RS の `(scheme base)` がこれらをエクスポートしないため)。
- REPL の初期環境は、`(sucheme core)` の全部をインポートしたものとする。段階1から見える束縛に、補助構文の6個(`...` `_` `else` `=>` `unquote` `unquote-splicing`)が加わる。それ以外は、これまでと同じである。この6個を評価したときのエラーの文言は、「束縛されていない変数」から「構文キーワードは変数として使えない」に変わる。準拠マトリクスの `(scheme base)` の束縛済みの数も、この6個ぶん増える。REPL の最上位の束縛の表は、表に無い名前を `(sucheme core)` から引き、インポートした束縛として写す。
- ユーザーのライブラリの本体の初期環境は空である。`(import (sucheme core))` などで、必要なものを得る。

段階3で、この公開を取り消す。取り消すのは、`lib/scheme/base.sld` が `(scheme base)` のエクスポートを定義し、REPL の初期環境を `(scheme base)` などの標準ライブラリのインポートに替えるスライスである。そのスライスで次を行う。

- `(sucheme core)` を、`lib/` に埋め込んだ標準ライブラリだけがインポートできるものにする。利用者のライブラリと REPL からのインポートは、拒否する。
- 段階2のテストのうち `(import (sucheme core))` を含むものを、`(scheme base)` を使う形に書き換える。`(scheme base)` に無い名前(2h の `%` で始まる名前)を呼ぶテストは、`lib/` の側へ移す。
- 決定の変更は、新しい ADR で行い、このADRを非推奨にする。

選ばなかった案は次のとおりである。

- 最小の `lib/scheme/base.sld` を段階2で作り、`(sucheme core)` のうち `(scheme base)` にある名前だけを再エクスポートする案。利用者のコードが段階3でも変わらない。しかし段階3の作業(`(scheme base)` の骨格)と `lib/` の埋め込みの仕組みを前倒しすることになる。レコードのプリミティブをテストから呼べない。準拠マトリクスの数え方が段階2で変わる。
- ライブラリのテストを Zig の単体テストだけにし、利用者には何も開かない案。内部の名前が漏れない。しかし REPL と Web UI でライブラリシステムを試せない。完了条件の手作業の確認も、できなくなる。

## 結果

- メリット: `(scheme base)` を前倒しで作らずに済む。REPL の振る舞いと既存のテストが、補助構文の6個を除いて変わらない。段階2の利用者のライブラリが、`define` や `lambda` を `import` で得られる。レコードの低水準のプリミティブをテストから呼べる。REPL の定義で隠した特殊形式とプリミティブを、`import` で取り戻せる。
- デメリット・受け入れたトレードオフ: `import` と `define-library` は、先頭の綴りで見分ける最上位の形式なので、REPL で同じ名前の手続きを定義しても、その呼び出しはライブラリの形式として扱われる。段階2の間、内部用の名前(`%make-record-type` など)が利用者に見える。段階2のテストに書いた `(import (sucheme core))` は、段階3で書き換える。段階2のリリース(v0.2.0)のリリースノートに、この名前が段階3で使えなくなることを書く。[frontend.md](../design/frontend.md) の起動順序の節は、取り消した後の段階3の状態を述べているので、段階2の間は実装と一致しない。
- 将来の見直し条件: 段階3の `(scheme base)` を構成するスライス。段階2のうちに、利用者のコードが `(sucheme core)` に依存する形で広がり、書き換えの費用が大きいと分かったとき。
