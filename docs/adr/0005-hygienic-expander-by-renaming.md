# ADR-0005: 衛生性は構文環境と別名による改名で実現する

- ステータス: ~~採用~~ 非推奨 → [ADR-0019: denotations-and-identifier-resolution](0019-denotations-and-identifier-resolution.md) に置き換え
- 日付: 2026-10-04

> 非推奨理由: 方式の選択(構文環境と別名による改名)は妥当だが、決定として書いた細部に3つの誤りがあった。意味の列挙5種が R7RS の補助構文6個を表現できない、局所変数の意味を相対的な字句アドレスにすると別々の字句環境の束縛が同一と判定される、識別子の解決の最終段のグローバル環境が処理系全体で1つだとライブラリ隔離(R7RS 5.1)に反する。

## 背景

R7RS 4.3 は衛生的マクロを必須としている。`syntax-rules` は、ネストした省略記号、利用者指定の省略記号、省略記号の後に置く固定パターン、ベクタパターン、リテラルの意味による照合をすべて要求する。

衛生性の実現方式には次の系統がある。

- 明示的改名(Clinger): 変換子に改名関数を渡す。`syntax-rules` はその上に構築できる。
- 構文クロージャ(Bawden と Rees): 式と環境の対を値にする。
- 印と置換(Dybvig): 構文オブジェクトに印と置換の列を持たせる。`syntax-case` を支える最も一般的な機構。

また、どの言語で実装するかという判断もある。本プロジェクトは「コア言語で表現できるものはコア言語で書く」方針を採るため、`syntax-rules` 自体を Scheme で書く選択肢もありえた。

## 決定

構文環境と別名による改名方式を採る。

- 構文環境は識別子から意味(特殊形式、マクロ、局所変数の字句アドレス、グローバルセル、パターン変数)への写像とする。
- 識別子は素のシンボルか別名である。別名は内側の識別子、解決すべき環境(マクロの定義環境)、同一展開を区別する印の3つを持つ。内側の識別子は素のシンボルか、さらに外側の展開由来の別名である。
- 識別子の解決は、現在の構文環境を同一性で検索し、見つからなければ別名の内側の識別子をその別名の環境で解決し、最後にグローバル環境を引く。内側の識別子を渡すことで1回の委譲ごとに別名の層が1つ減り、有限回で停止する。別名自身を渡すと停止しない。
- `syntax-rules` のリテラル照合は意味の一致で判定する。これにより、利用側が `else` を再束縛している場合にリテラルが照合しなくなるという規定が満たされる。
- `quote` の中に現れた別名は、コアIRの定数にする時点で元のシンボルに戻す。

`syntax-rules` の照合器とテンプレート展開器は Zig で実装する。これらは構文環境と別名の機構と密接に結びついており、Scheme で書くには構文環境を操作するAPIを Scheme に公開する必要がある。それは実質的に `syntax-case` 相当の非標準拡張を設計し維持することになるため、採らない。

派生構文(`let` `let*` `letrec` `cond` `case` `and` `or` `when` `unless` `do` `quasiquote` `delay` `guard` `define-record-type` `case-lambda` `let-values` など)は Scheme 側で `syntax-rules` を使って定義する。`parameterize` は、パラメータオブジェクトの表現の選択によりコアの構文として Zig 側に置く([ADR-0006](0006-library-system-and-scheme-level-stdlib.md))。R7RS 7.3 は `syntax-rules` による参考実装を与えているので、テンプレートで表せないという理由ではない。

## 結果

- メリット: `syntax-rules` に必要な機能に対して機構が過剰にならない。構文環境という1つの概念で、特殊形式、マクロ、変数、パターン変数を統一して扱える。派生構文を Scheme で書けるため、Zig 側のコード量が小さく保てる。
- デメリット・受け入れたトレードオフ: `syntax-case` や `er-macro-transformer` のような手続き的マクロへ拡張する場合、変換子の実行が Scheme 手続きの呼び出しになるため展開器を継続フレームとして表現し直す必要がある。段階2ではその拡張を想定した関数境界を作るが、実装はしない。
- 将来の見直し条件: 手続き的マクロを提供する要求が出た場合、印と置換の方式への移行を検討する。その場合は本ADRを非推奨にして新ADRを書く。
