# ADR-0033: aarch64 は自動テストの対象に加えない

- ステータス: 採用
- 日付: 2026-10-12

> 2026-10-12 追記: 本文の決定の段落は、aarch64 のクロスコンパイルのビルドに、スライス 1j-3 の `dist` が入るまで機械による検査が無いと書いている。スライス 1j-3a で `zig build dist` が入った。`dist` は aarch64-linux-musl、aarch64-windows、aarch64-macos を含む、[ADR-0010](0010-ci-cd-and-release-strategy.md) の一覧の全ターゲットを `ReleaseSafe` でビルドし、`full.yml` が PR を ready にしたとき、`main` への push、手動起動で走らせる([ADR-0034](0034-release-shape.md))。全コミットの `ci.yml` では走らせないので、ビルドが通ることの検査は、全コミットでなく、この頻度で入った。aarch64 の実行ファイルは、引き続きどこでも実行しない。結果の欄の「`full.yml` を変えずに済む」は、`dist` のジョブを足したため、この追記以降は当てはまらない(aarch64 の実行を足さないという決定の範囲では、`full.yml` を変えていない)。また、本文の選択肢にある「煙試験」は、このリポジトリの用語ではスモークテストと書く。決定は変わらない。
>
> 2026-10-13 追記: `full.yml` は `main` への push で走らなくなった。起動は、PR を ready にしたときと手動だけである([ADR-0036](0036-windows-tests-in-the-slow-tier.md))。2026-10-12 の追記の「`full.yml` が PR を ready にしたとき、`main` への push、手動起動で走らせる」のうち `main` への push と、本文の選択肢の「`full.yml`(層2、準備完了と `main` への push)」の起動の記述は、この追記以降は当てはまらない。`dist` は、ready のとき、手動、タグの push(`release.yml`)で走る。決定は変わらない。

## 背景

[ADR-0010](0010-ci-cd-and-release-strategy.md) の本文は、自動テストの実行対象を `ubuntu-latest` と `windows-latest`(いずれも x86_64)に限っている。aarch64 の実行ファイルは、クロスコンパイルで作るが実行しない。2026-10-07 の追記は、arm64 の標準ランナーが private リポジトリでも使えるようになったこと([ADR-0020](0020-repository-visibility-private.md) が一次情報を引用している)を受けて検討し、段階0では対象に加えないとした。見直しの時点は段階1と定め、そのときに新しい ADR を書くとした。値表現・GC・WASM が入ると、アライメント・ポインタ幅・エンディアンに依存する判断が初めてコードに現れるためである。

段階1の最後のスライス 1j で、この見直しを行う。判断の材料は次のとおりである。確認は 2026-10-12 に、Linux x86_64 の実行環境で Zig 0.17.0 を使い、`origin/main` の 5d4f07d に対して行った。

確認できたこと:

- `zig build -Dtarget=<t> -Doptimize=ReleaseSafe` が、`aarch64-linux-musl`、`aarch64-windows`、`aarch64-macos` で成功する(この3つを実行した)。[ADR-0010](0010-ci-cd-and-release-strategy.md) の一覧の全ターゲットで成功することは、2026-10-11 に計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md) の作成時に確かめてある。
- `aarch64-linux-musl` の成果物は、静的リンクの ELF 64-bit(ARM aarch64)で、デバッグ情報つきで strip されていない(`file` で確認した)。
- `src/` を `grep` した結果、ポインタの幅・アライメント・エンディアンに関わる記述は次の箇所にある。
  - `@sizeOf`: `src/heap.zig`(`Cell(T)` や `Value` の大きさから、確保量の計上を求める)と、`src/prim/vector.zig`、`src/prim/equiv.zig` のテスト。
  - `@intFromPtr`: `src/trace.zig`(テストの記録用)と、`src/wasm.zig` の `addressOf`(wasm32 の線形メモリ上のアドレスを `u32` にして返す)。
  - `@ptrFromInt`: `src/wasm.zig` の 2 か所(ホストから渡された `u32` のアドレスをポインタに戻す)。
  - `@alignCast`: `src/heap.zig` の `Heap.free` と `Marker.scan` で、ヘッダから `Cell(T)` を得る `@fieldParentPtr` の結果に使う。
  - `std.mem.nativeToLittle`: `src/reader.zig` のファジングの初期入力を作る関数(`fuzzSeed`)に1か所。
  - `@ptrCast` と `@bitCast` は `src/` に無い。
  - `src/wasm.zig` は wasm32 向けのビルドのルートで、`build.zig` の `wasm_exe` だけが使う。aarch64 のビルドには入らない。上の `src/wasm.zig` の記述は、aarch64 の実行ファイルとは無関係である。
- ネイティブのテストは x86_64(64 ビット、リトルエンディアン)で動き、1i の往復テスト(`zig build test-wasm`)は wasm32(32 ビット、4 バイトのポインタ)で動く。64 ビットでないポインタ幅は、すでに一度通っている。aarch64 の Linux と Windows の実行ファイルは、どこでも実行されない。

確かめられなかったこと:

- arm64 ランナーのラベル名と、課金の倍率。GitHub のドキュメントに実行環境から届かなかった。[ADR-0020](0020-repository-visibility-private.md) が引用している 2026-01-29 の Changelog(arm64 は private でも使える、2 vCPU、実行分数はプランに計上)は、その ADR の引用に依る。
- `mlugg/setup-zig` が arm64 ランナーで動くこと。
- QEMU のユーザーモードエミュレーションで aarch64 のテスト実行ファイルを動かすこと。この実行環境に QEMU が無く、Zig の `-fqemu` の動作を確かめていない。
- aarch64 の実行ファイルが、実機で正しく動くこと。
- 上で挙げた `@alignCast` などの箇所が、aarch64 で x86_64 と同じ結果になること。コードの読み取りだけで、実行はしていない。

## 決定

aarch64 を、自動テストの対象に加えない。aarch64 のコードは、ビルドが通ることを前提に書く。aarch64 の動作確認は、実行環境が要ると分かった時点で加える。

aarch64 の実行ファイルを走らせるジョブ(arm64 ランナー、QEMU を含む)は、どのワークフローにも足さない。`ci.yml` の行列も変えない。aarch64 のクロスコンパイルのビルドは、スライス 1j-3 の `dist` が入るまで、機械による検査が無い。

[ADR-0010](0010-ci-cd-and-release-strategy.md) の決定(自動テストは `ubuntu-latest` と `windows-latest` に限り、リリースのターゲットの一覧は ADR-0010 が正)は変わらない。本 ADR は ADR-0010 を置き換えず、2026-10-07 の追記が定めた見直しの結果として、対象に加えないことを記録する。ADR-0010 の本文と追記は書き換えない。

この決定のもとで、aarch64 の実行ファイル(Linux と Windows)は、ビルドが通るが動作確認をしていないものとしてリリースで配る。リリースノートの動作保証の範囲に、この旨を書く(リリースノートはスライス 1j-4 が書く)。README の対応プラットフォームの説明も、この決定に合わせる。

見直しの契機は、計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md) のとおり「必要になったとき」とする。見直すときは、下の選択肢から改めて選ぶ。契機を具体的な条件に直すかは、決めていない。[ADR-0020](0020-repository-visibility-private.md) は、リポジトリを公開に転じる判断が、arm64 ランナーの費用に関する前提を変えるので、そのとき ADR-0010 の見直しもあわせて行うと定めている。この結びつきは変わらない。

検討した選択肢(計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md) の問い2の記録に基づく)。選択の理由は記録していない。以下は各案の長所と短所である。

- `full.yml`(層2、準備完了と `main` への push)に aarch64 Linux のジョブを足し、`zig build test` と `zig build test-scheme` を走らせる。Windows の aarch64 と macOS はビルド保証のまま。
  - 長所: 配る aarch64 Linux の実行ファイルが、一度は動かされる。全コミットの CI に触れないので、費用は層2の頻度に収まる。`tools/check-docs` が固定している `ci.yml` の行列を変えずに済む。
  - 短所: private なので arm64 ランナーの実行分数がプランに計上される。ランナーのラベルと `setup-zig` の対応は未確認で、動かなければ別の案へ戻る。`full.yml` の変更にユーザーの承認が要る。
  - 計画の時点で、勧める案だった。ユーザーは別の案を選んだ。
- 加えない(採用)。
  - 長所: 費用がゼロで、検査ツールも変わらない。
  - 短所: 配る aarch64 の実行ファイルが動かされない。
- 全コミットの CI の行列に加える。
  - 長所: 最も強い保証。
  - 短所: 毎コミットの分数がかかる。`tools/check-docs` が固定している行列の値の意味を決め直す必要がある。
- `ubuntu-latest` で QEMU のユーザーモードエミュレーションを使い、aarch64 のテスト実行ファイルを動かす。
  - 長所: arm64 ランナーが要らない。
  - 短所: エミュレーションは実機ではない。`qemu-user` の導入手順が要る。上の「確かめられなかったこと」のとおり、動作を確かめていない。
- リリース時だけ、作った実行ファイルの煙試験を arm64 ランナーで行う。
  - 長所: 実行の回数が最小である。
  - 短所: テスト本体を動かさない。ジョブ間の成果物の受け渡し(`needs` とダウンロード)が要る。

## 結果

- メリット: 費用がかからず、検査ツール・`ci.yml`・`full.yml` を変えずに済む。
- デメリット・受け入れたトレードオフ: aarch64 固有の不具合は、自動では検出されない。リリースで配る aarch64 の Linux と Windows の実行ファイルは、一度も実行されないまま届く。利用者の報告に依存する。macOS の x86_64 と aarch64 は、ADR-0010 のとおり引き続き動作保証の対象外である。上で挙げたアライメント・ポインタ幅に関わる箇所は、wasm32 の往復テストが 32 ビットの幅を通すだけで、aarch64 では確かめていない。
- 将来の見直し条件: 動作確認が必要になったとき。そのとき、ADR-0010 と本 ADR をあわせて見直し、本 ADR を非推奨にして新しい ADR を書き、上の選択肢から選ぶ。リポジトリを公開に転じる判断をするときも、[ADR-0020](0020-repository-visibility-private.md) の定めに従い、ADR-0010 とあわせて見直す。
