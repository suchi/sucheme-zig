# ADR-0003: 非移動型の精密マーク・スイープGCを採用する

- ステータス: 採用
- 日付: 2026-10-04

> 2026-10-10 追記: GC を走らせる位置は、スライス 1g で [ADR-0031](0031-gc-at-machine-step-boundaries.md) が確保の内部から機械のステップの境目に変えた。本ADRの決定のうち、精密・非移動型・マーク・スイープであること、確保が `heap.zig` の API を通ること、確保量が閾値を超えたときに動作することは変わらない。変わるのは、GC が確保の内部で走らないこと、それに伴って一時ルートと `GCを起動しうる` の規約が、ステップの境目でしか GC が走らない間は要らないことである。
>
> 2026-10-15 追記: 決定のうちルート集合の一覧は、段階2のスライス 2b で、境目で持つルートの一覧を [ADR-0035](0035-stage-2-gc-roots-and-raise-reserve.md) が定めたので、その範囲では現在の一覧と合わない([ADR-0031](0031-gc-at-machine-step-boundaries.md) の 2026-10-13 の追記が、ADR-0031 の一覧について同じことを述べている)。GC が境目でしか走らないので、本文の一覧にある一時ルートスタックと展開器の作業状態は、境目で空であり、ルートにならない。境目で持つルートは、機械のレジスタ(環境、継続、値、動的点)と `Context` のルートの表である。精密・非移動型・マーク・スイープであることは変わらない。現在のルートの一覧は [runtime.md](../design/runtime.md) のルート集合の節と ADR-0035 が正である。

## 背景

Scheme は明示的な解放を持たない言語であり、循環構造を作れるため参照カウントでは不十分である。REPL が長時間稼働するため、確保したまま解放しない方式も採れない。

GC の選択肢と制約は次のとおりだった。

- 保守的スタック走査を伴うマーク・スイープ: ルート登録が不要で実装が楽。しかし WebAssembly では関数ローカル変数が線形メモリ上に存在せず走査できない。ネイティブと WASM で GC の正しさが変わってしまう。
- 移動型のコピーGC: 断片化しない。ただしポインタが収集で無効になるため、Zig 側が保持する生ポインタをすべてハンドル経由にする必要があり、コードが読みにくくなる。
- 非移動型の精密マーク・スイープ: ルートの明示管理が必要。ポインタは収集後も有効。

本プロジェクトは WebAssembly を一級の対象とするため、保守的走査は選べない。

## 決定

非移動型の精密マーク・スイープGCを採用する。停止型で、確保量が閾値を超えたときに動作する。

ルート集合は、CEK機械の4レジスタ、動的状態のリスト、グローバル環境、一時ルートスタック、展開器の作業状態とする。機械の状態が少数のレジスタに集約されていることが、精密GCを現実的にしている([ADR-0004](0004-cek-machine-evaluator.md))。

一時ルートはスコープ単位の枠で登録する。非移動型なので登録は到達可能性の保証のみを意味し、呼び出し側のローカル変数を書き換える必要がない。

確保は `src/heap.zig` の API 経由のみに限る。確保を行う関数はドキュメンテーションコメントの先頭に `GCを起動しうる` と書く。

## 結果

- メリット: WASM とネイティブで同じ正しさを持つ。生ポインタが有効なままなのでコードが読みやすく、ルート登録の意味が単純(到達可能性のみ)。
- デメリット・受け入れたトレードオフ: ルート登録の漏れがメモリ破壊を招く。登録漏れはコンパイラでは検出できないため、レビューとストレステストで守る必要がある。断片化が起きる。スイープが全オブジェクト走査になる。
- 将来の見直し条件: 断片化または停止時間が問題になった場合、世代別GCまたは領域ごとの管理を検討する。移動型への変更はアクセサとルート管理の前提を変えるため、その時点で改めてADRを書く。
