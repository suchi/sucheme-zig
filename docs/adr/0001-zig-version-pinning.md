# ADR-0001: Zig 0.17.0 への固定と API ノートの整備

- ステータス: 採用
- 日付: 2026-10-04

## 背景

Zig は1.0前であり、リリースごとに標準ライブラリとビルドシステムの破壊的変更がある。0.17.0 は2026-10-01リリースで、`pub fn main` のシグネチャ、`std.io` から `std.Io` への移行、`std.fs` の大部分の `std.Io.Dir` への移動、コレクションの非管理型化、ビルドシステムの構成器と実行器の分離など、広範な変更を含む。

本プロジェクトは実装フェーズを複数のモデル(Sonnet・Haiku)と複数のセッションに分割して進める。モデルの学習データには0.17.0の情報がほとんど含まれていないため、古い記法を書いてしまう危険が高い。

選択肢は次の3つだった。

- 0.17.0 に固定する。最新で、次の破壊的変更までの猶予が最も長い。情報が少ない。
- 0.16.0 に固定する。2026-04-13リリースで情報が比較的多い。いずれ移行コストを払う。
- 0.15.2 に固定する。情報は最も多いが、移行コストを2回払うことになる。

## 決定

Zig 0.17.0 に固定する。バージョンは `.zigversion` と `build.zig.zon` の `minimum_zig_version` と CI のワークフローの3箇所に記録し、常に一致させる。

情報不足への対策として次を行う。

- `docs/design/zig-api-notes.md` に、実機で動作を確認した記法を記録する。確認済みと未確認を区別して書く。実装前に必ず読む。
- 標準ライブラリのソースを一次情報とする。手元の `lib/std/` を読んで確認する。解説記事を根拠にしない。
- `zig build test` と `zig fmt --check` を全コミットの通過条件にする。古い記法はコンパイルエラーになるため、小さなコミットに分けていれば誤りが局所に留まる。

## 結果

- メリット: 次の破壊的変更までの猶予が最長になる。実機検証済みのノートを持つことで、情報の少なさを埋められる。ノートは他のモデルやセッションへの引き継ぎ資料にもなる。
- デメリット・受け入れたトレードオフ: 実装時に API の調べ直しが頻発する。コミュニティの事例が少ない。ZLS など周辺ツールの対応が追いついていない可能性がある。
- 将来の見直し条件: 0.18.0 のリリース後、安定したと判断できた時点で移行を検討する。移行は専用の PR で行い、`docs/design/zig-api-notes.md` の更新手順に従う。
