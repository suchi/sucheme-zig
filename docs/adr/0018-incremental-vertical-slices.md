# ADR-0018: 通しで動く縦切りを積み上げ、やり残しを明示して漸進的に進める

- ステータス: 採用
- 日付: 2026-10-05

## 背景

設計フェーズの成果物に対して、外部のレビューサービスと自前の敵対的レビューを繰り返した。巡ごとの指摘数と行数の推移は [docs/review/adversarial-review-baseline.md](../review/adversarial-review-baseline.md) にある。件数を本ADRに書かないのは、真実の源を重複させないためである。

観測された事実は3つである。自前レビューの巡ごとの指摘数が下降しないこと、各巡の指摘の大半が直前の巡で書いた修正文そのものの欠陥であること、設計ドキュメントの行数が増え続けていることである。

原因は、コードを1行も書かないまま完全な仕様書を作ろうとしたことである。書けば書くほど検証されない主張が増え、主張が増えるほど矛盾の機会が増えた。

一方、設計を薄くして実装で構造体を決める進め方も採れない。構造体は複数のモジュールにまたがるため、実装の中で個別に決めると全体としての整合性を確認する機会がなくなる。整合性の確認が設計の存在理由である。実例として、値表現とGCのルート集合と継続の表現は互いに依存しており、1つを変えると他の2つが影響を受ける。これを実装中に個別に決めると、後の段階で大きな作り直しになる。

詳細に入りすぎることの害も具体的である。設計が実装の完全な写しになると、実装が単なる変換作業になり、実装から得られる発見がなくなる。動くものを通しで作って初めて分かる問題(性能、使いにくさ、仕様の解釈の誤り)を、設計の段階では見つけられない。

## 決定

次の3つを同時に行う。

### 1. 全体整合性に必要な範囲で詳細設計する

構造体とインタフェースのうち、複数のモジュールにまたがるものは設計時に決める。これは実装前に整合性を確認するためである。

| 設計時に決めるもの | 理由 |
| --- | --- |
| 値の表現と種類の集合 | 全モジュールが使う。GCの走査、プリンタ、プリミティブが依存する |
| ヒープオブジェクトの共通部分 | GCの走査とスイープが依存する |
| GCのルート集合と計上の対象 | 全モジュールの確保が依存する |
| 機械の状態と継続フレームの種類 | 評価の全経路が依存する |
| 動的状態の表現 | `dynamic-wind`、例外、`parameterize` の3つが依存する |
| 構文環境と識別子の表現 | 衛生性の全体が依存する |
| WASM の ABI | 独立に実装される2つの側が依存する |
| ライブラリのエクスポート表 | ライブラリシステムと展開器が依存する |

これ以外は実装時に決める。1つのモジュールに閉じたデータ構造、補助関数のシグネチャ、内部のアルゴリズムの選択、バッファの大きさがこれにあたる。

設計ドキュメントには、設計時に決めたものを書く。実装時に決めるものは「実装時に決める」と明示し、何を根拠に決めるかを書く。

### 2. 通しで動く縦切りを積み上げる

段階ごとに、リーダからプリンタまで、ネイティブとブラウザの両方で通しで動く状態を作る。層を1つずつ完成させる進め方(リーダを完全に作ってから評価器に進む)は採らない。

縦切りにすることで、各段階の終わりに動くものがあり、設計の誤りを動作で発見できる。層ごとに進めると、最後に結合するまで誤りが見つからない。

段階1は意図的に小さくする。10進整数と記号と基本的な手続き呼び出しだけで、`(define (fact n) ...)` が動く状態を目標にする。この時点で値表現、ヒープ、GC、機械、リーダ、プリンタ、REPL、WASM、Web UI、CI がすべて最小の形で揃う。以降の段階はこの縦切りを太らせる作業になる。

### 3. やり残しを明示する

各段階の終わりに「この段階で確定したこと」と「次の段階以降に残していること」を記録する。残していることには、どの段階までに決めるかを書く。

未確定事項の一覧は [docs/design/open-questions.md](../design/open-questions.md) に1箇所だけ置く。各設計ドキュメントは自分の領域の未確定事項をそこへのリンクで示し、内容を複製しない。

完璧を目指さない。次の段階または最終段階までにやり残していることが明確であれば、設計はその段階として十分である。

## 結果

- メリット: 全体整合性の確認という設計の役目を果たしつつ、実装を早く始められる。各段階の終わりに動くものがあり、設計の誤りを動作で発見できる。未確定事項が1箇所に集まるため、別の環境やセッションで作業を引き継ぐときに「何が決まっていて何が決まっていないか」が分かる。設計ドキュメントの規模が制御される。
- デメリット・受け入れたトレードオフ: 縦切りにすると、後の段階で前の段階の実装を書き換えることがある。値表現に種類を足すたびに全モジュールの `switch` を触る。層ごとに進める方式より総作業量は増えうる。未確定事項を明示する作業そのものに手間がかかる。
- 将来の見直し条件: 縦切りの結果、ある段階で前の段階の設計を根本から覆す必要が出た場合、その原因が「設計時に決めるべきだったものを実装時に回した」ことにあるのかを分析して記録する。該当するなら上の表に項目を足す。

## レビューの停止規則への影響

[ADR-0017](0017-self-hosted-adversarial-review.md) の停止規則は「新規指摘ゼロ」を要求し、収束は検出器の調整で行うと定めていた。本ADRはそこに2つの選択肢を加える。

1つは、散文で書いた主張をコンパイラとテストが検査する形に移すことである。実装時に決めると明示した部分は、設計ドキュメントのレビュー対象から外れ、コードのレビュー対象になる。

もう1つは、指摘を未確定事項として記録して次の段階に回すことである。設計の誤りは直すが、「この詳細が未規定である」という指摘のうち実装時に決めると定めたものは、[open-questions.md](../design/open-questions.md) に記録して閉じる。記録せずに閉じることはしない。

基準を下げるのではなく、主張の置き場所と決定の時期を変える。
