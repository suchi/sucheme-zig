# ADR-0002: Scheme値は Zig のタグ付き union で表現する

- ステータス: 採用
- 日付: 2026-10-04

## 背景

Scheme の値表現は、処理系全体の読みやすさと性能を左右する。主な選択肢は次の3つだった。

- Zig のタグ付き union(16バイト)。即値はインライン、複合型はポインタ。
- パックドワード(8バイト)。下位ビットをタグに使い、fixnum は61ビットの即値、ポインタは整列を利用する。
- NaN ボクシング(8バイト)。`f64` の NaN 空間に他の型を詰める。

性能だけを見ればパックドワードか NaN ボクシングが有利である。一方、本プロジェクトは実装を複数のモデルとセッションに分割するため、誤りがコンパイル時に検出される構造を重視する必要がある。

## 決定

Zig のタグ付き union を採用する。即値(空リスト、未規定値、EOF、真偽値、fixnum、flonum、文字、シンボルID)はインラインに持ち、複合型は GC ヒープ上のオブジェクトへのポインタとして持つ。

表現の詳細に依存するコードは `src/value.zig` に閉じ、他モジュールはアクセサ関数を経由する。これにより、性能測定の結果に基づいて後からパックドワードへ差し替える余地を残す。

全ヒープオブジェクトは先頭に共通ヘッダ(種別タグ、マーク、全オブジェクトのリンクリスト)を持つ。GC は `Value` のタグを知らない状態でオブジェクトを辿るため、`Value` のタグとヘッダの種別タグは冗長に併存させる。対応表は `value.zig` に1箇所だけ置く。

## 結果

- メリット: `switch` の網羅性検査が効く。型を追加したときに修正が必要な箇所をコンパイラが列挙する。デバッガでの観察が容易。アクセサ経由にすることで差し替え可能性を保てる。
- デメリット・受け入れたトレードオフ: 8バイト表現に比べてメモリ使用量が倍になり、キャッシュ効率が落ちる。`Value` のタグとヘッダの種別タグが二重管理になる。
- 将来の見直し条件: 準拠テストが通った後に性能を測定し、値表現が支配的なボトルネックであると判明した場合にパックドワードへの移行を検討する。アクセサ境界が守られていることが移行の前提になる。
