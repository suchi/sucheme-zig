# ADR-0034: リリースは ReleaseSafe の成果物を下書きで作り、チェックサムだけを付けて配る

- ステータス: 採用
- 日付: 2026-10-12

> 2026-10-12 追記: 背景の「`release.yml` はまだ無い」は、スライス 1j-3c で当てはまらなくなった。`release.yml` は、タグ `v*` の push で、`dist` と `package.py` のあとに、実行ファイルの `--version` がタグと一致すること、`docs/releases/<タグ>.md` があることを確かめ、`gh release create --draft --verify-tag` で下書きを作る。リリースノートは、ファイルが無いと組み立ての前に失敗する。`--prerelease` は付けない。タグの名前は、`run:` の行に式として埋め込まず、環境変数で渡す。決定は変わらない。
>
> 2026-10-13 追記: 決定の「リハーサルとして `main` への push と準備完了のたびに走らせる」のうち、`main` への push では走らなくなった。`full.yml` の起動は、PR を ready にしたときと手動だけである([ADR-0036](0036-windows-tests-in-the-slow-tier.md))。リハーサルの目的(タグを打つ前に、組み立てが通っていることを確かめる)は、ready のときの `dist` ジョブと、タグの push で走る `release.yml` が果たす。決定そのものは変わらない。

## 背景

[ADR-0010](0010-ci-cd-and-release-strategy.md) は、タグ `v*` の push で全ターゲットをクロスコンパイルし、チェックサム、リリースノート、成果物を付けると決めた。ターゲットの一覧も ADR-0010 が正である。一方で、最適化モード、成果物の中身、公開の手順、チェックサムの扱い、第三者の表示は決めていない。スライス 1j(計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md))でリリース v0.1.0 を出すにあたり、これらを決める必要がある。

この ADR が決めるのは形である。実装は PR を分けている。成果物の組み立て(`zig build dist`、`tools/release/package.py`、`THIRD-PARTY-NOTICES.txt`、`full.yml` のリハーサル)は 1j-3a で入る。タグから下書きのリリースを作る `release.yml` は別の PR で入る。この ADR を書いた時点で、`release.yml` はまだ無い。

計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md) の「確かめた事実と、確かめられなかったこと」の表のうち、この決定に関わるものは次のとおりである。

- 確かめた: ADR-0010 の一覧の全ターゲットで `zig build -Dtarget=<t> -Doptimize=ReleaseSafe` が成功する。x86_64 Linux の成果物は `--version` に答え、`(fact 10)` に `3628800` を返す。Linux の成果物は静的リンクで、strip されていない。Windows のビルドは `.exe` の隣に `.pdb` を作る。
- 確かめられなかった: GitHub のドキュメントの記述全般(ホストランナーに `gh` が入っていること、成果物の attestation が private で使えるかを含む)。静的リンクした Zig の標準ライブラリと musl の MIT の表示義務が、成果物の配布で生じるか(法的な判断)。Windows と macOS の成果物の実機での実行。

## 決定

### 最適化モードは ReleaseSafe に固定する

`zig build dist` は、すべてのターゲットを `ReleaseSafe` で作る。`-Doptimize` では変わらない。`test-scheme` と wasm が使っている設定と同じなので、動かして確かめた設定を配ることになる。パニックは安全検査で止まり、未定義動作にならない。`ReleaseFast` より遅く、ファイルが大きいと推測している(測定していない。性能の測定は段階6)。

### 成果物の中身と組み立て

- ターゲットごとのアーカイブ: Linux と macOS は `tar.gz`、Windows は `zip`。名前は `sucheme-v<版>-<ターゲット>.<拡張子>`。中身は `sucheme-v<版>-<ターゲット>/` の下の、実行ファイルと `LICENSE` と `THIRD-PARTY-NOTICES.txt` である。`.pdb` は入れない。strip はしない(パニックの追跡を残す)。
- Web UI の zip: `sucheme-web-v<版>.zip`。`web/` の中身と `sucheme.wasm` と、上の2つの表示のファイルを、`sucheme-web-v<版>/` の下の同じ階層に並べる。展開した先で `node serve.mjs .` と打てば開ける。
- チェックサム: `SHA256SUMS` を1つ。`sha256sum -c SHA256SUMS` で確かめる。
- 組み立て: `zig build dist` が `zig-out/dist/<ターゲット>/` に全ターゲットを作り、`tools/release/package.py`(Python の標準ライブラリだけ)がアーカイブと `SHA256SUMS` を作って、アーカイブを開き直して確かめる。ターゲットの一覧は `build.zig` の `dist` だけが持ち、`package.py` はディレクトリ名から導く。
- 再現性: 順序は名前順、時刻・権限・所有者は固定する。同じ入力から同じバイト列ができる。ただし gzip と deflate の出力は zlib の版に依存するので、バイト単位の一致を約束するのは同じ Python の環境の中だけである。異なる環境で作ったアーカイブのチェックサムが一致することは、約束しない。
- 同じ2つの手順(`dist` と `package.py`)を、`full.yml` のジョブがリハーサルとして `main` への push と準備完了のたびに走らせる。タグを打つ前に、組み立てが通っていることを確かめるためである。

### 公開は下書きから、チェックサムのみ、`gh` で作る

- リリースは下書き(draft)で作り、ユーザーが成果物を開いて確かめてから公開する。
- 付けるのは `SHA256SUMS` だけである。attestation と署名は行わない。チェックサムは成果物と同じ経路で配るので、破損と取り違えには効くが、改ざんには効かない。attestation は `id-token` と `attestations` の権限が要り、private で使えるかも確かめられていない。
- リリースの作成は、ホストランナーの `gh` と `GITHUB_TOKEN` で行う。サードパーティのアクションは足さない([ADR-0021](0021-no-github-pages-defer-hosting.md) の「段階7までシークレットを増やさない」に従う)。権限は `contents: write` だけである。ホストランナーに `gh` が入っていることは、確かめられていない。

### 第三者の表示

各アーカイブに `THIRD-PARTY-NOTICES.txt` を入れる。内容は、Zig の `LICENSE` と、Linux の成果物が使う musl の `COPYRIGHT` の、Zig 0.17.0 のツールチェーンからの写しである。写しはリポジトリにコミットし、リリース時にツールチェーンから取り出さない。表示の義務が成果物の配布で生じるかは法的な判断で確認できないので、義務が生じる解釈に立っても満たされる側に倒した。[ADR-0022](0022-unlicensed-proprietary.md) が、リリース成果物を渡す経路があるので表示の記載を維持すると定めていることとも合う。

Zig の版を上げる([ADR-0001](0001-zig-version-pinning.md))たびに、この写しを新しいツールチェーンの該当ファイルと見比べ、必要なら更新する。写しが現在の Zig の版のものかは機械では見られない([ADR-0026](0026-verify-facts-about-code-not-prose.md))ので、Zig の版を上げる PR で人が見直す。

### 検討した選択肢

計画 [0009](../plans/0009-slice-1j-release-v0-1-0.md) の問い7から9の記録に基づく。選択の理由は、計画に書かれたものを除いて記録していない。

- 最適化モード
  - `ReleaseSafe`(採用): 上のとおり。
  - `ReleaseFast`: 速いが、安全検査が無い。
  - `ReleaseSmall`: wasm のサイズ測定(段階4)の前に選ぶ根拠が無い。
- 組み立ての手段
  - `dist` と `package.py`(採用): ローカルでも再現できる。順序・時刻・権限を固定でき、実行ビットを確実に残せる。`run:` を1行に収める制約に合う。`tools/` に Python のスクリプトが増える。
  - ワークフローのシェルの1行ずつ: ターゲットの一覧が `build.zig` とワークフローの2箇所に要る。ローカルで再現しにくい。
  - アーカイブまで Zig で書く: zip を書く標準ライブラリの手段を確認していない。
  - ターゲットごとのジョブの行列: ADR-0010 の「1ジョブ」から外れる。
- 公開の形
  - 下書きで作り、確認して公開(採用): 公開の前に成果物を実際に開ける。ユーザーの手作業が1回増える。
  - 自動で公開: 最初のリリースで誤りに気づく前に公開される。
  - `--generate-notes` による自動生成: PR の題名が英語で、動作保証の範囲などが入らない。
  - サードパーティのリリース用アクション: 供給連鎖の面が増える。
  - attestation: 上のとおり、権限が要り、private で使えるか確かめられていない。
- 第三者の表示
  - `THIRD-PARTY-NOTICES.txt` を入れる(採用): 義務が生じる解釈に立っても満たされる。費用が小さい。
  - 入れない: 義務が生じる解釈だった場合に満たさない。
  - 法務の確認を先に求める: v0.1.0 が待たされる。

アーカイブの中身を `sucheme-v<版>-<ターゲット>/` の下に置くことは、計画に書かれていない選択である。選択の理由は記録していない。

## 結果

- メリット: 動かして確かめた設定の実行ファイルを配れる。組み立てがローカルとリハーサルで同じ手順になる。公開の前に成果物を確認できる。サードパーティのアクションと新しいシークレットが増えない。
- デメリット・受け入れたトレードオフ: `ReleaseFast` より遅く、ファイルが大きい(推測)。チェックサムは改ざんに効かない。ユーザーの手作業が1回増える。Zig の版を上げるたびに `THIRD-PARTY-NOTICES.txt` の写しを人が見直す必要があり、機械では見られない。`dist` のターゲットの一覧と ADR-0010 の一覧が一致していることは、機械では見ていない。アーカイブのバイト単位の一致は、同じ Python の環境の中でだけ約束する。Windows と macOS の成果物は、実機で実行して確かめていない。aarch64 の成果物は ADR-0033 のとおり、実行して確かめていないまま届く。
- 将来の見直し条件: 公開に転じるとき(ADR-0020 とあわせて、attestation や署名を再検討する)。Zig の版を上げるとき(表示の写しを見直す)。性能の測定(段階6)で最適化モードを見直す必要が出たとき。
