# ADR-0049: 行編集は Zig で自前に作り、最小の核から先に組み込む

- ステータス: 採用
- 日付: 2026-11-12

## 背景

[ADR-0014](0014-repl-line-editor-boundary.md) は、行編集の実装方式(自前の Zig か、C のライブラリの取り込みか)を段階7に送り、段階7の開始時に選択肢とトレードオフを示して判断を得ることを、見直し条件にした。

[計画書 0021](../plans/0021-stage7-8-early-parts.md) の「行編集の実装方式」で、候補の C ライブラリ(linenoise、isocline、bestline、replxx)を比較した。2026-10-20 に、ユーザーが、勧める案(Zig で自前に作る)を承認した。決定が ADR に記録されていなかったので、ここに記録する。

その後、2026-11-12 に、作る順序についても判断があった。0021 は、部品 7a から 7j をそろえてから、最後の 7j で REPL に組み込む前提だった。この順序では、組み込みの完了まで、REPL の入力に編集機能が届かない。REPL を使ってテストする作業では、編集機能の不在が、いまの最大の障害になっている。

## 決定

1. 行編集は、Zig で自前に作る。GNU Readline など、外部のライブラリは使わない。理由は、計画書 0021 の勧める案に書いたとおりである。確かめた候補のうち、Windows、複数行、キルリングを含む Emacs の割り当ての3つを、README ですべて確かめられたものが無かった。完結判定を共有する形([ADR-0014](0014-repl-line-editor-boundary.md) の決定の第2項)を、自前なら確実に作れる。依存が増えず、`zig build dist` の全ターゲットへ C をクロスビルドする確認が要らない。
2. 最小の核を先に作り、REPL に組み込む。核に入れるものは次のとおり。
   - POSIX の生モード(7h)、キー列の解読(7a)、編集バッファ(7b)、キルリングと取り消し(7c)、記憶上の履歴(7d)、文字幅の境界(7f。仮の実装)、単一行の再描画(7g)、`LineReader` の union と `src/main.zig` の REPL への組み込み(7j)。
   - キー割り当ては Emacs の標準を含める。Ctrl-A、E、B、F、K、U、W、Y、T、D、P、N、R、Alt-B、F、D、矢印、Home、End、Delete、Ctrl-_ による取り消し。
   - `Enter` で `sucheme.isIncomplete` を呼び、閉じていなければ継続行に進む。完結判定を `dumb` と `rich` で共有する ADR-0014 の決定は、変えない。
3. 次のものは、核のあとに、スライスごとに組み込む。括弧の対応表示(7e)、複数行をまたぐカーソルの上下移動と複数行の再描画(7m)、識別子の補完(7k)、差分読み取り(7l)、履歴のファイルへの保存(7n)、Windows の生モード(7i)、文字幅の表の差し替え。
4. 核の間、Windows では `dumb`(いまの素朴な行読み取り)のままにする。端末でない入力(パイプ、ファイル)は、どの OS でも `dumb` を使う。
5. 核の再描画は、折り返しに依らない形にする。端末の幅を超える行は、横にずらして表示する(カーソルを上へ戻す操作を使わない)。これは、複数行の再描画を後に回すための設計である。

検討した別案と、採らなかった理由:

- 部品 7a から 7j をすべてそろえてから組み込む案(0021 の元の順序)。組み込みまで利用者に何も届かず、端末の癖への対応を、実機で試す機会が遅れる。
- C のライブラリを取り込む案。上のとおり、自前の案より確かめられた条件が少なく、依存と C のクロスビルドの確認が増える。

## 結果

- メリット: 編集と履歴が、複数行の編集と括弧の表示より先に使える。端末の癖(生モードの復帰、キー列の途中切れ)を、小さい範囲で先に確かめられる。後から足す部品が、`LineReader` の `rich` の側に、スライスごとに入る。
- デメリット・受け入れたトレードオフ:
  - 核の間、`Enter` で式が閉じていないときは、入力済みの行を確定して、継続行のプロンプトに進む。確定した前の行は、カーソルで戻って編集できない。複数行をまたぐ編集は 7m で入る。
  - 複数行の項目も履歴に記録するが、核の間は、上下の移動で呼び出せるのは、1行の項目だけである。
  - 文字幅は、仮の実装(符号位置が制御文字なら0、それ以外は1)なので、全角の文字を含む行で、カーソルの位置がずれる。
  - Windows では、核の間、行の編集ができない。
  - 作る量が多く、端末の癖への対応を自分で負う(自前の案を選んだことの帰結)。
- 将来の見直し条件: 7h の実機確認で、端末の癖が、自前の範囲に収まらないと分かったとき。核のあと、7m、7e、7i の作業量が見込みを大きく超えたとき。そのときは、ユーザーに判断を諮り、新しい ADR で記録する。
