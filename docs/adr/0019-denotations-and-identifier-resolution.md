# ADR-0019: 衛生性は構文環境と別名による改名で実現し、意味は6種とする

## 背景

ADR-0005 は衛生性の実現方式として構文環境と別名による改名を選んだ。方式の選択は妥当であり、本ADRもそれを引き継ぐ。

一方、同ADRが決定として書いた細部に3つの誤りがあった。6巡目の敵対的レビューで検出した([round6-findings.md](../review/round6-findings.md) の FE4、FE5、FE7、および前の巡で検出した局所束縛の表現)。

第1に、意味を5種(特殊形式、マクロ、局所変数の字句アドレス、グローバルセル、パターン変数)と列挙したが、R7RS 付録A は `(scheme base)` のエクスポートに `...` `=>` `_` `else` `unquote` `unquote-splicing` の6個を含めており、R7RS 4.2.1 と 4.3.2 はこれらを auxiliary syntax として項目化している。これらは式に変換されないので特殊形式ではなく、変換子を持たないのでマクロでもない。5種のどれにも当てはまらない。

第2に、局所変数の意味を字句アドレス(深さと添字の組)としたが、深さは利用側からの相対値なので、別々の字句環境にある無関係な束縛が同じ組になる。意味の同一性をその組で判定すると `syntax-rules` のリテラル照合が壊れる。

第3に、識別子の解決の最終段を「グローバル環境を引く」としたが、グローバル環境が処理系全体で1つだと、インポートしていないライブラリの定義が見えてしまう。R7RS 5.1 は「The initial environment of a program is empty, so at least one import declaration is needed to introduce initial bindings」と規定している。

## 決定

構文環境と別名による改名方式を採る。ADR-0005 からの変更点は3つである。

### 意味は6種とする

| 意味 | 内容 |
| --- | --- |
| 特殊形式 | コアIRに直接変換する構文 |
| マクロ | 変換子とその定義環境 |
| 補助構文 | それ自身では式にならず、他の構文のパターンリテラルとしてのみ現れる識別子 |
| 局所束縛 | 束縛ごとに1つ確保する独立したオブジェクト |
| グローバルセル | ライブラリまたは REPL のトップレベルの束縛 |
| パターン変数 | `syntax-rules` の展開中にのみ現れる |

補助構文を独立した意味にするのは、エクスポートとインポートとリテラル照合の3つを同じ仕組みで通すためである。採りえた代替案は、6個を「常に構文エラーを送出する変換子を持つマクロ」として登録することだった。リテラル照合は変換子オブジェクトの同一性で通るので機能はするが、「マクロだが展開できない」という実体に合わない分類が残る。R7RS が auxiliary syntax として項目化している概念をそのまま写すほうが、仕様との対応を検査しやすい。

意味を与えないと3つが同時に壊れる。`(import (only (scheme base) cond else))` がエクスポート表に `else` の行を作れない。`cond` のリテラル `else` の照合が識別子が未束縛であることに依存し、ライブラリごとに独立したグローバル環境を持つ設計では壊れる。ライブラリ本体の `(define else 5)` を拒否できない。

### 局所束縛は独立したオブジェクトとし、同一性はオブジェクトの同一性で判定する

字句アドレスは意味ではなくコアIRの表現とする。利用側の構文環境の深さから束縛を導入した rib の深さを引いて求める。

### グローバル環境はライブラリごと、および REPL ごとに独立とする

識別子の解決は、現在の構文環境を同一性で検索し、見つからなければ別名の内側の識別子をその別名の環境で解決し、最後にその環境が属するライブラリのグローバル環境を引く。内側の識別子を渡すことで1回の委譲ごとに別名の層が1つ減り、有限回で停止する。別名自身を渡すと停止しない。

同一性の一致は2つの識別子の間の関係とし、両方が素のシンボルで名前が一致する場合と、両方が別名で内側と印と環境が一致する場合にのみ成立させる。片方の種類で場合分けして「素のシンボルなら名前の一致」を適用してはならない。適用するとマクロが導入した別名の束縛を利用側の同名の素のシンボルが引き当て、衛生性が壊れる。

### ADR-0005 から引き継ぐこと

- 識別子は素のシンボルか別名である。別名は内側の識別子、解決すべき環境、同一展開を区別する印の3つを持つ。内側の識別子は素のシンボルかさらに外側の展開由来の別名である。
- `syntax-rules` のリテラル照合は意味の一致で判定する。
- `quote` の中に現れた別名は、コアIRの定数にする時点で元のシンボルに戻す。
- `syntax-rules` の照合器とテンプレート展開器は Zig で実装する。構文環境を操作するAPIを Scheme に公開すると、実質的に `syntax-case` 相当の非標準拡張を設計し維持することになるため採らない。
- 派生構文は Scheme 側で `syntax-rules` を使って定義する。`parameterize` はパラメータオブジェクトの表現の選択によりコアの構文として Zig 側に置く([ADR-0006](0006-library-system-and-scheme-level-stdlib.md))。

詳細は [design/frontend.md](../design/frontend.md) の構文環境と識別子にある。

## 結果

- メリット: `(scheme base)` のエクスポート一覧を1つの仕組みで覆える。リテラル照合が識別子の未束縛性に依存しなくなるため、ライブラリ隔離と両立する。局所束縛の同一性がオブジェクトの同一性になり、相対値による誤判定がなくなる。
- デメリット・受け入れたトレードオフ: 意味の種類が1つ増えるため、意味を分岐するすべての箇所に補助構文の分岐が増える。グローバル環境をライブラリごとに持つため、ライブラリ数に比例した表が必要になる。
- 将来の見直し条件: 手続き的マクロを提供する要求が出た場合、印と置換の方式への移行を検討する。その場合は本ADRを非推奨にして新ADRを書く。
