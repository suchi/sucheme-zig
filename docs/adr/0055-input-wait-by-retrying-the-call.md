# ADR-0055: 入力待ちは、何も消費しない読み取りを機械が保存して、入力が届いてからやり直す

- ステータス: 採用
- 日付: 2026-11-22

スライス 8f-1([plans/0030-phase8-web-ui.md](../plans/0030-phase8-web-ui.md) の決定3)の設計である。計画書の合意で、方式(読み取りが「入力待ち」を返し、機械が呼び出しを保存して制御を戻し、入力が届いたら同じ呼び出しをやり直す)は決まっている。この ADR は、GC のルート、ヒープの上限への計上、再開の正しさについて、実装で選んだ細部を記録する。

## 背景

ブラウザには、標準入力を読む口が無い。ホストが入力を渡し、`(read)`、`(read-line)`、`(read-char)` が、その入力を受け取る。[ADR-0053](0053-resumable-machine-step-budget.md) で、機械は `step` で制御を戻して再開できるようになり、`Outcome.needs_input` の型だけが入った。この ADR は、それを返す側と、再開の意味を決める。

## 決定

1. 入力の置き場。ホストが渡したバイト列で、まだ読まれていないものと、終端を受け取ったかどうかを、`HostInput`(`src/host_input.zig`)が持つ。`Interpreter` が1つ持ち、評価をまたいで残す。評価の間だけ `Heap.console_host` が指す。コンソールの入力ポートは、これが指されていれば、`console_input`(ネイティブの読み手)より先にここから読む。
2. 待ちの判断。ホストの入力を読み切っていて、終端も無ければ、`port.fill` は `error.WouldWait` を返す(読み切って終端があれば、従来どおり「終わり」の `false`)。`WouldWait` は `PrimitiveError` にも入る。条件にならず、Scheme の例外にもならない。
3. 何も消費しない約束。`WouldWait` を返すプリミティブは、返す前に何も消費しない。1文字だけ読む `read-char`、`peek-char` は、読む前に確かめるので満たす。複数回に分けて読む `read-line` と `read-string` は、読み進めると、途中で待ったときに読んだ分が失われる。そこで、読み始める前に、渡された分で終えられるか(行の終わり、`k` 文字、または終端)を、位置を動かさずに確かめる(`awaitText`)。`read` は、データが閉じるまで何も消費しない作りである(先頭の空白は、バッファが埋まったときにだけ読み飛ばす。ホストの入力は埋まらない)。`char-ready?` は、待たずに、手元に1文字あるか終端のときだけ真を返す。バイナリの読み取りは、コンソールの入力ポートが textual なので、コンソールには届かない。
4. 機械の保存。`Machine.apply` が `WouldWait` を受けたら、同じ呼び出し(引数の鎖と個数)を、継続の先頭の `spread` のフレーム(回収後の呼び直しと同じ形。`retryAfterCollection`)に載せ、`error.NeedsInput` で `step` まで戻す。`step` が、レジスタを `Context.parked` に写して `needs_input` を返す。再開は、`step` をもう一度呼ぶだけで、フレームが同じ呼び出しをやり直す。継続として保存しないので、機械の保存する状態は増えない。
5. GC のルート。待っている間の GC のルートは、`Context` の表と `Context.parked`(レジスタ)である。待った呼び出しの引数の鎖は、継続の先頭のフレームが指すので、`parked.kont` から辿れる。ストレスモードで、待つたびに GC して、確かめる。
6. 待てない実行。入れ子の実行(ライブラリの本体、`environment` の輸入集合)と `evalPrint`(完了まで回す層)は、制御を戻せない。`Machine.suspendable` を、`stepEval` が始める機械にだけ立て、立っていない機械の待つ読み取りは、`cannot wait for input in <名前> here` という Scheme の誤りにする(`guard` で捕まえられる)。待ちが `Machine.run` の `unreachable` に届かないようにするためである。
7. 計上。`HostInput` の領域は、ヒープの常駐の割り当て器(`Heap.residentAllocator`)から取り、`Heap.resident` に数える。上限に収まらない入力は、`HeapLimit` で断り、持っているものを変えない。読み終えた分は、残りの先頭へ詰めてから足し、全部読み終えると、領域を手放す。入力の大きさに比例する領域を、次の入力まで持ち越さない。
8. 終端。終端を受け取った後に渡した入力は捨てる。終端のあとの読み取りは、(手元に残りがあればそれを読み切ってから)すべて終端のオブジェクトを返す。終端は、評価をまたいで、`sucheme_reset` まで残る。
9. WASM の境界。`sucheme_provide_input(ptr, len)` と `sucheme_provide_eof()` を足す。どちらも、読み取りが待っているとき(直前の `sucheme_step` が 2 を返したとき)だけ受け取り、そうでなければ `-4` で状態を変えない。`sucheme_provide_input` は、`-8`、`-3` の順に検査し、保持できなければ `-1`(評価は捨て、定義は残る)を返す。成功は 1 で、続きは `sucheme_step` が進める。待っている間に `sucheme_step` を呼んでも害は無く(待っている読み取りをやり直し、入力が無ければまた 2 を返す)、`sucheme_abort` で評価を捨てられる。

## 結果

- メリット: 継続を保存しないので、機械の状態は増えず、GC のルートと計上は、既存の仕組み(`parked`、常駐の計上)に載る。ネイティブの挙動は変わらない(`Heap.console_host` は null)。
- デメリット・受け入れたトレードオフ:
  - 複数回に分けて読む読み取りは、渡された分で終えられるまで、何も読まずに待つ。`(read-string 100)` は、100 文字か終端が届くまで、手元の分も読まずに待つ。対話では、改行まで届く `read-line` が自然に動く。
  - `read` は、データが続くかもしれない末尾のトークン(`abc`)を、閉じる文字か空白が届くまで待つ。
  - 待つ読み取りがやり直すたびに、手元の分を数え直す。1回あたりの量は、渡された入力の大きさに比例するが、待つたびに起きるだけで、1歩の費用は変わらない。
  - 全体の計算量は、手元の分を数え直すので、入力の量の2乗になりうる。1バイトずつ渡すホストや、改行の無い長い行、大きな `k` の `read-string` がこれに当たる。8f-2 の画面は、1行ずつ渡す。1行ごとに待ちが起きるので、改行の無い長い行や大きな `read-string` の数え直しの影響は残る。独立レビューで、5MB の1行が約0.4秒で通ったと報告された(私は測り直していない)。直すのは、このスライスの範囲外である。
  - `sucheme_provide_input` は、1回の呼び出しごとに UTF-8 の妥当性を検査し(検査は、待っているかの確認より先)、文字が2回にまたがる入力を `-3` で断る。待っていないときに不正な入力を渡しても、`-4` でなく `-3` になる。`web/sucheme.js` は文字列全体を符号化するので通常は起きないが、バイト列を分割して渡すホストは、末尾の不完全なバイトを次の呼び出しに持ち越す必要がある。
  - ヒープの上限で `sucheme_provide_input` が `-1` になると、評価は捨てられるが、保持済みの入力は残り、計上されたままである。ホストが読み捨てる手段は無い(次の評価の読み取りが読むか、`sucheme_reset` で消える)。実害は確かめていない。
  - 入れ子の実行の中では、待てず、誤りになる(ライブラリの本体で入力を読む場合)。
- 将来の見直し条件: 入れ子の実行を中断できるようにするとき。バイナリのコンソール入力を足すとき(`read-u8` が待つ必要が出る)。ネイティブにも、待ちながら続ける読み手を足すとき。
