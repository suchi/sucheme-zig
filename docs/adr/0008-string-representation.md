# ADR-0008: 文字列は UTF-8 バイト列と ASCII 判定フラグで表現する

- ステータス: 採用
- 日付: 2026-10-04

## 背景

R7RS の文字は Unicode スカラ値であり(6.6)、文字列は可変である(`string-set!`)。表現の選択肢は次の2つだった。

- UTF-32 の配列: `string-ref` と `string-set!` が定数時間。1文字4バイト。入出力のたびに UTF-8 との変換が必要。
- UTF-8 のバイト列: 入出力と変換が不要。`string-ref` が文字数に比例する。幅の変わる `string-set!` で再確保が必要。

本プロジェクトではポートの入出力と WASM のホスト境界の両方で UTF-8 を使う。

## 決定

UTF-8 バイト列として保持し、全文字が ASCII かどうかのフラグを併せ持つ。ASCII のみの場合、`string-ref` と `string-set!` は定数時間になる。

R7RS は `string-ref` の計算量を規定していないため、非 ASCII 文字列での走査は準拠上の問題にならない。

幅の変わる `string-set!` はバイト列の再確保を伴う。バイト列は GC ヒープ外のアロケータから確保し、sweep 時に解放する。バイト列の大きさはヒープ上限の計上に含める([runtime.md](../design/runtime.md) の計上の対象)。`(make-string 1000000)` の繰り返しで上限が効かなくなることを防ぐ。

`string-upcase` などの完全大文字小文字写像は文字数を変えうるため、長さが変わる前提で実装する。

## 結果

- メリット: ポートと WASM の境界で変換が不要になる。実用上ほとんどの文字列は ASCII のみであり、その場合は定数時間アクセスになる。メモリ使用量が UTF-32 の4分の1から同等に収まる。
- デメリット・受け入れたトレードオフ: 非 ASCII 文字列に対する添字アクセスが文字数に比例する。`string-set!` の実装が複雑になる。文字数とバイト数の2つの長さを管理する必要がある。
- 将来の見直し条件: 非 ASCII 文字列に対する添字アクセスが実際の利用で問題になった場合、直近アクセス位置のキャッシュを持たせるか、非 ASCII 文字列のみ UTF-32 で持つ二重表現を検討する。
