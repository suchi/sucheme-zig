# ADR-0011: GitHub Pages は gh-pages ブランチ方式とし、PRごとのプレビューを配置する

- ステータス: 採用
- 日付: 2026-10-04

## 背景

要件として、リリース時の正式版だけでなく PR 時にも Web UI を試せる状態が求められている。

GitHub Pages の配信元には2つの方式がある。

- GitHub Actions 方式(`actions/deploy-pages`): サイト全体を1つの成果物として配置する。同時に複数のバージョンを置けないため、PRごとのプレビューを作れない。
- ブランチ方式: `gh-pages` のようなブランチの内容を配信する。ディレクトリを分ければ複数のバージョンを同時に置ける。

外部のホスティングサービスを使う方式は、シークレットの管理が増えるため採らない。

## 決定

`gh-pages` ブランチ方式を採用する。配置の構成は次のとおり。

| パス | 内容 |
| --- | --- |
| `/` | 最新リリースの Web UI |
| `/main/` | main ブランチの最新 |
| `/pr/<番号>/` | PR ごとのプレビュー |

PR のプレビューを配置したら、その URL を PR にコメントする。PR が閉じられたら該当ディレクトリを削除する。

フォークからの PR ではプレビューを配置しない。`gh-pages` への書き込み権限を伴う処理をフォークの変更に対して実行しないためである。該当する場合は CI の成果物(zip)を添付し、PR にその旨をコメントする。`pull_request_target` は使わない。

## 結果

- メリット: PR ごとに実際に動く URL が得られ、レビューで挙動を確認できる。リリース版と main と PR を同時に参照できる。シークレットの管理が増えない。
- デメリット・受け入れたトレードオフ: `gh-pages` ブランチの履歴が成果物のコミットで膨らむ。フォークからの PR ではライブプレビューが得られない。`actions/deploy-pages` を使う一般的な構成から外れるため、設定を自前で管理する必要がある。
- 将来の見直し条件: `gh-pages` の履歴が問題になった場合、定期的に履歴を切り捨てる運用を導入する。GitHub Pages が複数デプロイを公式に支援するようになった場合、Actions 方式への移行を検討する。
