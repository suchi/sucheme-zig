# ADR-0035: 段階2の GC のルートと境目を決め、条件オブジェクトを予約領域つきでヒープに置く

- ステータス: 採用
- 日付: 2026-10-13
- 一部置き換え: [ADR-0031: gc-at-machine-step-boundaries](0031-gc-at-machine-step-boundaries.md) の決定のうち、ルートの一覧、境目の一覧、条件オブジェクトをヒープの外のアリーナに作ることを置き換える。GC を確保の内部で走らせず境目でだけ走らせること、一時ルートの規約が要らないこと、ストレスモードは ADR-0031 のまま変わらない

## 背景

[ADR-0031](0031-gc-at-machine-step-boundaries.md) は、GC を機械のステップの境目と、`Interpreter` が1行の中の各フォームを読む前でだけ走らせると決めた。そのうえで、ルートを3つ(機械のレジスタのうち環境・継続・値、大域環境の値、コードの定数)に限り、条件オブジェクトをヒープに置かずに上限の外のアリーナに作るとした。見直し条件には、ハンドラと `guard` が入る段階2で条件オブジェクトをヒープに置き、送出のための予約領域([runtime.md](../design/runtime.md))を実装するときを挙げていた。追記は、1行の長さで抑えられない読み取りが入るときも見直すとしている。

段階2の計画([0014](../plans/0014-phase2-core-language.md))は、ADR-0031 の文面の外にあるものを足す。

- ルート: 動的点のレジスタ(2d)、送出された値 `Context.raised`(2b)、REPL の最上位の表(2i。マクロの束縛も入る。大域環境の一部として挙げる)、ライブラリの登録表と各ライブラリの環境(2m)、読み込みの作業リスト(2m、2n)。
- 境目: ライブラリと `include` のファイルの、フォームの間(2n)。ファイルを読むので、1行の長さで抑えられない。
- 条件オブジェクトのヒープ化と予約領域(2b)。

ルートと境目は ADR-0031 の決定の本文に列挙されているので、足すことは決定を変えることである。各スライスの追記で足していくと、ADR が実際にしていない決定を書いている期間ができる。そのため、段階2で入るものを、後のスライスの分まで含めてここで決める(計画書の合意を求める点の4)。

条件オブジェクトをアリーナに作る形は、段階1では行を打ち切るだけだったので足りた。段階2ではハンドラが条件を受け取り、持ち続けられる。アリーナにあると回収されず、エラーのたびにセッションの終わりまで残る。またアリーナの条件はヒープの値(irritant)を指せない。

## 決定

GC が走る境目は次の3つとする。どれも、持っている値がレジスタと `Context` のルートの表のものだけになる点である。

- 機械のステップの先頭。
- `Interpreter` が1行の中の各フォームを読む前。
- ライブラリと `include` のファイルのフォームを読む前(2n で入る)。ファイルの1つのフォームの読み取りの中では GC は走らない。読み取りの大きさは、そのフォームの大きさで抑えられる。

境目で持っているルートは次の2群とする。

- 機械のレジスタ: 環境、継続、値。2d から動的点。
- `Context` のルートの表(`Context.mark` が挙げるもの): 大域環境の値(REPL の最上位の表を含む。2i)、ライブラリの登録表と各ライブラリの環境(2m)、コードの定数、読み込みの作業リスト(2m、2n)、送出された値 `Context.raised`(2b)。

機械の実行をまたいでヒープの値を持つものは、すべて `Context` のルートの表に入れる。展開器は機械の実行をまたいで状態を持たない。ライブラリは、読む、展開する、機械で本体を走らせる、の順に1つずつ処理する(計画書の合意を求める点の4)。一時ルートと `GCを起動しうる` の規約は、ADR-0031 のとおり要らない。

送出された値 `Context.raised` は `Value` とし、条件オブジェクトに限らない(R7RS 6.11)。`Interpreter.evalPrint` は失敗の時点でそれを文字列に整形し、ヒープと呼び出しのアリーナの外のバッファに置く。`raised` は次の行の始めに空にするまでヒープを指すので、ルートに入れる。

条件オブジェクトは GC ヒープに置く。種別(R7RS 6.11 の述語に対応する `error` `read` `file`)、メッセージの文字列、irritant のリストを持つ。

上限に達していても送出できるよう、送出のための予約領域を置く。予約は計上を別に持たず、確保地点に上限を超えることを許す幅とする。予約から確保してよい地点は [runtime.md](../design/runtime.md) の必要量の表の地点で、地点が `heap.zig` の `Budget.raise_reserve` を選ぶ。その地点は、計上量が上限に予約の大きさを足した値を超えない限り確保できる。ほかの確保は上限を超えられない。確保したものは同じ計上に入り、同じスイープで回収される。メモリを初期化時に別に取っておくことはしない。2b で予約を使う地点は条件とそのメッセージだけで、初期の大きさは 4 KiB とする。2d と 2e が自分の地点を足し、2e が大きさを決める。

予約も尽きたときは、条件を作らずに Zig の `error.ReserveExhausted` を返し、`raised` を空のままにする。Scheme のエラーとして送出されないので、ハンドラを経ずにその行が終わる。診断は `heap limit exceeded` である。ヒープの `error.HeapLimit` とは別の名前にし、`Context` の失敗の集合にはヒープの `HeapLimit` を入れない。ヒープの確保の失敗を素の `try` で返すとコンパイルエラーになり、`heapFailure` で送出に写すことを型が強いるためである。

選ばなかった案は次のとおりである。

- ADR-0031 への追記で、各スライスが自分のルートと境目を足していく案。ADR が増えない。しかしルートと境目は決定の本文の列挙なので、追記で足すと、決定を変えたのに決定が変わっていない形の記録になる。
- 予約を別の計上にし、予約から確保したものを予約の側で数える案。[runtime.md](../design/runtime.md) の予約領域の節の書き方に最も近い。しかしハンドラが受け取った条件をリストに集めるプログラムでは、生きている条件が予約を埋め続け、ヒープに余裕があるのに予約が尽きて回復不能になる。条件は利用者が持ち続けられる値なので、この使い方は正当である。
- 予約を初期化時にメモリとして確保しておく案。ホストのメモリが尽きたときにも送出できる。しかし計上の上限はホストのメモリより十分小さく(`heap.max_host_limit`)、上限に達した時点でホストには予約の分の余裕がある。ホストのメモリが尽きるのは、上限超過とは別の `OutOfMemory` の経路である。
- 予約が尽きたとき、別に用意しておいた条件を送出する案。上限に達していても必ず Scheme のエラーにできる。しかしその条件を最初から持ち続けるルートが要り、尽きたことを区別できなくなる。runtime.md は予約の枯渇を回復不能として区別すると決めている。

## 結果

- メリット: 段階2で GC のルートと境目が増えても、ADR が実際の決定と一致し続ける。登録漏れの類型は、引き続き `Context.mark` と機械の境目の2か所に集まる。条件オブジェクトはエラーのたびに回収され、セッションの長さに比例して残らない。上限に達した状態でも、型エラーや `heap limit exceeded` の条件を作れる。
- デメリット・受け入れたトレードオフ: 計上量とその最大値(`Heap.peak`)は、上限を予約の分だけ超えうる。上限は、通常の確保に対する上限になる。予約の大きさは 2e で決まるまで仮の値である。名前を含むメッセージ(`unbound variable: ...`)は名前の長さだけ長くなる。条件とメッセージを作ると計上量が上限と予約の和を超えるときは、本来のメッセージでなく `heap limit exceeded` で行が終わる。上限の近くでは予約より短いメッセージでも起き、空のヒープでも、メッセージが上限と予約の和より長ければ起きる。ライブラリのファイルの1つのフォームが大きいとき、その読み取りの間は GC が走らない。
- 将来の見直し条件: 1つのステップや1つのフォームの読み取りの中で大きく確保する必要が出たとき(ADR-0031 の見直し条件と同じ)。段階2より後で、ここに無いルートや境目が要るとき。予約を測った結果、メッセージの長さに比例する分を予約で賄えないと分かったとき。
