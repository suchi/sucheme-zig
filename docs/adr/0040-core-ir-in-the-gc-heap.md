# ADR-0040: コアIRの節点を GC ヒープに置き、最上位の表を常に上限に数え、未束縛のセルを弱く持つ

- ステータス: 採用
- 日付: 2026-10-20
- 一部置き換え: [ADR-0031: gc-at-machine-step-boundaries](0031-gc-at-machine-step-boundaries.md) のルートの「コードの定数」と、[ADR-0035: stage-2-gc-roots-and-raise-reserve](0035-stage-2-gc-roots-and-raise-reserve.md) の境目で持っているルートの一覧(機械のレジスタに制御を加え、`Context` のルートの表からコードの定数を外す)を置き換える。GC を境目でだけ走らせること、境目の一覧、予約領域は変わらない

## 背景

段階2までの実装は、コアIRの節点を `Context.persist` の永続アリーナに置いた。GC は節点を辿らないので、節点が指すヒープの値(`quote` したデータ、シンボルの定数、局所変数の名前)を `Context.code_roots` に挙げ、節点が指しうるセルを、表から外れても持ち続けてきた(`env.Global.displaced_cells`、定義に失敗したライブラリの表)。[ADR-0031](0031-gc-at-machine-step-boundaries.md) は、ルートの1つとしてこの表を挙げ、「コードをヒープに移すスライスで要らなくなる」とした。

この形の帰結として、上限の外の確保と、回収されない保持が、ADR-0031 の追記に積み重なった。

- `quote` したデータと、失敗した展開の節点が、セッションの終わりまで残る(2026-10-10、2026-10-14 の追記)。
- `include` が読んだファイルから作る節点が、行をまたいで上限の外に残る(2026-10-15 の追記(2))。
- ライブラリごとの最上位の表が、上限の外の永続アリーナで、インポートした名前の数だけ伸びる(2026-10-15 の追記)。

REPL で解決した未知の名前は、未束縛のセルとして表に残り、回収されない([design/open-questions.md](../design/open-questions.md))。

構文環境(`SyntacticEnv` など)、別名、マクロ、ライブラリ、エクスポート、セルは、すでに GC ヒープにある。残るのは、節点と、最上位の束縛の表(`env.Global`)である。

## 決定

1. コアIRの節点 `Node`、`Lambda`、`Parameterize` を GC ヒープの型(`value.zig` の `heap_types`)にする。節点1つがオブジェクト1つである。節点の列(`sequence`、呼び出しのオペランド、`parameterize` の束縛)は、所有する節点のペイロードとして数え、節点と一緒に返す。
2. 継続のフレームと機械のレジスタは、節点の部分(`If` など)や部分スライスでなく、節点を指す。機械のルートに制御のレジスタを加える。ADR-0031 と [ADR-0035](0035-stage-2-gc-roots-and-raise-reserve.md) のルートの一覧のうち、「コードの定数」(`Context.code_roots`)を外し、「制御」を加える。
3. 展開器は、節点をヒープから上限つきで確保する。展開の途中では GC が走らない(ADR-0031 は変えない)ので、作りかけの節点を登録しない。展開が返した根の節点は、機械の最初のステップの前に制御のレジスタに置く。機械の実行をまたいで、節点を Zig の局所変数に持たない。
4. 最上位の束縛の表(REPL とライブラリごとの `env.Global`)とライブラリの登録表は、ヒープの上限に常に数える(`Heap` の常駐の計上)。下の割り当て器は、個別に解放できるものにする。`import` の作業領域は、展開の作業領域と同じく、その間だけ数える。表の共有(インポートごとの複製をやめること)は、この ADR では決めない。
5. コードから辿れるセルは、コードが持つ。表から外れたセルを持ち続ける保持(`displaced_cells`、定義に失敗したライブラリの表)をやめる。
6. 最上位の表は、自分の未束縛のセルを弱く持つ。GC は、マークの後、掃除の前に、マークされなかった未束縛のセルの束縛を表から外す。

## 結果

- メリット: `code_roots` が無くなり、ルートの一覧が機械のレジスタと文脈の表だけになる。到達できないコードと、その定数は回収される。失敗した展開の節点、`include` の節点、ライブラリの表、REPL の未束縛のセルが、上限に数えられるか回収される。上限を超える入力は、ほかの確保と同じ `heap limit exceeded` で終わる。
- デメリット・受け入れるトレードオフ: GC のたびに、生きているコードをマークする。初期化で読み込む `(scheme base)` のコードは常に生きているので、GC の時間と、ストレスモードの時間が伸びる。節点ごとにヘッダと個別の確保が要り、初期化の時間とメモリが増える。どれだけ増えるかは、実装のスライスで測る(この ADR の時点では未測定)。表を上限に数えるので、初期化に要る上限の最小値が上がる。
- 将来の見直し条件: GC の時間が、初期化で読み込んだコードのマークに支配されるとき(固定の仕組みを検討する)。インポートごとの表の複製が、上限の大部分を占めるとき(表の共有を検討する。[plans/0017-parallel-lanes.md](../plans/0017-parallel-lanes.md) の層2の測定の結果を待つ)。展開の途中で GC を走らせる設計に変えるとき(作りかけの節点の登録が要る)。

## 選ばなかった案

- 最上位の形式の展開の結果を1つのコードの塊にし、その中に節点をアリーナで置く案。確保とヘッダは減るが、クロージャ、継続のフレーム、制御のレジスタのそれぞれに塊への所有者のポインタが要り、塊の一部が生きていれば全体が残る。
- 節点を永続アリーナに置いたまま、アリーナの全体を上限に数える案。回収されないので、失敗した展開と到達できないコードの残り方は変わらず、上限が実効的に縮むだけである。
- 未束縛のセルの数に上限を置く案。上限の値に根拠が無く、上限に達したときの振る舞いを新しく決める必要がある。
