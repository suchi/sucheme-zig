## 解こうとしている問題

いまのリポジトリの文書は、開発者に向けたもの(設計、ADR、計画書、[onboarding.md](../onboarding.md))だけである。sucheme を使う人が読む文書が無い。`sucheme --help` は、言語の中身を説明しない。

利用者向けの文書には、コードの例が多数入る。人の目で確かめた例は、インタプリタの変更で黙って古くなる。たとえば、いまの REPL は `(scheme base)` だけを見るので、`display` は `(import (scheme write))` の後でしか使えない。`write` は段階5のスライス 5j まで無い。こうした事情を知らずに書いた例は、読者の手元で動かない。逆に、後のスライスが出力の形を変えれば、正しかった例が誤りになる。

そこで、文書の中のコードと期待する出力を、検証コマンドとして毎コミットで走らせる。文書を書くことより先に、この検査の仕組みを作る。

## 完了条件

4種類の文書それぞれについて、何がそろえば完了かを書く。どの文書も、日本語で書く([AGENTS.md](../../AGENTS.md) の言語ルール)。

- 共通: 文書の中の Scheme のコードブロックと、プログラム集のファイルが、すべて検査の対象になっている。検査は全コミットの CI で走り、緑である。検査の外に置いたコードブロックが、文書の置き場所に1つも無い(検査がそれを断る。下の「検査の仕組み」)。
- チュートリアル: 下の章立ての章のうち、その時点の main で動く機能の章がすべてある。各章は、例と練習問題(答えつき)を持ち、例と答えはすべて検査を通る。まだ動かない機能の章は、前提のスライスのマージのあとに足す(「実装の到達点との関係」の表)。段階8の完了の時点で、表のすべての章がある。
- ユーザーズガイド: 実行ファイルの引数、REPL、ファイルの実行、ライブラリの探索(`-I`)、エラーと終了コード、Web UI の使い方、既知の制限の章がある。コマンドの例(引数と終了コード)も検査を通る。終了コードの契約は [src/main.zig](../../src/main.zig) の doc コメントが正なので、ガイドは表を写さず、その doc コメントにリンクし、例の実行で確かめる(合意を求める点の4)。
- リファレンスマニュアル: `import` できる R7RS のライブラリ(`(scheme ...)`)が輸出するすべての識別子と、sucheme に固有の利用者向けの機能に、項目がある。各項目は、形式、説明、少なくとも1つの例を持ち、例は検査を通る。項目と輸出の一覧の対応は、機械で確かめる(合意を求める点の5)。後のスライスが識別子を足したら、そのスライスの PR か、直後の L9 のスライスで項目を足す。
- プログラム集: 下の候補のうち、その時点で動く機能のものが、それぞれ1つの `.scm` と期待する標準出力のファイルの組として置かれ、実行ファイルで走らせた結果が一致する。

## 実装の到達点との関係

2026-10-29 に、main の `79346c7` を `zig build` で作った実行ファイルで、短い式を走らせて確かめた。確かめていない動作は、動くと書かない。

確かめた事実:

- REPL とファイルの実行の初期環境は `(scheme base)` である。`display` は `(import (scheme write))` のあとで使える。`(scheme write)` は、いまは `display` だけを輸出する(`write` は 5j)。
- `import` できるライブラリは、`(scheme base)` `(scheme write)` `(scheme inexact)` `(scheme complex)` `(scheme lazy)` `(scheme case-lambda)` `(scheme cxr)` である。`(scheme char)` `(scheme read)` `(scheme file)` `(scheme process-context)` `(scheme time)` `(scheme eval)` は `error: unknown library` になる。1つの `import` に読めないライブラリが混じると、その `import` 全体が誤りになる。
- 数は、bignum(`(fact 30)`)、有理数(`(/ 1 3)` が `1/3`)、浮動小数点数、複素数(`(sqrt -4)` が `+2i`)が動く。`exact->inexact` は `(scheme base)` に無い(R7RS では `(scheme r5rs)` の名前で、段階5の 5q)。
- 文字列ポート(`open-input-string`、`open-output-string`)、`define-record-type`、`call/cc`、`guard`、`error-object-message`、`parameterize`、`syntax-rules`、`let-values`、`case-lambda`、`delay` と `force`(`(scheme lazy)`)、末尾呼び出しの 100 万回のループと、末尾でない 10 万段の再帰が動く。
- `-I <dir>` で、利用者の `define-library` のファイルを読める(`(mylib greet)` を `mylib/greet.sld` に置いて確かめた)。
- ファイルの実行は、実行時エラーで `error: ` を標準エラーに出して終了コード 1、読めないファイルで 66、標準入力のプログラム(`-` だけ)で 69 を返した。
- `(string-upcase "abc")` と `(char-upcase #\a)` は `unbound variable` になる(`(scheme char)` は PR suchi/sucheme-zig#209 で作業中)。

確かめていないこと: Web UI(WASM)で同じ式を走らせたときの出力。[web/samples.mjs](../../web/samples.mjs) のサンプルが期待どおりに動くことは、[tools/test-wasm/main.mjs](../../tools/test-wasm/main.mjs) が CI で確かめているが、この計画書を書く間に、私は `test-wasm` を走らせていない。

## 検査の仕組み

この計画書の中心である。文書のコードを2種類に分け、それぞれを機械で走らせる。

1. 文書の中のコードブロック(チュートリアル、ユーザーズガイド、リファレンス)。
2. プログラム集の `.scm` ファイル。

### 既存の道具の再利用

既存の道具を読んで、次を確かめた。

- [tools/test-scheme/main.zig](../../tools/test-scheme/main.zig) は、`sucheme.Interpreter.evalPrint` をプロセスの中で呼び、REPL と同じ形の出力(値ごとに改行、誤りは `error: ` とメッセージ)を作って、期待するテキストと比べる。ケースごとに新しいインタプリタを作る。期待する出力の書き方(`<no output>`、`error: `)は、そのまま文書の期待する出力の書き方に使える。
- [tools/check-docs/main.zig](../../tools/check-docs/main.zig) は、リポジトリのすべての `.md` を歩き、CommonMark のフェンスを開閉の規則どおりに読んで、相対リンクを検査する。利用者向けの文書を `.md` で書けば、リンクの検査は何もしなくても効く。
- [tools/test-wasm/main.mjs](../../tools/test-wasm/main.mjs) は、Web UI のサンプルを、識別子ごとの期待する出力と比べている。プログラム集を Web UI のサンプルとつなぐときの前例になる。
- [build.zig](../../build.zig) は、実行ファイルを走らせる run を作れる(規模を試す層の `tests/cli-slow/`)。ただし、標準出力を検査する run は終了コードを読まなくなるので、`build.zig` 自身の検査(`checkRunIsHeard`)が断る。

結論: 新しい道具 `tools/check-examples/` を作る。評価の部分は、`test-scheme` と同じく `evalPrint` をプロセスの中で呼ぶ形を写す。`test-scheme` を部品に分けて共有する案は、他のレーンの所有するファイルを変えるので採らない(合意を求める点の3)。フェンスの読み取りは、`check-docs` の規則を参考に、必要な部分集合だけを書く。

### コードブロックの記法

[CommonMark](https://spec.commonmark.org/0.31.2/#fenced-code-blocks) の情報文字列(フェンスの後ろの語)で、ブロックの種類を表す。GitHub は最初の語で色付けをするので、後ろに語を足しても、表示は Scheme のままである(この点は、GitHub の表示で確かめていない。未確認)。

````markdown
```scheme
(define (square x) (* x x))
(square 12)
```

```output
144
```
````

規則は次のとおりである。

- `scheme` で始まる情報文字列のブロックは、すべて走らせる。直後(空行だけを挟んでよい)に `output` のブロックがあれば、出力をそれと比べる。無ければ、出力が空で、誤りも出ないことを求める。定義だけのブロックを、期待する出力なしで書けるようにするためで、検査の外に出るわけではない。
- 期待する出力の書き方は、`test-scheme` と同じである。値は REPL と同じ形で1行ずつ、`display` などの出力は書いた順に、誤りは `error: ` とメッセージで書く。誤りを見せる例も、期待する出力として固定する。
- 同じ `.md` ファイルの中のブロックは、1つのインタプリタで、上から順に走る。前のブロックの定義を、後ろのブロックが使える。チュートリアルが章の中で定義を積み上げるためである。
- `scheme fresh` のブロックは、新しいインタプリタで走り、以降のブロックはその状態を引き継ぐ。リファレンスの項目ごとに、前の項目の定義の影響を切るために使う。
- 形式を示すだけの、走らせない断片(`(if <test> <consequent> <alternate>)` のような文法の型)は、`text` のブロックに書く。`scheme` のブロックには書かない。
- 文書の置き場所(下の「置き場所」)の中では、情報文字列の無いフェンス、知らない情報文字列(`scheme`、`output`、`text`、`console` 以外)、行頭から書かれていない `scheme` のフェンス(リストの中に字下げしたもの)を、誤りとして報告する。読み違えて検査の外に出るブロックを、黙って残さないためである。字下げしたフェンスを断るのは、CommonMark のリストの中のフェンスの読み取りを、この道具に実装しないためである。

### コマンドの例(ユーザーズガイド)

ユーザーズガイドは、実行ファイルの引数と終了コードを見せる。これも走らせて確かめる(合意を求める点の4)。

````markdown
```console
$ sucheme hello.scm
Hello, world
```
````

- `console` のブロックの、`$ ` で始まる行は、`sucheme` の実行ファイルの呼び出しに限る。シェルを通さず、引数を空白で区切って、実行ファイルを直接起動する。任意のシェルのコマンドは走らせない(文書の編集が、CI の中で任意のコマンドの実行になるのを避ける)。
- 呼び出しの作業ディレクトリは、文書と同じ場所の `examples/` の下にある、名前を決めたディレクトリとする。`hello.scm` のような入力のファイルは、そこに置く。
- 終了コードが 0 でない例は、出力の後ろに `[exit 66]` の形の行を書く。書かなければ 0 を求める。
- 標準エラーの出力は、標準出力の後ろに続けて比べる(いまは標準エラーへの書き込みの一部が標準出力に出る。5i の既知の制限)。

### プログラム集の形式

- `docs/manual/programs/` に、`名前.scm` と、期待する標準出力 `名前.out` を組で置く。終了コードは 0 を求める。
- 道具は、`build.zig` から実行ファイルのパスを受け取り、各 `.scm` をファイルの実行として起動し、標準出力と終了コードを比べる。プロセスの中で評価せず実行ファイルを使うのは、利用者が実際に打つ経路(引数の処理、出力のバッファ)を通すためである。
- 組になっていないファイル(`.out` の無い `.scm`、逆も)、`.scm` と `.out` でも `.md` でもないファイル、プログラムが1つも無い実行を、失敗とする。`test-scheme` が、ケースを減らしたまま緑になる手口を断っているのと同じ理由である。
- 入力を読むプログラム(段階5の 5l 以降)は、`名前.in` を標準入力に渡す。ファイルを読み書きするもの(5k 以降)は、一時ディレクトリで走らせる。この2つは、前提のスライスのマージのあとに、道具に足す(YAGNI)。

### 検査の性質

- 双方向にする。文書から検査への向き(書いたブロックが走る)に加えて、検査から文書への向きとして、置き場所の中の `.md` のすべてのフェンスを分類し、分類できないものを断る。綴りを1つずつ受け付けて穴を閉じるのではなく、知らないものをすべて断る形にする([AGENTS.md](../../AGENTS.md) の「穴を閉じるとき」)。
- 黙って止まらない。対象の `.md` が無い、ブロックが1つも無い、プログラムが1つも無い実行は失敗とする。引数でディレクトリやフィルタを受け取らない(範囲を狭めたまま緑になるのを避ける。`test-scheme` と同じ)。
- 環境に依らない例だけを書く。`(features)`、時刻、パス、乱数のように、OS や実行のたびに変わる出力は、期待する出力にしない。Windows の層2でも同じ結果になる必要がある。
- 規模を試す例は書かない。どの例も、全コミットの層の時間に収まる大きさにする。

### `zig build` の step と検証コマンドの表

- step の名前は `check-examples` とする(内部の名前なので、勧める名前で進め、PR に書く)。
- 依存: 実行ファイル(`exe`)と、`sucheme` のモジュール。`test-scheme` と同じく、プロセスの中の評価のために `sucheme` を import する。
- [AGENTS.md](../../AGENTS.md) の検証コマンドの表に、「テスト(文書の例)」として、`zig build check-examples` の行を、使える段階 4、CI は全コミット、で足す。
- `build.zig` の `current_stage` 以下の段階の全コミットの行は、`check-docs` が `ci.yml` に要求し、`ci.yml` の各 `run:` 行は `full.yml` の `windows` ジョブにも要る([AGENTS.md](../../AGENTS.md))。したがって、表の行と、2つのワークフローの step は、同じ PR で足す必要がある。ワークフローの変更は、ユーザーの承認が要る(下の「承認を求める点」)。
- 層: 全コミット(層1)で走らせる。文書だけの PR でも層1は走るので、文書の例の誤りは、文書だけの PR でも見つかる。層2には足さない(Windows のジョブには、上の照合の規則で足す)。

### 他のレーンへの影響

検査が全コミットで走ると、インタプリタの出力を変える PR(数の書式、誤りのメッセージ)は、文書の例を赤くする。これは検査の目的どおりだが、他のレーンの PR が、L9 の所有する文書を直すことになる。取り決めを合意を求める点の6に書く。

## 構成案

### チュートリアル

対象の読者は、何か1つ以上のプログラミング言語(C、Python、JavaScript など)を使えるが、Lisp 系の言語は初めての人である。知っている言語との対比で、括弧の構文と、式がすべて値を持つことから入る。

| 章 | 内容 | 前提 |
| --- | --- | --- |
| 1 はじめに | REPL の起動と終了、式を打って値を見る、ファイルの実行 | なし |
| 2 式と前置記法 | 括弧と前置記法、数と算術、比較、真偽値(`#f` だけが偽) | なし |
| 3 定義と束縛 | `define`、`let` と `let*` と `letrec`、`set!` | なし |
| 4 手続き | `lambda`、手続きの定義、可変長の引数、クロージャ | なし |
| 5 条件分岐 | `if`、`cond`、`case`、`and` と `or`、`when` と `unless` | なし |
| 6 リスト | ペアとリスト、`car` と `cdr`、`quote`、リストの手続き、連想リスト | なし |
| 7 再帰と末尾呼び出し | 再帰で考える、末尾呼び出しがループになること、名前つき `let`、`do` | なし |
| 8 高階手続き | `map`、`for-each`、`apply`、手続きを返す手続き、畳み込みを自分で書く | なし |
| 9 文字列と文字 | 文字列と文字のリテラル、比較、部分、変換、文字列ポートで文字列を組み立てる | 大文字小文字の節は 4u3 |
| 10 ベクタとバイトベクタ | 添字で引く、更新、`vector-map`、バイトベクタと UTF-8 | なし |
| 11 数 | 正確な数と不正確な数、bignum と有理数、浮動小数点数、複素数 | なし |
| 12 レコード | `define-record-type` | なし |
| 13 制御 | 多値、`call/cc`、`dynamic-wind` | なし |
| 14 エラーの扱い | `error`、`guard`、`raise`、`with-exception-handler`、エラーオブジェクト | なし |
| 15 構文の定義 | `syntax-rules` と `define-syntax`、衛生性 | なし |
| 16 パラメータと遅延評価 | `make-parameter` と `parameterize`、`delay` と `force` | なし |
| 17 ライブラリ | `import`、`define-library` を書いて `-I` で読む | なし |
| 18 入出力 | `write`、ファイル、`read` | 5j、5k、5l |
| 19 プログラムとして動かす | コマンドラインの引数、`exit`、時間の計測 | 5m、5n |

### リファレンスマニュアル

- 構成は、R7RS のライブラリごとに1ファイル(`scheme-base.md`、`scheme-write.md` など)とし、`(scheme base)` の中は R7RS の章の順(4章の構文、6章の手続きの節)に並べる。R7RS の本文と対照しやすく、輸出の一覧との突き合わせ(下)が、ライブラリ単位で書ける。
- 各項目: 形式(`text` のブロック)、何をするか、引数の型と誤りになる条件、例(`scheme fresh` のブロックと `output`)、R7RS の節番号。
- sucheme に固有のものは、別のファイル `sucheme.md` に分ける。いま利用者から見える固有のものは、`features` の値、`-I` の探索、誤りのメッセージの形である。`(sucheme core)` は、利用者が `import` すると誤りになる。`(sucheme derived)`、`(sucheme procedures)`、`(sucheme test-results)`、`(chibi test)` は、利用者からも `import` できた(2026-10-29 に REPL で確かめた)。これらは標準ライブラリと準拠スイートの部品なので、リファレンスに載せず、輸出の突き合わせ(合意を求める点の5)の対象からも外す(合意を求める点の8)。
- [docs/status/](../status/) の準拠マトリクスとの関係: マトリクスは生成物で、識別子が束縛されるかを示す。リファレンスは手書きで、使い方を示す。リファレンスに件数を書かない(導ける数を2箇所に書かない)。
- 手書きか生成か: 手書きにする。説明と例は生成できない。項目の抜けだけを機械で確かめる(合意を求める点の5)。

## 合意を求める点

勧める案を先に書く。勧める案でよいときは、そう返信する。小さく戻せる選択(章の分け方、ファイルの名前、step の名前)は、ここでは諮らず、PR に書く。

1. 期待する出力の記法。
   - 勧める案: `scheme` のブロックの直後に `output` のブロックを置く(上の「コードブロックの記法」)。
     - メリット: 読者がコードだけをコピーできる。期待する出力の書き方は `test-scheme` と同じで、`display` の出力と値の両方を書ける。
     - デメリット: ブロックが2つになり、文書が縦に長くなる。
   - 別案A: REPL の書き写しの形(`> (+ 1 2)` の次の行に `3`)を1つのブロックに書く。対話の様子がそのまま見えるが、コピーしたコードにプロンプトが混じり、継続行(`... `)の扱いを道具に足すことになる。
   - 別案B: コードの中のコメント(`(+ 1 2) ; => 3`)で書く。短いが、`display` の出力と値を区別できず、誤りの例が書きにくい。
2. 検査の層。
   - 勧める案: 全コミット(層1)で走らせる。
     - メリット: インタプリタの変更で例が壊れたことを、その PR の中で知れる。文書だけの PR でも走る。
     - デメリット: 層1の時間が延びる(D1 で測る)。他のレーンの PR が、文書の例を直す手間を負う(6)。
   - 別案: 層2だけで走らせる。層1は延びないが、文書だけの PR では層2が走らないので、文書の例の誤りが main に入る。
3. 評価の部品を `test-scheme` と共有するか。
   - 勧める案: 共有せず、`evalPrint` を呼ぶ数十行を `tools/check-examples/` に写す。
     - メリット: 他のレーン(L8)の所有する `tools/test-scheme/` に触れない。
     - デメリット: 同じ形のコードが2か所にある。`evalPrint` の誤りの扱いが変わったら、両方を直す。
   - 別案: 評価の部分を共有のモジュール(`tools/common/` など)に出し、両方から使う。重複は消えるが、`test-scheme` の変更になり、L8 との調整が要る。
4. ユーザーズガイドのコマンドの例を走らせるか。
   - 勧める案: 走らせる。`console` のブロックで、`sucheme` の呼び出しだけを、シェルを通さずに起動する(上の「コマンドの例」)。終了コードの表は、ガイドに写さず [src/main.zig](../../src/main.zig) の doc コメントにリンクし、代表の例(0、1、64、66、69)を走らせて見せる。
     - メリット: 引数と終了コードの説明が、契約から黙ってずれない。任意のシェルのコマンドを CI で走らせない。
     - デメリット: 道具が大きくなる(子プロセスの起動と、作業ディレクトリの用意)。D3 で足す。
   - 別案: コマンドの例は走らせず、人が確かめる。道具は小さいが、「載せるコードがすべて動く」の条件から外れる。
5. リファレンスの項目の抜けを機械で確かめるか。
   - 勧める案: 確かめる。`import` できる各ライブラリの輸出の一覧(`lib/scheme/*.sld` を読むか、インタプリタに問い合わせる)と、リファレンスの項目の見出しを、双方向に突き合わせる。D5 で足す。
     - メリット: 後のスライスが識別子を足したときに、項目の書き忘れが CI で分かる。コードについての事実なので、[ADR-0026](../adr/0026-verify-facts-about-code-not-prose.md) の範囲に入る。
     - デメリット: 識別子を足す他のレーンの PR が赤くなる(6 と同じ扱い)。見出しの書き方を決めて守る必要がある。
   - 別案: 確かめない。リファレンスの抜けは、段階の終わりに人が読んで見つける。
6. 他のレーンの PR が文書の例を壊したときの扱い。
   - 勧める案: 出力を変える PR が、同じ PR の中で `docs/manual/` の期待する出力を直す。所有の外への書き込みだが、期待する出力の置き換えに限って、事前に認める。説明の文の書き換えが要るときは、L9 に知らせ、L9 が直す。
     - メリット: main が赤くならない。変更の理由を知る担当が直す。
     - デメリット: 他のレーンの PR の差分に、文書が混じる。
   - 別案: 出力を変える PR は、先に L9 に知らせ、L9 が文書を直す PR を先にマージする。差分は分かれるが、順序の調整が要り、待ちが増える。
7. 文書の言語。
   - 勧める案: 日本語だけで書く([AGENTS.md](../../AGENTS.md) の言語ルールで、`.md` は日本語)。コードの中の識別子と、出力のメッセージは英語のままである。
   - 別案: 英語版も作る。読者は広がるが、検査の対象と執筆の量が2倍になり、言語ルールの例外を決める必要がある。
8. 内部のライブラリ(`(sucheme derived)` など、`import` できるが標準でないもの)の扱い。
   - 勧める案: リファレンスに載せない。ユーザーズガイドの「ライブラリ」の章に、内部の部品で、名前と中身が予告なく変わることを1文で書く。
     - メリット: 利用者が内部の名前に依存しにくい。リファレンスの範囲が R7RS と sucheme 固有のものに限られる。
     - デメリット: `import` できるのに説明の無いライブラリが残る。
   - 別案: `(sucheme core)` と同じく、利用者からの `import` を断るよう、インタプリタを変える。文書の外の設計の変更なので、L0 の判断になる。
