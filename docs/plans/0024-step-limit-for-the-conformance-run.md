- 段階: 6 の完了の前。レーン L5([0017](0017-parallel-lanes.md))。機械の変更は L0 と L3 の所有ファイルに及ぶ(下の「所有と調整」)
- 日付: 2026-10-21
- 状態: 合意済み(2026-10-21)。「合意を求める点」の5項目すべてを、勧める案どおりに承認した。実装は L5 が行い、3o-4 のマージのあと、親のセッションが時期を指示してから始める

## 解こうとしている問題

スライス 6f から、全コミットの CI の `zig build check-report` が、取り込んだ準拠スイートを毎回すべて走らせる。スイートの中の形式が止まらなくなると、今は `ci.yml` のジョブの `timeout-minutes: 20` だけが止める([0020](0020-conformance-harness-early.md) の「節と、インタプリタの単位」)。そのとき次のことが起きる。

- ランナーの分数を 20 分使い切る。
- どの節のどの形式で止まらなくなったかが、出力に出ない。
- 手元では、手で止めるしかない。
- 段階6の完了の時点で `zig build test-conformance` を CI に入れると、同じ弱点が2つの step に広がる。

止まらない形式は、他のレーンの実装の誤りで生まれうる。例えば、末尾位置の判定を誤った `do` や、終わらない `string->number` である。準拠スイートは、まだ通らない手続きを多く使うので、レーンの PR が識別子を足すたびに、新しい形式が評価されるようになる。

この計画は、機械の1ステップごとに数を数え、上限に達したら評価を打ち切る仕組みを入れる。ランナー(`tools/conformance-run`)と準拠マトリクスの生成ツール(`tools/coverage-report`)は、同じプロセスの中でインタプリタを呼ぶ。同じ仕組みが両方に効く。

## 現状の調査

`origin/main`(`4341845`、スライス 3o-3 のマージ)のコードを読んで確かめた。

- 機械のループ: `src/machine.zig` の `Machine.steps` が、`while (true)` で1節点の評価か、1つの継続の適用を繰り返す。ループの先頭で `ctx.heap.shouldCollect()` を見て GC を走らせる。`Machine.run` は、`steps` が `error.Raised` を返したら `handOver` でハンドラに渡し、それ以外の誤りはそのまま返す。
- 誤りの型: `src/context.zig` の `pub const Error = error{ OutOfMemory, Raised, ReserveExhausted }`。`sucheme.Error` はこれを含む和である。`OutOfMemory` と `ReserveExhausted` は、Scheme のハンドラを通らずに `evalPrint` まで戻る。
- 上限の超過(`heap limit exceeded`)は、Scheme の条件として送出され、ハンドラで捕まえられる(`Registers.limit_reported` の注釈)。
- 初期化の選択肢: `Interpreter.initBare` などは `heap.Options` だけを受け取る。機械の選択肢を渡す口は無い。
- 呼び出し側の誤りの扱い:
  - `src/main.zig`(REPL とファイルの実行)と `src/wasm.zig` は、`WriteFailed` などの数個を見て、残りを `else` で扱う。誤りを1つ足しても、網羅の switch で落ちない。
  - `tools/conformance-run/run.zig` は、`Raised` と資源の誤り(`OutOfMemory`、`HeapLimit`、`ReserveExhausted`、`WriteFailed`)以外を、リーダの誤り(読めない)として数える。新しい誤りは、ここで分類を足さないと「読めない」に数えられる。
- 段階8の設計: [runtime.md](../design/runtime.md) の「歩数制限とWASM」と、[platform-and-web.md](../design/platform-and-web.md) の再開可能性は、機械が歩数の制限で制御を呼び出し元に返し、`sucheme_step` で再開する設計を目標として書いている。機械の状態の表には「歩数の残り」の行がある。まだ実装は無い。[0021](0021-stage7-8-early-parts.md) の合意を求める点の3で、再開可能な機械(`sucheme_step`、歩数の制限、入力待ち)は L3 が持つと決まっている。
- マクロの展開: 展開器は機械の外(Zig のループ)で走る。止まらない展開は、この計画の歩数では数えない。入れ子の `lambda` や `let-syntax` を重ねる止まらないマクロは、roadmap の段階3の「マクロの展開の有界化の残り」の (1) で、スライス 3p-2(suchi/sucheme-zig#171)が止めた。展開器が作る構文環境の入れ子の深さ(環境の鎖の長さ)に上限(`src/syntax/expand.zig` の `max_depth`)を置き、超えたら実装制限の誤りにする。この上限は、機械の歩数とは別の仕組みである。入れ子を深くせずに展開が増え続ける形(マクロの適用が再帰的に増える形など)が止まるかは、この計画では確かめていない。

確かめられなかったこと:

- 今のスイートの形式1つあたりの歩数の最大値。上限の値を決めるのに要る(下の「上限の値」で測り方を書く)。
- 1ステップごとに数を減らして比べる費用(下の「費用の測り方」で測る)。
- `steps` が `error.Raised` 以外で抜けたあと、同じインタプリタで次の `evalPrint` を続けてよいか。`OutOfMemory` は今もこの経路を通るが、`dynamic-wind` の `after` を呼ばずに抜けたあとの状態を、どこまで保証しているかは読み切れていない。L0 に確かめる(合意を求める点の3)。

## 設計

### 上限の単位

機械の `steps` のループの1周を1歩と数える。1周は、節点を1つ評価するか、継続のフレームを1つ適用する。

- プリミティブの呼び出しは、中で何をしても1歩である。プリミティブは Zig で書かれ、有限の入力に対して終わるので、止まらない原因にならない(長い文字列の処理は、時間はかかるが終わる)。ただし、機械の外で走る処理は数えない。循環するデータを印字する処理と、マクロの展開がそれに当たり、どちらも止まらないことがある(6h-2 の敵対的レビューで、循環リストを値に返すトップレベルの形式で、ランナーが止まらないことを確かめた)。これらは上限の外に残し、下の「残っていること」に書く(印字は、スライス 5j で止まるようになった。下の「済んだこと」)。
- GC、ハンドラへの受け渡し(`handOver`)、巻き戻しのフレームの起動は、`steps` の周回を通るものだけを数える。`handOver` の中は数えない。
- 数える範囲は、`Machine.run` の1回の呼び出しである。トップレベルの形式1つの評価ごとに、残りを上限の値に戻す。REPL の1行や `evalPrint` の1回でなく形式ごとにするのは、ランナーが形式ごとに `evalPrint` を呼び、形式の長さによらず同じ上限で比べられるからである。

時間の上限にしない理由: ランナーの速さで結果が変わる。CI の生成物(`docs/status/conformance.md`)が、走らせる機械によって変わってはならない。歩数は決定的である。

確保の量を上限にしない理由: 確保をしないループ(`(let loop () (loop))`)を止められない。

### 上限に達したときの誤り

`src/context.zig` の `Error` に `StepLimit` を足し、機械は上限に達したら `error.StepLimit` を返す。Scheme の条件としては送出しない。

- ハンドラで捕まえられない。`(chibi test)` の `test` は、`with-exception-handler` でテストの式が上げた条件を捕まえて記録し、次へ進む(`lib/chibi/test.scm`)。条件として送出すると、テストの中で止まらない式は、記録されたあと、次のテストでまた上限まで回る。`guard` で誤りを握りつぶすループは、上限に達するたびに捕まえて回り続ける。
- `dynamic-wind` の `after` は呼ばない。`OutOfMemory` と同じ扱いである。上限に達した形式の動的状態は捨てる。
- `Interpreter.diagnostic` の文言は `step limit exceeded` にする(`describe` に1行足す)。

### API

```zig
// src/sucheme.zig(L0)
/// Sets the most steps one top-level form may take, or null for no limit.
pub fn setStepLimit(self: *Interpreter, limit: ?u64) void;
```

```zig
// src/context.zig(L0)
pub const Error = error{ OutOfMemory, Raised, ReserveExhausted, StepLimit };

pub const Context = struct {
    // ...
    /// The most steps one run of the machine may take, or null for no limit.
    step_limit: ?u64 = null,
};
```

```zig
// src/machine.zig(L0 と L3)
// Machine.run が ctx.step_limit から残りを作り、steps のループの先頭で減らす。
// 0 になったら error.StepLimit を返す。null のときは数えない。
```

- 既定は null(上限なし)である。REPL、ファイルの実行、WASM の挙動は変わらない。
- 初期化の選択肢(`heap.Options`)には足さない。`heap.Options` はヒープの選択肢で、機械の上限は別の関心である。初期化の署名を変えないので、呼び出し側(`initBare` などを呼ぶ箇所)の差分も出ない。
- 段階8の再開可能な機械(L3)は、同じ残りの数を使い、上限に達したら誤りでなく状態コード 1(続きがある)で制御を返す形に広げられる。この計画はその形を先取りしない。打ち切りだけを入れる(YAGNI)。

### ランナーと生成ツールでの扱い

- `tools/conformance-run/run.zig`: 節ごとのインタプリタを作ったあと、`setStepLimit` で上限を置く。`evalPrint` が `error.StepLimit` を返したら、その形式を「誤り」に数え、詳細を `step limit exceeded` にする。定義の形式なら、今の誤りと同じく `markBroken` で連鎖のもとにする。同じインタプリタで次の形式を続ける(合意を求める点の3の答えによる)。
- 分類の列は増やさない。誤りの列に数え、`zig build test-conformance` の失敗の一覧の詳細で見分ける。列を足すと、生成物(`docs/status/conformance.md`)の形が変わるためである。
- `tools/coverage-report` は `runVendored` を通るので、ランナーと同じ扱いになる。変更は要らない見込みである。

### 上限の値

上限は、ランナーの定数として `run.zig` に置く。値は次の手順で決める。

1. 使い捨ての写しで、機械に歩数を数える一時の計器を入れ、今のスイートを走らせて、形式1つあたりの歩数の最大値を得る。
2. 上限は、その最大値の 100 倍を目安にする。他のレーンが手続きを足して、今は評価されない形式が評価されるようになっても、正当な形式が上限に当たらない余裕を取る。値と根拠は、定数の `Why:` コメントに書く。
3. 上限に当たった正当な形式が見つかったら、その形式の歩数を測って、上限を上げる。上限に当たると「誤り」に数えられ、`check-report` が赤になるので、黙って見逃されない。

時間の目安: 今のスイートは、全体をランナーだけで走らせて約 78 ミリ秒だった(計画書 0020 の 6f の測定)。上限まで回る形式1つが何秒かかるかは、上の1で測った1歩あたりの時間から見積もり、PR に書く。

### 費用の測り方

1ステップごとに残りを減らして比べる費用を、次のとおり測る。

- 対象: `ReleaseSafe` でビルドした `sucheme` で、(a) 末尾呼び出しのループ 1000 万回、(b) `fib` の 27(非末尾の再帰)、(c) 準拠スイート全体(ランナー)の3つ。
- 比べるもの: `origin/main` と、この変更のブランチ。上限なし(null)と、上限あり(大きな値)の両方。
- 回数: それぞれ5回走らせ、中央値を取る。
- 判断: 上限なしの退行が 3% を超えたら、マージの前に相談する。数え方を変える案(例: 周回ごとでなく、手続きの適用ごとに数える)を併せて示す。
- 結果は PR に書く。文章に実測値を残すのは、この計画書の「測定」の節だけにする。

## テスト(Red から始める)

6h-1(`src/sucheme.zig` の単体テスト):

1. Red: `setStepLimit(1000)` のインタプリタで `(let loop () (loop))` が `error.StepLimit` を返し、`diagnostic()` が `step limit exceeded` である。
2. Red: 同じインタプリタで、続けて `(+ 1 2)` が `3` を返す(残りは形式ごとに戻る)。
3. Red: `(guard (e (#t 'caught)) (let loop () (loop)))` と、`with-exception-handler` で包んだ同じループが、`caught` を返さずに `error.StepLimit` で終わる。
4. 上限を置かないインタプリタで、10 万回の末尾呼び出しのループが終わる(既定で止めないことの縮小版。100 万回の版は `tier.slow()` に置く)。
5. 上限ちょうどの境界: 歩数が上限と等しい式は通り、1歩多い式は止まる(数え方の off-by-one を固定する。式の歩数は、1の計器で測った値を使う)。

6h-2(`tools/conformance-run/run.zig` の単体テスト):

1. Red: 偽のスイートで、節の中に止まらない `(define (f) (f)) (test 1 (f))` があるとき、その形式が誤りに数えられ、詳細が `step limit exceeded` で、同じ節の後続のテストが走る。
2. 止まらない定義(`(define x (let loop () (loop)))`)が、連鎖のもとになる。

ミューテーションテストの代表(敵対的レビューのミューテーション担当に渡す): 減らす位置をループの外に出す、比較を `<` と `<=` で入れ替える、形式ごとに戻さない、`StepLimit` を「読めない」に数える。

- スイートの最初の2回は 3% を超えたので、計画どおり実装を止めて相談した。起動だけ、`import` だけ、スイートに分けて測り直すと、スイートの差は負の側に出た。同じ負荷を同じ回数測っても、差の符号が入れ替わる。周回の費用は、この環境のばらつき(数%)より小さく、見分けられなかったと判断した(2026-10-21 に、親のセッションの指示で、この形で受け入れた)。

- 上限を置いたときの費用は、測っていない。上限の有無で変わるのは `run` が作る残りの初期値だけで、周回で比べて減らす処理は上限なしと同じである(6h-1 の実装を読んで確かめた)。
- 6h-2 の上限の値(2026-10-22、使い捨ての写しで実施): 機械に一時の計器を入れて、取り込んだスイートの評価したトップレベルの形式(550 個)の歩数を数えると、最大は 2339 歩(1690 行目の形式)、合計は 91820 歩だった。上限は約 100 倍の 250000 歩にした。ReleaseSafe で、上限まで回る形式は、250000 歩で約 0.1 秒、1000000 歩で約 0.27 秒で止まった。今のスイートで上限に当たる形式は無く、`docs/status/conformance.md` は変わらない。

## 合意を求める点

勧める案を先に書く。全部勧める案でよければ、そう返信してください。

1. 上限の単位。
   - 勧める案: 機械の `steps` のループの1周を1歩とし、トップレベルの形式1つ(`Machine.run` の1回)ごとに数え直す。
     - メリット: 決定的で、CI の生成物が機械の速さで変わらない。止まらないループを、確保の有無によらず止める。数える場所が1か所である。
     - デメリット: 1周ごとに減らして比べる費用が乗る(測って判断する)。プリミティブの中の重さは数えない。
   - 別案: 手続きの適用(クロージャの呼び出し)ごとに数える。
     - メリット: 数える回数が減り、費用が小さい見込み。
     - デメリット: 1歩の重さが手続きの本体の長さで変わり、上限の値の意味が分かりにくくなる。止まらない計算が必ず手続きの呼び出しを通ることを、展開器が作る形ごとに確かめる必要がある。
2. 上限に達したときの誤りの種類。
   - 勧める案: Scheme の条件にせず、`error.StepLimit`(ハンドラで捕まえられない誤り)にする。
     - メリット: `(chibi test)` の `test` や `guard` が握りつぶして回り続けることがない。ランナーの分類が単純である。
     - デメリット: `dynamic-wind` の `after` が呼ばれない。REPL で上限を使う日が来たら、`after` の扱いを決め直す必要がある(今は REPL では上限を置かない)。
   - 別案: `heap limit exceeded` と同じく、Scheme の条件として送出する。
     - メリット: `after` が呼ばれる。利用者のプログラムが、上限の超過を捕まえて後始末できる。
     - デメリット: 捕まえて続けるループが止まらない。上限を一度超えたら、次の歩ごとに送出し直すかどうかの規則(`limit_reported` に当たるもの)が要る。
3. 打ち切ったあとのインタプリタを使い続けてよいか(L0 に確かめる)。
   - 勧める案: `OutOfMemory` と同じく、次の `evalPrint` を続けてよいとする。L0 がそれを保証できない場合は、ランナーは、打ち切った節の残りの形式を、すべて連鎖に数えて、次の節へ進む。
     - メリット: 1つの止まらない形式で、節の残りのテストを失わない。
     - デメリット: 保証の確かめに、L0 の読みが要る。
4. 誰が実装するか。
   - 勧める案: L5 が、6h-1 と 6h-2 を、3o のマージのあとに実装する。6h-1 の差分は、L0 と L3 に見てもらってからマージする。
     - メリット: 準拠スイートの CI の弱点を、段階6の完了の前に、L3 の段階8の作業を待たずに閉じられる。変更が小さい。
     - デメリット: L0 と L3 の所有ファイルに、L5 が触る。
   - 別案: 6h-1 を L3 の再開可能な機械(8e と 8f)に含めてもらい、L5 は 6h-2 だけを行う。
     - メリット: 機械の歩数の設計が1つのレーンにまとまる。
     - デメリット: L3 の段階5の作業(5m、5o)のあとになり、段階6の完了の前に間に合うかが分からない。
5. ADR を書くか。
   - 勧める案: 6h-1 の PR で、ADR を1つ書く。決めるのは、歩数の単位、ハンドラで捕まえられない誤りとしたこと、既定で上限を置かないこと。
     - メリット: 段階8で L3 が同じ数を広げるときに、決めた理由が残る。
     - デメリット: ADR が1つ増える。
