# 0015: GitHub Actions の実行分数を抑える

- 対応する決定: [ADR-0010](../adr/0010-ci-cd-and-release-strategy.md)(CI のテスト対象)、[ADR-0020](../adr/0020-repository-visibility-private.md)(private では分数が枠に計上される)
- 段階: 横断の運用。段階2の最中に起きた
- 日付: 2026-10-13
- 状態: 合意済み(2026-10-13)。案 A の運用の規則と、案 B のうち B1 と B2 を、[#86](https://github.com/suchi/sucheme-zig/pull/86) で入れ、`main` に入った。B3 は採らない。実績の確認は未了である。2026-10-24 に追補を足した(層2 の伸びの測定と、文書だけの PR で層2 と Preview を起動しない案 2 の採用)

## 解こうとしている問題

2026-10-13(JST)に、ユーザーから、Actions の月の実行分数が月の半ばで枠を超えたと知らされた。このリポジトリは private なので、標準ランナーの実行分数がプランの枠に計上される(ADR-0020)。段階2は、複数のスライスを並行して進め、PR ごとに push を重ねたため、CI が短い間隔で何度も走った。

枠の大きさ(プランごとの含まれる分数)と、Windows の倍率は、公式文書に到達できず確かめられなかった(未確認)。以下の見積りは、Windows を Linux の 2 倍で数える。実際の内訳は、GitHub の Billing のページの使用量レポート(ワークフロー別)で確かめられる。見積りと食い違ったら、見積りを直す。

## 使用量の見積り

ワークフローの実行回数は、2026-10-01 以降の GitHub の実行の総数から取った。1 ジョブの所要時間は、直近の実行のジョブの開始と完了の時刻から取り、1 分単位に切り上げた。いずれも概算で、約束ではない。

| ワークフロー | ジョブ | 1 実行の所要(切り上げ) | 計上の目安 |
| --- | --- | --- | --- |
| CI | test (ubuntu) | 3 分 | 3 |
| CI | test (windows) | 5 分 | 10(2 倍) |
| Preview | preview (ubuntu) | 3 分 | 3 |
| Full | slow tests (ubuntu) | 7 分 | 7 |
| Full | dist (ubuntu) | 4 分 | 4 |

| ワークフロー | 2026-10-01 以降の実行数 | 1 実行の計上 | 合計の目安 |
| --- | --- | --- | --- |
| CI(取り消し以外) | 約 286 | 13 | 約 3,700 |
| CI(取り消し) | 33 | 約 3 | 約 100 |
| Preview | 43 | 3 | 約 130 |
| Full | 110 | 11 | 約 1,200 |
| 合計 | | | 約 5,200(約 5,160) |

CI の Windows ジョブだけで約 2,900 で、合計の半分を超える。CI 全体では合計の約 4 分の 3 である。

## 案

### 案 A: push をまとめる運用(PR #86 で入れる)

ワークフローは変えない。push の回数を減らす。

- PR ブランチへの push は、PR を作るときの 1 回と、レビューの指摘への対応をまとめた 1 回を基本にする。実装の途中の節目ごとには push しない(ローカルで層1 を通してから push する規則は変えない)。
- main に他の PR が入ったときの取り込みは、競合が実際に出るかを `git merge-tree` で確かめる(分数を使わない)。取り込みの push は、PR を ready にする直前にまとめて行う。
- サブエージェントへの依頼文に、同じ規則を書く。
- ミューテーションテストは、網羅を目指さない。変更した判定の分岐ごとに代表的な書き換えを数件にとどめる。ローカルの時間とトークンの節約であり、Actions の分数には効かない。

見積り: PR 1 件あたりの層1 の実行を、約 5.4 回から約 3.5 回に減らす。どちらも推測で、5.4 回の導き方は記録していない。CI と Preview(約 3,950)の約 35% で、約 1,400 分。

### 案 B: ワークフローの変更(B1 と B2 を採る。ユーザーが 2026-10-13 に承認した)

B1. Windows の test ジョブを、全 push の CI から外し、`full.yml`(PR を ready にしたとき、手動。B2 を採らなければ `main` への push も)に移す。

- 長所: CI 1 実行が 13 から 3 になる。Windows でしか起きない不具合は、ready にする時に検出される。ready のあとに push したコミット(指摘の修正、main の取り込み)では `full.yml` が起動しないので、マージの承認を求める前に、PR の先頭のコミットで手動で走らせる(AGENTS.md の規則)。この手順を飛ばすと、Windows でだけ壊れるコミットが、Windows のテストを通らずに main に入る。
- 短所: ADR-0010 が決めた「CI は全コミットで Linux と Windows」を変える。draft の間の push では Windows の不具合が見えず、ready にしてから見つかる。`tools/check-docs` の `ci.yml` の matrix の照合([tools/check-docs/main.zig](../../tools/check-docs/main.zig) の `os`)と、検証コマンド表の「CIで実行」の列、ADR-0010 の追記を直す必要がある。`tools/check-docs` には、`full.yml` が `runs-on: windows-latest` を持つことと、`ci.yml` の各 `run:` 行を `full.yml` も持つことの照合を足す。どちらも、どのジョブにあるかまでは見ない(2つのジョブの `runs-on` を入れ替える2箇所の編集は通る)。
- 見積り: CI から約 2,900 を外し、Full に Windows(10)を足す。Full に足す回数が 110 なら約 1,100 で、差し引き約 1,800(合計の約 34%)の減。ready のときだけ足すなら(約 50 回、約 500)、差し引き約 2,400(約 46%)の減。約 50 回は、2026-10-01 以降の Full の実行のうち `pull_request`(ready)の起動の数(51)である。

B2. `full.yml` の `main` への push の起動を外し、`ready_for_review` と手動だけにする。

- 長所: Full の約半数(main への push、58 回)が無くなる。手動の起動を数えなければ、約 640 分(約 12%)の減。
- 短所: PR が最新の main を取り込んでいなければ、マージ後の組み合わせの不具合を Full は見ない。ただし `main` への push の CI(層1)は残る。リリースのタグの push では `release.yml` が dist を再び組み立てる。
- 見積りの補正: ready のあとに push した PR では、マージの承認を求める前に、先頭のコミットで Full を手動で走らせる(AGENTS.md の規則)。手動の実行 1 回の計上は、slow 7、dist 4、windows 10 の計 21 である。ready のあとに push する PR を n 件とすると、B2 の減は 640 − 21n になる。2026-10-01 以降に ready で Full が起動した PR(51 件)がすべて 1 回ずつ手動で走らせると、約 1,070 増え、B2 は差し引き約 430 の増になる。手動の実行を 1 PR に 1 回とみなしたので、ready のあとに 2 回以上 push して、そのたびに走らせれば、さらに増える。
- 注: `AGENTS.md` の検証コマンド表の「CIで実行」の列(層2 の行)を直す。

B3. Windows の test ジョブで走らせる step を、プラットフォームに依存するもの(`zig fmt --check`、`zig build`、`zig build test`、`zig build test-scheme`)に絞る。`wasm`、`test-wasm`、`check-docs`、`check-extract`、`check-report` は Linux だけにする。

- 長所: B1 を採らない場合の次善。Windows の所要が 5 分から 3.5 分前後になる(推測)。
- 短所: `ci.yml` の step の並びを OS ごとに分ける必要があり、`if:` を使わない規則(`tools/check-docs` が見る)と衝突する。ジョブを分ける形になり、変更が大きい。
- 見積り: 約 570 分(約 11%)の減。B1 と同時には採らない。

### 案 C: 枠そのものを変える(ユーザーの設定)

- 支出の上限(spending limit)の引き上げ、またはプランの変更。コードの変更は要らない。
- リポジトリを public にすると、標準ランナーの分数は計上されない(ADR-0020 が private を選んだ理由とのトレードオフ。ADR-0022 の許諾の扱いも関わる)。この計画では提案しない。

## 見積りの合算

同じ作業量(2026-10-01 から 10-13 の実績)に対する、約 5,200 分(丸める前は約 5,160)からの減り方。

計算の順序は次のとおりである。B1(ready のときだけ足す、約 2,360 の減)と B2(約 640 の減)を先に引く。案 A の 35% は、そのあとに残る CI と Preview(CI の 1 実行が 3 になったあとの約 1,090)に掛ける(約 380 の減)。案 A を B1 の前の CI と Preview(約 3,950)に掛けると、B1 で外す Windows の分を 2 回数える。最後に、B2 の見積りの補正(ready のあとに push した PR の手動の Full、1 回 21)を足す。下の表は両端を示す。n = 0 は ready のあとに push する PR が無いとき、n = 51 は ready で Full が起動した PR(51 件)がすべて 1 回ずつ手動で走らせるとき(約 1,070 を足す)である。案 A のみは B2 を含まないので、手動の分は足さない。

| 組み合わせ | 合計の目安(n = 0) | 減少(n = 0) | 合計の目安(n = 51) | 減少(n = 51) |
| --- | --- | --- | --- | --- |
| 案 A のみ | 約 3,800 | 約 27% | 約 3,800 | 約 27% |
| 案 A と B1(Full に Windows を ready のときだけ足す)と B2 | 約 1,800 | 約 66% | 約 2,850 | 約 45% |
| 案 B1 と B2 のみ | 約 2,200 | 約 58% | 約 3,230 | 約 37% |

案 A と B の組み合わせでも、この作業量を月の枠に収められるかは、枠の大きさが未確認なので言えない。今月の残りの期間は、枠を超えたあとの実行の扱い(止まる、または支出の上限まで課金される)が、ユーザーの設定に依る。

## 推奨と決定

案 A、B1、B2 を採る。B3 は B1 と同時には採らない。B1 は ADR-0010 の決定のうち走る時機を変えるので、[ADR-0036](../adr/0036-windows-tests-in-the-slow-tier.md) に記録し、ADR-0010、ADR-0033、ADR-0034 に追記した。案 C(枠の設定)は、ユーザーの設定である。

## 2026-10-24 の追補: 層2 の伸びと、文書だけの PR

### 測定(2026-10-05 から 10-24)

ワークフローの実行の一覧とジョブの一覧から、ジョブの開始と完了の時刻を足し合わせた概算である。Billing の使用量レポートの値ではない。Windows のジョブは Linux の 2 倍で数えた(倍率は未確認のまま)。測定は親のセッションが行った。

| 区分 | 分数の目安 | 合計に占める割合 |
| --- | --- | --- |
| 合計 | 約 10,800 | - |
| Full(層2) | 約 5,370 | 約 50% |
| CI(層1) | 約 4,660 | 約 43% |
| Preview | 約 715 | 約 7% |

| 内訳 | 分数の目安 | 備考 |
| --- | --- | --- |
| `docs/` で始まるブランチの PR | 約 2,480(約 23%) | Full が約 1,200(40 実行)、CI が 156 実行、Preview が 70 実行 |
| `main` への push の CI | 約 1,250 | 取り消された 41 実行(約 137)を含む |
| 取り消された実行(全体) | 約 359 | |
| 失敗した実行(全体) | 約 160 | |

Full の 1 実行は、2026-10-11 の約 4 分から、10-20 以降の約 50 分に伸びた(3 ジョブのジョブ時間の合計。並行に走るので、壁時計では最も長い slow tests の約 33 分)。主因は slow tests のジョブである(10-11 は 2:50 から 3:41、10-23 と 10-24 は 22:00 から 33:09)。その中では、`zig build test -Dslow=true` が 1:44〜2:26 から 8:40〜13:41 に、`zig build test-scheme -Dslow=true` が 0:27〜0:34 から 11:00〜18:54 に伸びた。Full は 1 PR につきほぼ 1 回なので、実行の数は原因ではない。

確かめられなかった点。

- 枠の大きさと Windows の倍率(前回から変わらず未確認)。
- ブランチ名で数えたので、`docs/` のブランチの PR が文書だけだったとは限らない。
- slow tests が伸びた理由の内訳(テストの数が増えたのか、1 件が遅くなったのか)は、この測定では分けていない。

### 案と決定

- 案 1: 層2 の規模を試すテストを `-Doptimize=ReleaseSafe` で走らせる。上の伸びの主因に効く見込みの案である。計測の結果を受けて、ユーザーが 2026-10-24 に承認し、[ADR-0047](../adr/0047-slow-unit-tests-default-to-releasesafe.md) で採った(`-Dslow=true` のときの最適化の既定を ReleaseSafe にする)。上の測定の層2 の所要時間は、ADR-0047 の前の値である。
- 案 2: 文書だけの PR では、層2 と Preview を起動しない(`full.yml` と `preview.yml` の `paths-ignore`)。ユーザーが 2026-10-24 に承認した。[ADR-0046](../adr/0046-skip-slow-tier-for-docs-only-prs.md) に記録した。`ci.yml` には絞り込みを付けない。`tools/check-docs` は、`ci.yml` が `paths-ignore` を持つと赤にする。
- 案 3: `main` への push の CI を、日次の定期実行に変える。採らない(ユーザーが 2026-10-24 に承認した)。マージのたびの層1 が無くなり、`main` の破損に気づくのが遅れるからである。

案 2 の見込み: 上の期間に当てはめると、`docs/` のブランチの PR の Full と Preview の分(約 1,350)が減る(見込み。文書だけでない `docs/` のブランチも含む)。層1 の分(CI の 156 実行)は残る。

### 案 2 の挙動の確かめ方

公式文書の記述で確かめたことと、未確認のまま残る点は、[ADR-0046](../adr/0046-skip-slow-tier-for-docs-only-prs.md) の「結果」に、出典と日付つきで分けて書いた(docs.github.com には届かず、そのソースの github/docs リポジトリを読んだ)。未確認のまま残るのは、`ready_for_review` と組み合わせたときの効き方と、`workflow_dispatch` に効かないことの明記である。最初の文書だけの PR で、次の手順で確かめる。

1. 文書だけを変えた PR を、ドラフトで開く。Preview の実行が起動しないこと、CI の実行が起動することを、その PR の check run の一覧で確かめる。
2. その PR を ready にする。Full の実行が起動しないことを、Full のワークフローの実行の一覧で確かめる。
3. その PR がマージできる状態か(必須のチェックが保留のまま残らないか)を、PR の mergeable_state で確かめる。保留のまま残るときは、ユーザーに伝える。公式文書は、パスのフィルタでスキップしたワークフローのチェックが保留のまま残り、それを必須にしている PR はマージできない、と書いている。2026-10-24 の時点で `main` にブランチ保護もルールセットも無い、という報告は、この PR の独立レビューの担当が、その環境の読み取り API で得たものである。この PR を作った環境では、同じ API が 403 になり、確かめられていない。ブランチ保護の有無は、確認できていないものとして扱う。
4. 文書だけでない PR で、ready にしても Full が起動しなかったときは、手動で Full を走らせ、`paths-ignore` の一覧と AGENTS.md の定義の食い違いを調べて報告する(AGENTS.md の文書だけの PR の例外)。
5. コードを1行でも変えた PR では、Preview と Full が今までどおり起動することを、次のコードの PR で確かめる。
6. 結果を、この計画書の進捗の表に書く。

### 残っていること

- `preview.yml` の一覧が `full.yml` の一覧と同じであることを見る検査は無い。`tools/check-docs` が固定するのは `full.yml` の値だけである。食い違うと、Preview だけが余分に走るか、成果物の添付が無くなる(検証は止まらない)。
- リリースノートだけを足す PR では `dist` が走らない。`dist` はリリースノートを読まないので、リリースノートの不備がタグの push で初めて見つかるのは、この追補の前から同じである。
- `tools/check-docs` に足したテストは、固定する値の表(`slow_workflow_pins`)を確かめるが、`full.yml` を読んで照合する検査のループそのものは走らせない。ループの条件を無効にするミューテーションでは、`zig test` は落ちない(`zig build check-docs` を実際のワークフローに対して走らせたときにだけ見える)。
- 期待と違って Full が起動したとき(文書だけの PR で起動したとき)の手順は決めていない。分数が余分にかかるだけで検証は止まらないので、見つけたら報告し、一覧と定義を見直す。

## 作業の順序

1. この計画書と、AGENTS.md の運用の規則(案 A)を入れる。
2. 案 B の B1 と B2 を、同じ PR で実装する(`ci.yml`、`full.yml`、`release.yml` のコメント、`tools/check-docs`、AGENTS.md の表、ADR-0036 の新設、ADR-0010、ADR-0033、ADR-0034 への追記、計画 0007 の起動の記述)。
3. 実装後、使用量レポートで実績を確かめ、この計画書に実績を足す。
