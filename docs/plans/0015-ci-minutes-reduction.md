# 0015: GitHub Actions の実行分数を抑える

- 対応する決定: [ADR-0010](../adr/0010-ci-cd-and-release-strategy.md)(CI のテスト対象)、[ADR-0020](../adr/0020-repository-visibility-private.md)(private では分数が枠に計上される)
- 段階: 横断の運用。段階2の最中に起きた
- 日付: 2026-10-13
- 状態: 合意済み(2026-10-13)。案 A の運用の規則と、案 B のうち B1 と B2 を、この PR で入れる。B3 は採らない

## 解こうとしている問題

2026-10-13(JST)に、ユーザーから、Actions の月の実行分数が月の半ばで枠を超えたと知らされた。このリポジトリは private なので、標準ランナーの実行分数がプランの枠に計上される(ADR-0020)。段階2は、複数のスライスを並行して進め、PR ごとに push を重ねたため、CI が短い間隔で何度も走った。

枠の大きさ(プランごとの含まれる分数)と、Windows の倍率は、公式文書に到達できず確かめられなかった(未確認)。以下の見積りは、Windows を Linux の 2 倍で数える。実際の内訳は、GitHub の Billing のページの使用量レポート(ワークフロー別)で確かめられる。見積りと食い違ったら、見積りを直す。

## 使用量の見積り

ワークフローの実行回数は、2026-10-01 以降の GitHub のランの総数から取った。1 ジョブの所要時間は、直近のランのジョブの開始と完了の時刻から取り、1 分単位に切り上げた。いずれも概算で、約束ではない。

| ワークフロー | ジョブ | 1 ランの所要(切り上げ) | 計上の目安 |
| --- | --- | --- | --- |
| CI | test (ubuntu) | 3 分 | 3 |
| CI | test (windows) | 5 分 | 10(2 倍) |
| Preview | preview (ubuntu) | 3 分 | 3 |
| Full | slow tests (ubuntu) | 7 分 | 7 |
| Full | dist (ubuntu) | 4 分 | 4 |

| ワークフロー | 2026-10-01 以降のラン数 | 1 ランの計上 | 合計の目安 |
| --- | --- | --- | --- |
| CI(取り消し以外) | 約 286 | 13 | 約 3,700 |
| CI(取り消し) | 33 | 約 3 | 約 100 |
| Preview | 43 | 3 | 約 130 |
| Full | 110 | 約 11.5 | 約 1,300 |
| 合計 | | | 約 5,200 |

CI の Windows ジョブだけで約 2,900 で、合計の半分を超える。CI 全体では合計の約 4 分の 3 である。

## 案

### 案 A: push をまとめる運用(この PR で入れる)

ワークフローは変えない。push の回数を減らす。

- PR ブランチへの push は、PR を作るときの 1 回と、レビューの指摘への対応をまとめた 1 回を基本にする。実装の途中の節目ごとには push しない(ローカルで層1 を通してから push する規則は変えない)。
- main に他の PR が入ったときの取り込みは、競合が実際に出るかを `git merge-tree` で確かめる(分数を使わない)。取り込みの push は、PR を ready にする直前にまとめて行う。
- サブエージェントへの依頼文に、同じ規則を書く。
- ミューテーションテストは、網羅を目指さない。変更した判定の分岐ごとに代表的な書き換えを数件にとどめる。ローカルの時間とトークンの節約であり、Actions の分数には効かない。

見積り: PR 1 件あたりの層1 の実行を、約 5.4 回から約 3.5 回に減らす(推測)。CI と Preview の約 35% で、約 1,400 分。

### 案 B: ワークフローの変更(B1 と B2 を採る。ユーザーが 2026-10-13 に承認した)

B1. Windows の test ジョブを、全 push の CI から外し、`full.yml`(PR を ready にしたとき、手動。B2 を採らなければ `main` への push も)に移す。

- 長所: CI 1 ランが 13 から 3 になる。Windows でしか起きない不具合は、ready にする時に検出される。ready のあとに push したコミット(指摘の修正、main の取り込み)では `full.yml` が起動しないので、マージの承認を求める前に、PR の先頭のコミットで手動で走らせる(AGENTS.md の規則)。この手順を飛ばすと、Windows でだけ壊れるコミットが、Windows のテストを通らずに main に入る。
- 短所: ADR-0010 が決めた「CI は全コミットで Linux と Windows」を変える。draft の間の push では Windows の不具合が見えず、ready にしてから見つかる。`tools/check-docs` の `ci.yml` の matrix の照合([tools/check-docs/main.zig](../../tools/check-docs/main.zig) の `os`)と、検証コマンド表の「CIで実行」の列、ADR-0010 の追記を直す必要がある。
- 見積り: CI から約 2,900 を外し、Full に Windows(10)を足す。Full に足す回数が 110 なら約 1,100 で、差し引き約 1,800(合計の約 34%)の減。ready のときだけ足すなら(約 50 回、約 500)、差し引き約 2,400(約 45%)の減。

B2. `full.yml` の `main` への push の起動を外し、`ready_for_review` と手動だけにする。

- 長所: Full の約半数(main への push)が無くなる。約 700 分(約 13%)の減。
- 短所: PR が最新の main を取り込んでいなければ、マージ後の組み合わせの不具合を Full は見ない。ただし `main` への push の CI(層1)は残る。リリースのタグの push では `release.yml` が dist を再び組み立てる。
- 注: `AGENTS.md` の検証コマンド表の「CIで実行」の列(層2 の行)を直す。

B3. Windows の test ジョブで走らせる step を、プラットフォームに依存するもの(`zig fmt --check`、`zig build`、`zig build test`、`zig build test-scheme`)に絞る。`wasm`、`test-wasm`、`check-docs`、`check-extract`、`check-report` は Linux だけにする。

- 長所: B1 を採らない場合の次善。Windows の所要が 5 分から 3.5 分前後になる(推測)。
- 短所: `ci.yml` の step の並びを OS ごとに分ける必要があり、`if:` を使わない規則(`tools/check-docs` が見る)と衝突する。ジョブを分ける形になり、変更が大きい。
- 見積り: 約 570 分(約 11%)の減。B1 と同時には採らない。

### 案 C: 枠そのものを変える(ユーザーの設定)

- 支出の上限(spending limit)の引き上げ、またはプランの変更。コードの変更は要らない。
- リポジトリを public にすると、標準ランナーの分数は計上されない(ADR-0020 が private を選んだ理由とのトレードオフ。ADR-0022 の許諾の扱いも関わる)。この計画では提案しない。

## 見積りの合算

同じ作業量(2026-10-01 から 10-13 の実績)に対する、約 5,200 分からの減り方。

| 組み合わせ | 合計の目安 | 減少 |
| --- | --- | --- |
| 案 A のみ | 約 3,800 | 約 27% |
| 案 A と B1(Full に Windows を ready のときだけ足す)と B2 | 約 1,800 | 約 65% |
| 案 B1 と B2 のみ | 約 2,200 | 約 58% |

案 A と B の組み合わせでも、この作業量を月の枠に収められるかは、枠の大きさが未確認なので言えない。今月の残りの期間は、枠を超えたあとのランの扱い(止まる、または支出の上限まで課金される)が、ユーザーの設定に依る。

## 推奨と決定

案 A、B1、B2 を採る。B3 は B1 と同時には採らない。B1 は ADR-0010 の決定のうち走る時機を変えるので、[ADR-0036](../adr/0036-windows-tests-in-the-slow-tier.md) に記録し、ADR-0010 と ADR-0034 に追記した。案 C(枠の設定)は、ユーザーの設定である。

## 作業の順序

1. この計画書と、AGENTS.md の運用の規則(案 A)を入れる。
2. 案 B の B1 と B2 を、同じ PR で実装する(`ci.yml`、`full.yml`、`release.yml` のコメント、`tools/check-docs`、AGENTS.md の表、ADR-0036 の新設、ADR-0010 と ADR-0034 への追記、計画 0007 の起動の記述)。
3. 実装後、使用量レポートで実績を確かめ、この計画書に実績を足す。
