- 状態: 提案。ユーザーの合意を待っている。合意の前に実装(下の変更 2 から 5)は始めない

## 解こうとしている問題

段階1の最後のスライス 1j-5 がマージされ、v0.1.0 は公開された。[onboarding の「段階を完了させる」](../onboarding.md)の手順のうち、リリースタグ以外はまだ行っていない。[AGENTS.md](../../AGENTS.md) は、段階が終わるたびに [0012](0012-schedule-estimates-and-actuals.md) の見積りと実績を比べることも求めている。

あわせて、公開の日付の記録に誤りがある。v0.1.0 の公開は 2026-10-12 15:00:50 UTC で、日本標準時では 2026-10-13 00:00 である。計画 0009 と 0012 は、UTC の日付を日本標準時の表の中に「2026-10-12」と書いている。0012 の日付の列は日本標準時で書いてあるので、食い違っている。

## 変更

1. この計画書(提案)。
2. 公開の日付を直す。0009 の「次にやること」と 0012 の段階1の行にある「2026-10-12」を、日本標準時の 2026-10-13 に直す。[open-questions](../design/open-questions.md) のタグの保護の行の「2026-10-12 の時点」は、ルールセットの有無を確かめた日で、公開の日付ではないので、そのままにする。
3. `build.zig` の `current_stage` を 1 から 2 にする。`tools/check-docs` は、`current_stage` 以下の段階の全コミットの行を CI に要求する。AGENTS.md の検証コマンド表に、段階2 を開始とする行は無いので、新しい要求は生まれない見込みである。`zig build check-docs` で確かめる。
4. roadmap の「現在の段階」を段階2に更新する。説明文の、`current_stage` を上げたときの注意は、そのまま残す。
5. 0012 に段階1の実績を足す。
   - 開始は 2026-10-09 13:59(1a のマージ)、終了は 2026-10-13 00:00(v0.1.0 の公開)で、暦日は約3.5日である。見積りの「約4〜5日」より短かった。
   - 補正の進め方(0012 の「補正の進め方」)に従い、実績と見積りの比を出して、段階2以降の見積りを直すかを決める。段階1は、見込みの終了日(10-13 前後)に収まったので、直さない案を勧める。
   - 実績のばらつきの原因を、記録に残す。リリースの仕組み(ワークフロー、アーカイブ、検査)に、想定より時間を使った。プロセスの失敗は [process-lessons](../review/process-lessons.md) に別の PR で書く。

## 判断を仰ぎたい点

1. 上の変更 2 から 5 の範囲でよいか。
   - 勧める案: この範囲でよい。理由は、onboarding の手順のうち、足りない部分だけを行うからである。
2. `current_stage` を上げる変更 3 を、この PR に入れてよいか。
   - 勧める案: 入れる。上げても新しい要求が生まれないことを、`check-docs` で確かめられる。確かめて要求が生まれたら、その行を足す計画に直して、改めて合意を求める。
   - 別の案: 段階2の最初のスライスの PR で上げる。段階の切り替えが、段階2の実装と同じ PR に混ざる。
