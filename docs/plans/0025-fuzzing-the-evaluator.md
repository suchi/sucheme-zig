## 解こうとしている問題

ファジングの対象は、今はリーダだけである(`src/reader.zig` の `fuzzReader`)。週に1回の `fuzz.yml` が、`zig build test --fuzz=500K -Doptimize=ReleaseSafe` で走らせる。

評価器(展開器、コアIRへの変換、機械、プリミティブ、`(scheme base)` の Scheme の定義)は、ファジングの対象に入っていない。これまで対象にできなかった理由は2つあった。

- 止まらない入力がある。`(let loop () (loop))` のような入力で、1回の実行が終わらない。`--fuzz` の探索中は `--test-timeout` が効かない(AGENTS.md の検証コマンドの節)。
- 確保が際限なく増える入力がある。

ヒープの上限と、スライス 6h-1 で入った機械の歩数の上限([0024](0024-step-limit-for-the-conformance-run.md)、[ADR-0044](../adr/0044-machine-step-limit-not-catchable.md))で、2つとも、形式ごとに誤りとして打ち切れるようになった。評価器を通しで試す対象を足せる。

準拠スイートと `tests/scheme/` は、書いた人が思いついた入力しか試さない。ファジングは、壊れた入力、途中で切れた入力、型の合わない引数、深い入れ子を試す。見つけたいのは次の種類の誤りである。

- 安全検査の失敗(範囲外の参照、到達しないはずの分岐、整数の溢れ)と、panic
- 確保の漏れ(`std.testing.allocator` が報告する)
- 決めた誤り以外の誤りが、`evalPrint` から返ること
- 誤りのあとで、インタプリタが使えなくなること

## 現状の調査

`origin/main`(`67a7e5d`)のコードと設定を読んで確かめた。

- リーダの対象: `src/reader.zig` の `fuzzReader`。入力は最大 `fuzz_max_input`(1024)バイトで、初期入力は `fuzz_inputs` に並べ、`fuzzSeed` が長さの接頭辞を付ける。1つの入力を、通常の確保と、途中で失敗する確保の2回で読む。
- 1つのバイナリに `std.testing.fuzz` を呼ぶテストを2つ置くと、探索の実行で片方が飛ばされ、ファザーが進まなくなる(`src/reader.zig` のテストの `Why:` コメント)。そのため、リーダのファジングは1つのテストにまとめてある。
- `fuzz.yml`: 週に1回と手動起動。`zig build test --fuzz=500K -Doptimize=ReleaseSafe` を1行で走らせ、`.zig-cache/f/crash` を成果物に上げてから、ファイルがあればジョブを失敗させる。`timeout-minutes: 30`。ジョブ名は `fuzz reader (ubuntu-latest)` である。
- `check-docs` は `fuzz.yml` の `run:` の行を照合しない([open-questions.md](../design/open-questions.md) の「CI が表の行を走らせることの検査の範囲」の行)。
- インタプリタの口: `src/sucheme.zig` の `Interpreter.initWithFiles(gpa, options, files)` は、`files` に null を渡すとファイルを読まない。`setStepLimit` は形式ごとの歩数の上限を決める。`evalPrint` は形式を順に評価し、結果を `out` に書く。
- 歩数で止まらないもの([0024](0024-step-limit-for-the-conformance-run.md) の「残っていること」): 循環するデータの印字と、マクロの展開。どちらも機械の外で走る。

確かめられなかったこと:

- `zig build test --fuzz=<N>` が、複数のテストのバイナリにまたがるファジングのテストをどう扱うか。`<N>` が全体の上限か、テストごとの上限かも確かめていない。スライス 6i-1 の最初に、使い捨てのブランチで確かめる。
- インタプリタを `(scheme base)` つきで1回作る時間。6h の測定で、実行ファイルの起動が約 3.5 ms だった(準拠スイートの実行の測定。[0024](0024-step-limit-for-the-conformance-run.md) の「測定」)。これを1回の実行ごとに払うと、500K 回で約 30 分になる見込みである(起動の時間で割った概算で、ファジングの中で測った値ではない)。6i-1 で測る。
- マクロの展開が止まらないとき、どこで止まるか。入れ子の `lambda` を重ねる形は、スライス 3p-2(suchi/sucheme-zig#171)が、展開器が作る手続きの入れ子の深さの上限で誤りにする予定である(2026-10-23 の時点で未マージ)。入れ子を深くせずに増える形は、展開が確保を伴うならヒープの上限で止まる見込みだが、確保せずに回る展開がありうるかは読み切れていない。

## 設計の案

### 対象

評価器を通しで試す対象を1つ足す。1回の実行は次のとおりである。

1. 入力のバイト列を、ソースとして受け取る(最大 `fuzz_max_input` バイト。リーダと同じ値)。
2. `std.testing.allocator` で、ファイルを読まないインタプリタを作る。ヒープの上限は小さくし、歩数の上限を付ける。
3. 大きさの決まった書き出し先(固定長のバッファ)に向けて、`evalPrint` を呼ぶ。書き出し先が満ちると `WriteFailed` になり、循環するデータの印字もそこで止まる。
4. 返った誤りが、決めた集合に入っていることを確かめる。集合は、`Raised`、`StepLimit`、`HeapLimit`、`ReserveExhausted`、`WriteFailed` と、リーダの誤りである。
5. 同じインタプリタで `(+ 1 2)` を評価し、`3` が書かれることを確かめる(誤りのあとも使えること)。
6. インタプリタを片付ける。漏れは `std.testing.allocator` が報告する。

確保の失敗を混ぜる2回目の実行(リーダの対象にあるもの)は、最初のスライスでは入れない。`OutOfMemory` で抜けたあとに、同じインタプリタを使い続けてよいかは、まだ確かめていない([0024](0024-step-limit-for-the-conformance-run.md) で確かめたのは `StepLimit` のあとである)。

### 見つけた誤りの扱い

ファジングで見つけた誤りは、直す前に、失敗する入力を `tests/scheme/` のテスト(L5 の 0800 台)か、該当するファイルの単体テストに落とす。直すのは、所有するレーンである([0017](0017-parallel-lanes.md) の所有の表)。issue は、6g と同じく、ユーザーの承認を得てから作る。

## 合意を求める点

1つ目から3つ目は、ワークフローを変えない。4つ目だけが `fuzz.yml` の変更を伴いうるので、ユーザーの承認が要る点として分けた。

### 1. 評価器の対象の初期化の仕方

- 案A(勧める): 1回の実行ごとに、`(scheme base)` つきのインタプリタを作り直す。
  - 利点: 実行が互いに独立し、見つけた入力1つで誤りを再現できる。Scheme で書いた標準の定義も試せる。
  - 欠点: 初期化が遅いと、同じ時間で試せる入力の数が減る(上の「確かめられなかったこと」の概算で、1回あたり数 ms)。
- 案B: 1回の実行ごとに、`initBare` の、標準環境の無いインタプリタを作り直す。
  - 利点: 初期化が速い見込みである(測っていない)。
  - 欠点: 入力が使えるのはコアの構文とプリミティブだけで、`(scheme base)` の定義を試さない。
- 案C: 1つのインタプリタを、実行をまたいで使い回す。
  - 利点: 速い。
  - 欠点: 前の入力の定義が残るので、見つけた入力1つでは誤りを再現できない。ファザーが保存するのは最後の入力だけである。

6i-1 で案Aの1回あたりの時間を測り、遅すぎるとき(目安: 500K 回が `fuzz.yml` の上限に収まらないとき)は、案Bに切り替えるかを諮る。

### 2. 置き場所

- 案A(勧める): `tools/fuzz-eval/` に、独立したテストのバイナリとして置き、`build.zig` の `test` の step に足す。
  - 利点: 1つのバイナリにファジングのテストが1つ、という制約を守れる。L0 の所有する `src/sucheme.zig` を触らない。
  - 欠点: 複数のバイナリにまたがる `--fuzz` の扱いを確かめていない(上の「確かめられなかったこと」)。うまく動かなければ、案Bに移る。
- 案B: `src/sucheme.zig` にテストとして置く。
  - 利点: `--fuzz` の扱いの不確かさが、リーダと同じ形になる(バイナリごとに1つ)。
  - 欠点: L0 の所有ファイルを触るので、L0 との調整が要る。

### 3. 入力コーパス

- 案A(勧める): 初期入力は、自分で書いた短い入力にする。`tests/scheme/` の形式を参考に、構文ごと(`define`、`lambda`、`let` の仲間、`define-syntax`、`guard`、`dynamic-wind`、`call/cc`、ベクタと文字列の手続き)に数件ずつ置く。リーダの `fuzz_inputs` にも、評価器の入力に使う綴り(`#;`、ブロック注釈、文字の名前)を足す。
- 案B: 取り込んだ `tests/vendor/` の `r7rs-tests.scm` を、ビルドのときに読み込み、形式ごとに初期入力にする。
  - 利点: 初期入力が多く、手間が少ない。
  - 欠点: 1つの形式が `fuzz_max_input` を超えるものがある。テストのバイナリに BSD 3条項の文面を埋め込むことになり、[ADR-0041](../adr/0041-bsd-name-clause-attribution-not-endorsement.md) と [ADR-0022](../adr/0022-unlicensed-proprietary.md) の線を引き直す要がある。

### 4. `fuzz.yml`(変更を伴う案は、ユーザーの承認が要る)

- 案A(勧める): `fuzz.yml` を変えずに始める。`zig build test --fuzz=500K` が新しい対象も走らせるなら、ワークフローの変更は要らない。6i-1 で、1回の手動起動(`workflow_dispatch`)で、新しい対象が走ることと所要時間を確かめる。ジョブ名の `fuzz reader` は実態とずれるが、名前だけの変更のために `fuzz.yml` を触らない。
- 案B: 6i-1 の測定のあとで、`fuzz.yml` を変える。`<N>` の値、`timeout-minutes`、ジョブ名、対象ごとにジョブを分けることのどれかである。この案は `.github/workflows/` の変更なので、測定の結果を添えて、ユーザーの承認を得てから行う。

案Aで始めて、測定の結果、上限に収まらないか、新しい対象が走らないと分かったときに、案Bの具体的な差分を諮る。

### 5. ADR

ADR-0013 は、ファジングの対象をリーダとして書いている。評価器を対象に足すことは、テストの方針の決定なので、6i-1 で新しい ADR を作り、ADR-0013 には決定を変えない追記で新しい ADR を指す(勧める案)。計画書だけに書く案は、ADR-0013 を読んだ人が、対象はリーダだけだと受け取るので勧めない。

## 残っていること

- 確保の失敗を混ぜる実行を、評価器の対象にも入れること。`OutOfMemory` のあとの状態の保証を L0 に確かめてから計画する。
- 循環するデータの印字は、書き出し先の大きさで止める。スライス 5j(L3)で `write` が循環を扱うようになったら、この止め方が要るかを見直す。
- 止まらないマクロの展開のうち、3p-2 の入れ子の上限にもヒープの上限にもかからない入力があれば、L0 に回す。
