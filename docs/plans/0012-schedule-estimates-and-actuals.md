- 対応する決定: [ADR-0018](../adr/0018-incremental-vertical-slices.md)(漸進的な縦切り)
- 段階: 全体。段階の定義と完了条件は [../roadmap.md](../roadmap.md) が正
- 日付: 2026-10-11
- 状態: 案。ユーザーの依頼(2026-10-11)による。見積りは概算で、実績で補正していく

## 目的

完了時期を、段階の規模と、これまでの実績から見積もる。厳密さは求めない。段階が終わるたびに、見積りと実績の差を記録し、残りの段階の見積りを補正する。

この文書は、約束ではなく見立てである。コミットメントとして使わない。

## 単位

- 日数は、暦日(カレンダーの日)である。休日も数える。ユーザーのレビューとマージの待ち時間、エージェントの並行実行、CI の待ち時間を含む。
- 規模は、段階1を 1.0 とした相対値である。コード量ではなく、設計の難しさと、作る機構の数を合わせた印象で付ける。
- 日付は JST(UTC+9)。

## 見積りの根拠と、ばらつきの大きい点

- 段階2(2.0): 衛生的マクロ展開器が最も難しい。段階2の「衛生性の検証項目」を通すまでに、設計の手戻りが入る恐れがある。完全な `call/cc` と `dynamic-wind`、例外の動的点、ライブラリシステムも、機械に手を入れる。
- 段階3(0.8): 大半が Scheme のコードで、テストが書きやすい。ただし `syntax-rules` の実用上の穴が、ここで露出しうる。
- 段階4(1.5): bignum、分数、浮動小数点の出力のラウンドトリップ性、Unicode テーブルの生成。個々は定石があるが、量が多い。
- 段階5(1.0): ポートの抽象、リーダの完全化、循環構造の `write`。
- 段階6(1.2、ばらつき大): `r7rs-tests.scm` の不合格の裾野が読めない。見つかった不具合の修正が、前の段階の設計に戻る恐れがある。
- 段階7(0.6): 端末の違い(特に Windows)で時間を取られうる。実装方式の判断(選択肢の提示)を含む。
- 段階8(0.6): 配置先の選定は、ユーザーの判断を待つ。

## 補正の進め方

段階が終わるたびに、次を行う。

1. 上の表に、その段階の実績(開始日、終了日、暦日)を足す。
2. 実績の暦日を、見積りの暦日(幅の中央)で割った比を出す。
3. 残りの段階の暦日に、直近の比を掛けて、見積りを直す。直近 2 段階の平均を使う。1 段階しかないときは、その比の半分だけ寄せる。
4. 差の理由を一言で書く(ペースが違った、機構が難しかった、待ち時間が長かった、など)。理由が繰り返すなら、見積りの単位や進め方を見直す。

実測値を文章に複製しない([ADR-0027](../adr/0027-severity-by-consequence-and-a-cost-side-stop.md))。実績の日付は `git log` から導ける。表は日付と範囲だけを持ち、件数や行数は書かない。

## 段階2で分かった、速さに効いたことと効かなかったこと

次の段階の進め方の入力にする。判断が要るもの(進め方の規則を変えるもの)は、[handoff.md](../handoff.md) の「ユーザーに確認したい進め方」にあり、ここには事実と、それが何に効いたかだけを置く。

速さに効いたもの。

- 実装の前に、段階の計画書を合意した。完了条件が1行で決まったスライスは、着手の迷いが少なかった。
- スライスを小さく切った。1スライスの完了条件を、最初の失敗するテストの1行にした。
- 系列を分け、作業ツリーを分けて並行にした(実行時、マクロ、ライブラリ)。ファイルが重なる所は、計画書の「重なりの確認」の表で先に決めた。
- 機械の検査(`check-docs`、`check-report`、`check-extract`、層1と層2の CI)が、文書と実態の食い違いを早く止めた。
- ミューテーションテストを、テストの強さの確認に使った。レビューより、見つかる欠陥の質が高かった。
- 勧める案を先に書いて、ユーザーが「勧める案どおり」と答えられる形にした。判断の待ち時間が短くなった。

速さに効かなかったもの、または足を引いたもの。

- レビュー用のサブエージェントが、何も書かずに止まることが繰り返された。止めると決めた期限まで待つ時間が、1回ごとに無駄になった。完走したレビューのうち、欠陥を見つけたのは、テストの強さの担当(ミューテーション)が多く、挙動を広く試す担当は、見つけた件数が少なかった。
- メモリの計上の外の問題(ライブラリの表、リーダの作業領域、`include` の節点)が、レビューで後から見つかり、2m から 2o が複数巡になった。スライスの設計の段階で、入力の大きさに比例して確保するものを列挙して測っていれば、早く見つかった。
- 層2の CI は、PR を ready にしてから走るので、レビューの後ろに逐次に並ぶ。実行時間は Actions の実行記録にある。
- 10分ごとの状況報告は、変化がない回も出す規則である。待ちの間の文脈を、同じ内容の報告で消費した。
- GitHub のツールが、セッションの途中で何度も切れた。再接続のたびに、ツールの読み込みが要る。
- タグの push は、この環境からは拒否された(HTTP 403)。ユーザーに頼むため、リリースの最後に往復が1回増えた。
- 見積りの単位が、人の作業時間の感覚だった。実績は数時間単位だったので、見積りの粒度では計画の精度が出ない。

測り直す指標(段階3以降)。スライスごとに、着手(最初のコミット)から PR の ready まで、ready からマージまでを、`git log` と PR の時刻から取る。レビューの待ちと CI の待ちとユーザーの待ちを、分けて見る。実測値は、この文書の表に日付の形で足す。文章には書かない。

## 段階3で分かった、速さに効いたことと効かなかったこと

段階2の節と同じく、事実と、それが何に効いたかだけを置く。進め方の規則を変える案は、[handoff.md](../handoff.md) とユーザーへの確認で扱う。

速さに効いたもの。

- 大きいスライス(3o)は、先に設計の PR と ADR を合意してから、5つの PR に分けた。判断の待ちが短い時間帯のスライスは、時間単位の見積りの範囲に収まった。
- ミューテーションの担当1本のレビューは、段階3でも、テストの穴と、固定長の整数の端のような境界の不具合を見つけた。
- 見積りを時間単位にしたので、スライスごとに、見積りとの差を時刻で比べられた(上の表)。

速さに効かなかったもの、または足を引いたもの。

- 合意を求める点で決まった範囲(整数の手続き)が、スライスの表と roadmap の項目に写されず、段階の最後まで残った。3r の下調べで見つけ、3s を足した。
- 手元の検証で、`zig build test-wasm` の出力を `tail` に通して終了コードを隠し、赤のまま push したことが1回あった(3s)。CI が止めたが、1巡を使った。
- main の push の CI は、同じ ref の古い実行を取り消す(`ci.yml` の `concurrency` の `cancel-in-progress`)。マージが続くと、途中のマージコミットの CI が最後まで走らない。v0.3.0 のタグを打った `b73aaa1` もそうで、同じ木の PR の先頭の CI を根拠にした。
- ガード用のフックのスクリプトが、git の記録で実行権限を持っていなかった。Linux のセッションでは起動が失敗し、段階3の大半の間、フックの判定が働いていなかった(suchi/sucheme-zig#183 で直した)。
- 2026-10-23 の夜に、Actions の新しいジョブが手順を1つも走らせずに失敗する時間帯があり、push を止めて待った。原因は確かめていない。
- 並行のレーンと、広い範囲を触る文書の PR(用語集)が同じ時期に進み、段階3の最後の PR は、main の取り込みとコンフリクトの解消を2回行った。

## 段階4で分かった、速さに効いたことと効かなかったこと

段階2と段階3の節と同じく、事実と、それが何に効いたかだけを置く。

速さに効いたもの。

- 大きいスライス(4e、4g)を、レビューを小さくするために複数の PR に分けた。4g の4つの PR は、1日のうちに続けてマージされた。
- 純粋な関数の層(字句、書式、多倍長、型の骨格)を先に並行に入れ、その上に手続きを積んだ。4a から 4d は、計画書のマージ(10-20 09:24)から約2.4日のうちにマージされた。
- Unicode の表は、生成ツールと比較モード(`check-unicode`)を先に入れてから(4u1)、表(4u2)と手続き(4u3)を足した。

速さに効かなかったもの、または足を引いたもの。

- 計画に無かったスライスが2つ足された(4e-3、4u3b)。どちらも、前のスライスのレビューや、次のスライスの前提を詰める段階で見つかった。
- 4g のあと、段階4のスライスが約2.8日マージされなかった。同じ時期に、段階5と段階6のレーンが進んでいた。
- 段階の完了の監査(4z)で、計画書の進捗の表の5行が、マージ後も「確認中」のまま残っていたと分かった。open-questions の段階4の行は、決める根拠(実測)がそろったまま、基準が決まらずに残っていた。どちらも、段階の最後にまとめて直した。
- 配布物に入る第三者の表示に、段階4で入れた Unicode の表の表示が無いことが、リリースの準備のときに分かった。4u1 で、UCD のライセンスの条件(通知を複製に添えること)を原文で読んで計画書 0018 に記録していたが、配布物の `THIRD-PARTY-NOTICES.txt` に足す作業は、どのスライスにも割り当てられていなかった。
- 段階の最後のスライスからタグまで、段階5のスライスを先にマージする順序にしたので、約2日待った。
