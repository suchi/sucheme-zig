# SOW-0001: sucheme-zig の構築

- ステータス: 有効
- 作成日: 2026-10-04
- 合意: PR #1 のマージをもって合意成立とする
- 対象: プロジェクト全体

範囲または進め方を変更する場合は、本 SOW を非推奨にして次の番号で新しい SOW を作成する。既存の記述を書き換えない。進捗は本 SOW には書かず、[../roadmap.md](../roadmap.md) を単一のソースとする。

## 目的

Zig で R7RS-small に完全準拠した Scheme インタプリタを作る。マクロ(衛生的な `syntax-rules`)まで準拠させる。単体の実行ファイルとして動き、WebAssembly を通じてブラウザ上でも動く。

## 範囲

### 含むもの

- R7RS-small の16ライブラリすべての実装
- 衛生的マクロ、完全な継続、適切な末尾再帰、完全な数値塔、Unicode 対応
- ネイティブの CLI と REPL。最終的に複数行編集と Emacs バインディングを備える
- ブラウザで動く Web UI のサブプロジェクト
- GitHub Actions による CI/CD、GitHub Release による節目ごとの配布
- Web UI の配置。段階8で、private にアクセス制限できるクラウドに置く([ADR-0021](../adr/0021-no-github-pages-defer-hosting.md))。段階7までは配置せず、CI の成果物を zip で添付してローカルで開く
- 設計ドキュメント、ADR、オンボーディングドキュメント、進捗の可視化

### 含まないもの

- R7RS-large(赤版・橙版など)のライブラリ。将来の課題とする
- SRFI の実装。要求が出た時点で個別に判断する
- バイトコードコンパイラやネイティブコード生成。性能測定の結果に基づいて将来検討する
- macOS 環境での自動テストによる動作保証([ADR-0010](../adr/0010-ci-cd-and-release-strategy.md))
- マルチスレッドと並行性。R7RS-small の範囲外である

## 進め方

### 3手順

| 手順 | 内容 | 担当モデル | 区切りの成果物 |
| --- | --- | --- | --- |
| 1 | 設計 | Opus | `docs/design/` と `docs/adr/` |
| 2 | 具体的実装計画 | Opus | `docs/plans/` の段階ごとの計画書 |
| 3 | 実装 | Sonnet。機械的な作業は Haiku | コードとテスト |

各手順の区切りでドキュメントを残し、別の環境・別のセッションでも継続できる状態にする。手順3に入る前に、その段階の計画書が存在することを条件とする。

### マルチエージェントの使い方

段階内で独立性の高い作業は並行させる。並行させる条件は次の2つを満たすこととする。

- 触るファイルが重複しない
- 互いのインタフェースが計画書で確定している

例として、段階4の bignum と Unicode テーブル、段階5の各ライブラリ、リーダとプリンタの拡張は並行できる。一方、値表現と GC と機械は相互依存が強いため逐次で進める。

### 作業の分解

段階0から段階8までの作業分解と完了条件は [../roadmap.md](../roadmap.md) にある。全体の流れは要件どおり次の順序とする。

1. 最小限の REPL を実現する(段階1)
2. コアの Scheme 構文を作る(段階2)
3. コア Scheme で表現できるものはコア Scheme スクリプトで実現する(段階3以降)

Web UI から実行できる仕組みは段階1から用意し、以降のすべての段階で維持する。

## 検証と受け入れ基準

### 常時の検証

全コミットで、`AGENTS.md` の検証コマンド表のうちその時点の段階で使えるものをすべて通す。コマンド名はここに列挙しない。表が正である。

段階0ではフォーマット検査、単体テスト、ビルド、ドキュメントの検査が対象になる。振る舞いテストは段階1から、準拠テストは段階6から対象に加わる。CI も同じ規則で、存在しない step を呼ばない。

### 段階の完了判定

各段階の完了条件は [../roadmap.md](../roadmap.md) に記載する。条件を満たしたらリリースタグを打つ。

### プロジェクトの完了判定

R7RS-small 準拠の判定基準は [../design/r7rs-coverage.md](../design/r7rs-coverage.md) に定める。付録Aの識別子の網羅、仕様どおりの振る舞い、意味論上の性質(適切な末尾再帰・完全な継続・衛生的マクロ・記憶モデル)の3つをすべて満たしたときに準拠と称する。

## 主なリスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 固定した Zig の版の情報が少なく、実装モデルが古い記法を書く | 手戻りが頻発する | 実機検証済みの [../design/zig-api-notes.md](../design/zig-api-notes.md) を整備し、実装前に読む。標準ライブラリのソースを一次情報とする。小さなコミットに分けて誤りを局所化する |
| 精密GCのルート登録漏れ | メモリ破壊。再現しにくい不具合 | 確保点を `heap.zig` に一元化し、確保を行う関数を命名規約とコメントで明示する。CEK機械によりルートを少数のレジスタに限定する。ストレステストを常時実行する |
| 衛生的マクロの微妙な誤り | 準拠を主張できない | [../design/frontend.md](../design/frontend.md) の衛生性の検証項目をすべてテストにし、段階2の完了条件とする |
| 継続の多重起動に関する誤り | 準拠を主張できない | 継続フレームと引数蓄積を不変にする設計上の選択で構造的に防ぐ([ADR-0004](../adr/0004-cek-machine-evaluator.md)) |
| 段階4の作業量が過大 | 全体が停滞する | 数値塔と Unicode を並行させる。多倍長整数は `std.math.big.int` を使い自前実装しない。必要なら複素数のみ繰り延べる(ユーザーの承認を得る) |
| ドキュメントとコードの乖離 | 引き継ぎが機能しない | 準拠マトリクス(`docs/status/`)を生成物にし、CI で同期を検査する。README には数値を置かない。節目ごとに整合性チェックを実施する |
| GitHub Actions の課金 | 継続が難しくなる | テストは ubuntu と windows に限る。クロスコンパイルは1ジョブに集約する。private リポジトリの無料枠は public より小さいので([ADR-0020](../adr/0020-repository-visibility-private.md))、全コミットで走らせる検証を増やすときは使用量を見る |

## 運用

- GitHub Flow。`main` への直接コミットとプッシュは禁止。
- ブランチ名は `feature/xxx` `fix/xxx` `docs/xxx` `chore/xxx`。
- TDD。失敗するテストを書いてから最小の実装、その後に整理。
- 1コミット=1論理変更。節目ごとにプッシュ。
- PR は自前の敵対的レビューを実行し、新規指摘ゼロになるまで修正を繰り返す([../adr/0017-self-hosted-adversarial-review.md](../adr/0017-self-hosted-adversarial-review.md))。
- マージはレビュー完了・CI 全ジョブグリーン・ユーザー承認の3つが揃ってから行う。
- 技術選択と設計判断、およびレビュー提案をあえて採用しない場合は ADR に記録する。

## 前提と制約

- Zig は `.zigversion` が固定する版を使う。設計フェーズの時点でローカルに導入済みであることを確認した([ADR-0001](../adr/0001-zig-version-pinning.md))。
- 開発環境は Windows。CI は ubuntu と windows。
- 依存パッケージを持たない。Zig の標準ライブラリと、ベンダリングする準拠テストスイートのみ。
- ビルド時にネットワークへアクセスしない。
