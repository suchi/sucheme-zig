# 0007: テストの層と実行タイミングの設計

- 対応する決定: [ADR-0010](../adr/0010-ci-cd-and-release-strategy.md), [ADR-0013](../adr/0013-testing-strategy-and-conformance-suite.md), [ADR-0026](../adr/0026-verify-facts-about-code-not-prose.md)
- 段階: 1(横断。スライスに属さない)
- 日付: 2026-10-11
- 状態: 合意済み(2026-10-11)。層0 から層2 の仕組みは実装済みで、`full.yml` も [#28](https://github.com/suchi/sucheme-zig/pull/28) で入った。層3(ファジングのスケジュール実行)は未着手

## 解こうとしている問題

修正や実装から、結果が分かるまでの時間(リードタイム)が長い。スライス 1h では、ミューテーションテストの待ちが 40 分を超えた。原因を測ると、毎回走らせる必要のないテストと、毎回走らせるべきテストが、同じ検証コマンドに混ざっていた。

- 規模を試すテスト(深さ 10 万の再帰、100 万回のループ、上限まで再帰する無限再帰)が、小さな論理のテストと同じ `zig build test` と `zig build test-scheme` に入っている。これらは、検査の価値は高いが、論理の誤りをほとんど見つけない。見つけるのは、再帰の深さや確保の量に比例して壊れる種類の誤りである。
- ミューテーションテストを、書き換えたファイルのテストでなく、全体のテストで 1 件ずつ走らせていた。
- 実行の頻度を決める基準が無く、「コミット前に必ずテストを実行する」([AGENTS.md](../../AGENTS.md))が、全部を毎回走らせる意味になっていた。

目標は、検査の価値を落とさずに、待ち時間と CPU の消費を減らすことである。そのために、テストを実行の頻度で層に分け、各層をいつ走らせるかを決める。

## 層

```mermaid
flowchart LR
    edit[編集] --> l0[層0 編集ループ]
    l0 --> commit[コミット・push]
    commit --> l1[層1 毎回の門]
    l1 --> ready[PR を ready にする・マージ前]
    ready --> l2[層2 品質確認]
    l2 --> nightly[定期]
    nightly --> l3[層3 耐久・探索]
```

| 層 | いつ | 何を | 目標 | CI |
| --- | --- | --- | --- | --- |
| 層0 編集ループ | 1 回の編集のたび | 書き換えたファイルの `zig test src/<ファイル>.zig` と `zig fmt` | 十数秒以内 | なし |
| 層1 毎回の門 | コミット前、PR への push のたび | `zig build test`(速いテストだけ)、`zig build test-scheme`(速いケースだけ)、`zig build`、`zig fmt --check .`、`check-docs`、`check-extract` | 1 分以内 | 全コミット(今の `ci.yml`) |
| 層2 品質確認 | PR を ready にする前、`main` へのマージ前 | 遅いテスト全部(規模を試すもの)、スキームの全ケースの両モード、変更したファイルのミューテーションテスト、敵対的レビュー | 10 分以内 | PR が ready になったとき、`main` への push、手動 |
| 層3 耐久・探索 | 定期(夜間・週次)、手動 | ファジング、10 倍の規模のソーク、メモリが増え続けないことの確認、性能の測定 | 制限なし | スケジュール |

層の目標の数字は、守る目標であって測定値ではない。超えたら、そのテストを層の上へ移すか、速くする。

## 何をどの層に置くか

置き場所の規則を 1 つに決める。

- 論理を試すテストは、層1 に置く。入力が小さく、誤りがあれば確実に落ちるもの。ストレスモードの GC を含む。
- 規模を試すテストは、層2 に置く。深さ・個数・上限に比例して壊れる種類の誤りを見るもの。層1 に、その縮小版(小さい規模で同じ論理を通すもの)を必ず残す。
- 層1 から外すのは、その縮小版を置いたあとだけにする。これが、検査の価値を落とさない条件である。

今あるテストで当てはめると、次のとおりになる。

| テスト | 層 | 層1 に残す縮小版 |
| --- | --- | --- |
| `0012-gc.txt` の 100 万回ループ | 層2 | 数万回のループ(収集が何度も走る大きさ)。ストレスモードで全ステップ収集 |
| `0012-gc.txt` の上限まで再帰する無限再帰 | 層2 | 単体テスト(`machine.zig` の上限での回復)が、小さい上限で同じ論理を通す |
| `0012-gc.txt` の 10 万段の非末尾再帰 | 層2 | 数千段の再帰 |
| `machine.zig` の深さを試す単体テスト(メモリが許す深さの再帰、20 万回の末尾呼び出しでヒープが増えないこと) | 層2 | 5000 段の再帰、3 万回の末尾呼び出し |
| `reader.zig`・`printer.zig`・`expand.zig` の「10 万段でも再帰しない」テスト | 層1 のまま(計画では層2 だったが、アロケータを速いものにしたあとは短く、外さなかった。「実装での差分」を参照) | 外していないので縮小版は無い |

縮小版の大きさは、同じ論理を通す大きさにする(収集が何度も走る、深さに応じて継続が伸びる、など)。Zig のスタックを使い切るかどうかは、層2 の規模のテストで見る。

## 実装の仕組み

選択肢が 2 つある。勧める案を先頭に置く。

1. 実行時に飛ばす。遅いテストを `slow()` で守り、ビルドのオプション(`-Dslow`)が無いときは `error.SkipZigTest` を返す。スキームのテストは、遅いケースを `tests/scheme-slow/` に置き、同じ step を `-Dslow=true` で走らせたときだけ、ランナーが読む。
   - 長所: テストのコードが 1 か所に残る。飛ばしたテストは、`zig build test --summary all` の概要に skipped の件数が出て、黙って消えない(素の `zig build test` は成功すると何も出さない。`ci.yml` は `--summary all` を付けている)。
   - 短所: `zig build test` が飛ばした件数を、読む人が気にする必要がある。
2. ファイルを分ける。遅いテストを別のファイル(`src/*_slow.zig`)に移し、別の step の対象にする。
   - 長所: 層1 に遅いテストが入る余地が構造上ない。
   - 短所: テストが対象のコードから離れる。深さを試すテストは、リーダ・プリンタ・展開器の内部の関数を使うので、非公開の関数を出す必要が出る。

CI の置き場所は、2 つの案を比べる。

1. 層2 を別のワークフロー(`full.yml`)にする。起動は `pull_request` の `ready_for_review`、`main` への push、`workflow_dispatch`。層3 のファジングは、[ADR-0010](../adr/0010-ci-cd-and-release-strategy.md) の計画どおり、別のワークフローをスケジュールで動かす。
   - 長所: 層1 の CI が速いまま保たれる。
   - 短所: ready にする前の push では、層2 の誤りが見えない。
2. 層2 も全コミットで走らせる。
   - 長所: 設定が単純。
   - 短所: 毎回の待ち時間と CPU のコストが残る。今回の問題が戻る。

ワークフローの変更は、[AGENTS.md](../../AGENTS.md) のセキュリティの規定により、ユーザーの承認を得てから行う。

## ミューテーションテストの扱い

層2 に置く。変更したファイルだけを対象にし、ファイル単位の `zig test` で捕まるかを先に見る。生き残ったものだけを、全体のテストで確かめる。実行の前に、作業ディレクトリが複製の中であることを、スクリプトが自分で確かめる。スクリプトを `tools/` に置くかどうかは、置き場所と保守の費用を比べて別に決める([ADR-0026](../adr/0026-verify-facts-about-code-not-prose.md))。

## 待ち時間の方針

[AGENTS.md](../../AGENTS.md) の「進め方」に、次を足す。

- 検証コマンドを走らせる前に、どの層かを決める。編集のたびは層0、コミット前は層1、PR を ready にする前は層2。
- 1 つの検証が目標を超えたら、待つ前に原因を測る。並行にしたり、担当を増やしたりする前に、1 件あたりの時間を測る。

## 検証コマンド表の変更

[AGENTS.md](../../AGENTS.md) の検証コマンド表に、層2 の行を足す。行は、その step が `build.zig` に実在してから足す。

| 用途 | コマンド | 使えるようになる段階 | CIで実行 |
| --- | --- | --- | --- |
| テスト(規模を試すもの) | `zig build test -Dslow=true` と `zig build test-scheme -Dslow=true` と `zig build test-wasm -Dslow=true` | 1 | PR が ready のとき、`main` への push、手動 |

## 作業の順序

1. 層の規則と縮小版の方針の合意(この計画書)。
2. 縮小版を層1 に足す(同じ論理を通すことを確かめる)。
3. 規模を試すテストを `slow()` で守り、スキームの遅いケースを `tests/scheme-slow/` に移す。`build.zig` に step を足す。
4. [AGENTS.md](../../AGENTS.md) の検証コマンド表と進め方を更新する。
5. `full.yml` を足す(ユーザーの承認が要る)。

2 から 4 は 1 つの PR にまとめられる。5 は別の PR にして、承認を得る。

## 合意を求める点

1. 4 つの層(編集ループ、毎回の門、品質確認、耐久・探索)と、置き場所の規則(縮小版を層1 に残したうえで、規模を試すテストを層2 に移す)。
2. 実装の仕組み: 実行時に飛ばす案(勧める)とファイルを分ける案。
3. CI の置き場所: 層2 を別のワークフローにする案(勧める)と全コミットで走らせる案。

## 実装での差分

- 飛ばした件数が出るのは `zig build test --summary all` の概要だけである。素の `zig build test` は成功すると何も出さない。`zig build test-scheme` は飛ばした件数を出さず、走らせた件数だけを出す(`tests/scheme-slow/` は `-Dslow=true` のときに読むので、層1 では飛ばすのでなく読まない)。計画の「概要に件数が出る」は、この範囲に狭めた。
- スキームの遅いケースは、別の step にせず、`zig build test-scheme -Dslow=true` で同じランナーが `tests/scheme-slow/` も読む形にした。ランナーを 2 つにすると、`build.zig` の「検証が黙って止まる」ための検査(ランナーを 1 つだけ要求する)を広げることになるためである。
- 単体テストで層2 に移したのは、`machine.zig` の 2 つ(10 万段の非末尾再帰、20 万回の末尾呼び出しの計上)だけである。リーダ・プリンタ・展開器の深さのテストは、アロケータを速いものにしたあとでは短く、層1 に残した。
- スキームの `0012-gc.txt` は、縮小版(3 万回のループ、3000 段の再帰、2 万回のループ)を層1 に残し、100 万回のループ、上限までの無限再帰、10 万段の再帰を `tests/scheme-slow/0012-gc-scale.txt` に移した。
- WebAssembly の往復テストにも層2 がある。ホストが 4 GiB 近い上限を渡したときに、計上が 1 GiB で止まること(約1分)を確かめるテストで、`zig build test-wasm -Dslow=true` のときだけ走る。`build.zig` が環境変数 `SUCHEME_SLOW` を `tools/test-wasm/main.mjs` に渡す。`full.yml` がこの step を走らせる(ユーザーが 2026-10-11 に承認した。[review/stage1-slice-1i-round2.md](../review/stage1-slice-1i-round2.md))。
