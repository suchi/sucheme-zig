## 解こうとしている問題

小さなセルを重ねてヒープの上限(既定 256 MiB)に届くプログラムが、`error: heap limit exceeded` を出すまでに 40 秒を超える。誤りの経路なので、正しいプログラムの速度には直接効かない。ただし、止まらない再帰や確保の暴走を書いた利用者は、毎回これだけ待つ。ファイルの実行では待つ間、何も表示されない。

[リファレンスの「実装の上限」](../manual/reference/limits.md)には、以前の観測(Debug で約 55 秒、ReleaseSafe で約 38 秒)を、一例として書いてある。この計画書は、その数値を測り直し、時間の使われ方を調べる。

## 再測定(2026-11-11)

環境は、このセッションのクラウドのコンテナ(Linux 6.18)で、`zig version` は 0.17.0。コミットは `3ce0407`(main)。入力は次の2行で、`zig build` の実行ファイルにファイルとして渡した。以前の観測と同じ入力かは、Issue に入力が書かれていないため、リファレンスの文面にある `grow` の定義から再構成したもので、確かめていない。

```scheme
(define (grow acc) (grow (cons 1 acc)))
(grow '())
```

測り方は、bash の `time` で壁時計の時間を1回ずつ取った(繰り返しは、ReleaseSafe の2回だけ)。

以前の観測より、ReleaseSafe で約 14%、Debug で約 9% 長い。機械が違うのか、その後のコードの変更なのかは、確かめていない。

## H2 の計測(2026-11-11)

H1 と同じ環境とコミットで測った。上限と計装は、`src/heap.zig` の `default_limit` と `Heap.collect` を一時的に書き換えた別のビルドで取った(出力先を分け、測定のあとで元に戻し、コミットしていない)。

### 上限を変えたときの伸び方(ReleaseSafe、`grow`、壁時計の時間を1回ずつ)

| 上限 | 所要時間 | 前の行との比 |
| --- | --- | --- |
| 16 MiB | 1.25 秒 | - |
| 64 MiB | 10.5 秒 | 8.4(上限は 4 倍) |
| 128 MiB | 21.9 秒 | 2.09(上限は 2 倍) |
| 256 MiB(既定) | 43.5 秒 | 1.99(上限は 2 倍) |

64 MiB 以上では、時間は上限にほぼ比例する。2 乗には伸びていない。16 MiB から 64 MiB の伸びが比例より大きい理由は、確かめていない(推測: 小さいヒープは CPU のキャッシュに収まり、1 個あたりの費用が小さい)。

### 確保のパターン(ReleaseSafe、上限 64 MiB。一部は別の計測と同時に走らせたので、時間は目安)

| 入力 | 所要時間 |
| --- | --- |
| `(cons 1 acc)`(`grow`) | 10.5 秒 |
| `(cons (make-string 10 #\a) acc)` | 6.5 秒 |
| `(cons (lambda () acc) acc)` | 1.95 秒 |
| `(cons (make-vector 10 0) acc)` | 0.75 秒 |
| 末尾でない再帰(`depth`) | 2.56 秒 |

セルが小さく、1 反復あたりの確保のうち回収されるものの割合が高い入力ほど遅い。`grow` が最悪で、ほかのパターンは、いずれも 7 秒以下だった。

### 関数ごとの内訳(callgrind、上限 16 MiB、`grow`)

callgrind は命令数を数えるもので、時間ではない。キャッシュのミスの費用は入らないので、上限 256 MiB の時間の内訳(回収が 93%)より、回収の割合が低く出ると見込む。ReleaseSafe の実行ファイルは、そのままでは valgrind が扱えない命令(AVX-512)を使うので、`-Dcpu=baseline` で作った。

| 項目(命令数の割合) | ReleaseSafe | Debug |
| --- | --- | --- |
| 回収(`Heap.collect`)全体 | 約 62% | 約 52% |
| うち マーク(`Marker.finish`) | 約 42% | 約 31% |
| うち 掃除(`Heap.sweep`)。ReleaseSafe は掃除の割合を別に出せなかった(関数が展開されている) | 約 20%(推定。回収からマークを引いた) | 約 20% |
| うち オブジェクトの解放(`Heap.free`) | 約 15% | 約 18% |
| うち 下の割り当て器 `SmpAllocator.free` | 約 9% | 約 9% |
| 確保(`createIn`) | 約 8.5% | 約 12.5% |

掃除の中身は、一覧をたどる分より、オブジェクトごとの解放(`Heap.free`)のほうが大きい。解放と確保の合計(割り当て器の分を含む)は、命令数で約 2 割ある。Debug の壁時計時間の内訳(回収が何割か)は、上限 16 MiB の実行で 3.05 秒(ReleaseSafe は 1.25 秒)と測っただけで、回収の割合は取っていない。

## H3 の計測: 案 B の効果の見積り(2026-11-11)

案 B を実装する前に、効果を見積もるための計測を行った。環境とコミットは H1 と同じ(Linux 6.18、Zig 0.17.0、コミット `3ce0407`)。コードの変更は、すべて一時的な試作で、コミットしていない。

### 掃除の時間は、解放ではなく、一覧のたどりである(ReleaseSafe、上限 256 MiB、`grow`)

`Heap.collect` の掃除の直前に、オブジェクトの一覧をたどって `marked` を数えるだけの走査(ダミーの走査)を入れ、その時間を、掃除の時間と並べて測った。回収は 129 回。

| 項目 | 合計 |
| --- | --- |
| マーク | 19.6 秒 |
| ダミーの走査(一覧をたどるだけ) | 20.3 秒 |
| 掃除(一覧をたどりながら解放する) | 20.4 秒 |
| 掃除からダミーの走査を引いた分(解放の費用に当たる) | 0.12 秒 |

最後の回収で、生きているオブジェクトは約 489 万個。1 個あたり、マークが約 117 ns、ダミーの走査が約 110 ns だった。

1 個あたり約 100 ns は、主記憶へのアクセスの待ち時間の大きさである。確かめるために、5 百万個(1 個 48 バイト)の連結リストを、メモリの順にたどる場合と、順序を乱してたどる場合で、1 個あたりの時間を測った(小さな単体の実験。`zig build-exe -O ReleaseFast`)。

| たどり方 | 1 個あたり |
| --- | --- |
| メモリの順 | 8.3 ns |
| 順序を乱した | 148.6 ns |

掃除の約 105 ns は、順序を乱した側に近い。したがって、掃除の時間は、`Header.next` の連結を、散らばったメモリの上でたどる待ち時間が決めている。H2 の callgrind で見えた「解放が命令数の約 15%」は、時間にはほとんど表れない(解放の費用は、たどりの待ちの陰に隠れる)。

### 閾値の倍率を上げる試作は、ほとんど効かない

`Heap.collect` の `live *| 2` を `live *| 4` にした版(試作)を測ると、43.5 秒が 41.7 秒(約 4% 減)になっただけだった。回収の回数が多い前半(97 回)は、全体の時間の主因ではない。この案は、メモリの常駐量が増える代償に見合わないので、候補から外す。

### 過去の案 C と、`Why` コメントの読み直し

- [handoff.md](../handoff.md) の判断の履歴(2026-10-19)は、案 A を採った事実と、案 B(`SafeAllocator` の設定変更)と案 C(ヒープのセルを自前のスラブに載せる変更)を示していたことだけを記している。案 C を退けた理由は、書かれていない。したがって、案 C は、その場の不具合を直すには案 A で足りたので採られなかっただけで、長所と短所を比べた上で退けられたのではない。
- `src/heap.zig` の `large_resident_bytes` の `Why` コメントは、実行ファイルの割り当て器そのものを替える案が、`vm.max_map_count` を超えて異常終了したこと(`tests/cli-slow/multi-list-map.scm`)と、常駐の確保だけをページ単位の割り当て器に回して伸びを抑えたことを記している。新しい確保の方式は、領域の `mmap` の数を増やさない大きさ(64 KiB 以上のチャンクなど)で取る必要がある。
- `Marker` の `Why` コメントは、再走査が、オブジェクトの一覧を新しい順に1回なめる前提で、深い鎖で再走査の回数が鎖の長さに比例することを記している。一覧の順序を変える設計は、この前提を崩さないか、確かめる必要がある。

### 案 B の具体的な手(候補と見込み)

#### 手 B1: 掃除を、連続したメモリの走査にする(勧める)

セルを、一定の大きさのチャンク(64 KiB 以上)から切り出し、掃除を、`Header.next` の連結でなく、チャンクの連続した走査にする。解放されたセルは、種類ごとの空きリストに戻す。ペイロード(`Frame` のスロットなど)は、今までどおり別に確保する。

- 見込み: 掃除の約 20 秒のうち、たどりの分(約 20 秒)を、連続走査の速度(上の実験で 8.3 ns/個)にできると、約 1.5 秒になる。ただし、`Frame` などのペイロードの解放が、たどりの陰から出て、時間として見えてくる。その大きさは測っていない。掃除が約 1.5 秒から 10 秒の間に入るとすると、全体は 43.5 秒から約 25 秒から 33 秒になる見込みである(見込みであり、実測ではない)。
- 変更の範囲: `src/heap.zig` の中に収まる見込み。`objects` を使う箇所は、`deinit`、`sweep`、`countOf`、`link`、`Marker.finish` の再走査(`Heap` の外では、`src/trace.zig` のテスト用の配列だけで、一覧とは別物)。セルの大きさと `Header` の配置は、変えなくてよい。
- 見込みの扱い: 上の 25 秒から 33 秒は、連続走査の速度(実験の 8.3 ns/個)と、ペイロードの解放が陰から出る分の上限(掃除の約半分)から置いた範囲で、B1 を作って測った値ではない。実測がこの範囲に入らないときは、計画書のこの節を、実測で書き直す。
- 止める条件: B1 の最初のコミット(`objects` 一覧をチャンクの走査に替えるところまで)で、`grow` の掃除の合計が 10 秒を下回らなければ、そこで止めて報告する(H1 の計装と同じ方法で測る)。
- リスク(`Marker` の再走査の順序): `Marker.finish` の再走査は、`objects` 一覧(新しい順)を1回なめる前提で書かれている。チャンクの走査は、チャンクの中のアドレス順になるので、新しい順と一致しない。再走査は、作業リストを伸ばせないときの退避の経路で、通常は走らない(H1 の計測で、回収 129 回すべてで 0 回)。ただし、順序に依存するテストが 2 つある(`src/heap.zig`)。
  - `when the marking list cannot grow the marking rescans, as many times as the spine is long, and still finishes`: 背骨が新しいペアへ向く入力で、再走査の回数が 40 回以上であることを求める。新しい順の走査が遅くなる向きを固定している。アドレス順の走査では、この向きは速くなり、回数が減って、このテストは落ちる見込みである(B1 を作って確かめるまでは、推測)。
  - `an object a rescan puts on the list is scanned before the rescan ends`: 再走査の途中で積んだオブジェクトを、再走査の後でリストを空にして走査することを確かめる。`y`、`z`、`w` の新旧の順に頼る入力で、走査の順が変わると、確かめたい性質を通らずに通るテストになりうる。
  - 確かめ方: B1 の最初のコミットで、この 2 つが、順序を替えたあとも、同じ性質を確かめているかを、ミューテーション(再走査の後の `drain` を外す、再走査の回数を固定する)で確かめる。必要なら、順序の向きを逆にした入力を足す。再走査の順序は、設計として決める(新しいチャンクから逆のアドレス順に走査して、確保が新しい順の近似を保つか、順序を保証せず、テストを性質だけにするか)。この選択は、B1 の PR に、理由つきで書く。
- リスク(その他): `vm.max_map_count`(上の `Why` コメント)。チャンクを返す時期(使わなくなったチャンクを OS に返すか)を決める必要がある。

#### 手 B2: 確保を、アドレスの順にする(B1 の上に載る。効果は未知)

掃除のあと、空きのセルを、アドレスの低いほうから使う。リストを `cons` で伸ばす入力では、鎖の順とアドレスの順がそろい、マーク(約 20 秒)のたどりも連続に近づく見込みがある。

- 見込み: 上の実験の 8.3 ns と 148.6 ns の差が、そのままは出ない(鎖と確保の順が一致するのは、特定の入力だけ)。実測するには、B1 を作ってから、空きの選び方だけを替えて比べる必要がある。ここでは、効果を見積もれない。
- リスク: 空きのセルの選び方で、確保 1 回の費用が増える可能性がある。

#### 効かない見込みの手

- 解放をスラブに替える: 掃除の時間のうち、解放の分は約 0.12 秒で、時間にはほとんど表れない(上の表)。命令数の約 15% は、時間の改善に結びつかない見込み。B1 の中で、空きリストとして自然に入るので、単独では行わない。
- マークの先読み(prefetch): 先読みの対象は、同時に複数の取り出し先があるときに効く。リストの鎖は、次の取り出し先が1つしかないので、効かない見込み(推測。測っていない)。
- 閾値の倍率を上げる: 上の試作で約 4% 減にとどまった。

#### 勧める手

B1 を、小さく切って進める。最初のコミットでは、`Heap` の `objects` 一覧を、チャンクの走査に替えるところまでにして、`grow` の時間を測る。掃除の時間が 10 秒を下回らなければ、そこで止める。B2 は、B1 の結果を見てから判断する。

## 原因の仮説と、確かめたこと

### 仮説

回収の方針(`Heap.collect`)は、次の回収の閾値を `min(softLimit, max(min_threshold, 生きている量 × 2))` にする。生きている量が `softLimit` の半分を超えると、閾値は `softLimit` に張り付く。そこから先は、「`softLimit` までの余裕」(生きている量が増えるほど縮む)を使い切るたびに全ヒープの回収が走り、1 回の費用は生きている量に比例する。回収の間隔は縮み、1 回の費用は伸びるので、上限の近くで時間が積み上がる。誤りは、回収のあとの生きている量が `limit - 2 × limit/16`(224 MiB)を超えたときに出る(`exhausted`)ので、そこまで、この状態が続く。

仮説の内容は、非移動の全体回収に、固定の上限を組み合わせたときの、一般的な性質である。この実装に固有の欠陥とは、まだ言えない。

### 確かめた証拠

- 回収が時間の約 93% を占める(上の表)。プログラムの実行の時間ではない。
- 回収の間隔の縮みと、1 回の費用の伸びが、後半の回収の記録で見える(上の節)。
- マークの作業リストはあふれない(再走査が 0 回)ので、再走査による 2 乗の増加は、この入力では起きていない。
- 同じバイト数でも、大きなセルを少数作る入力(`make-vector` を重ねる)は、0.37 秒で上限に届く。時間は、バイト数ではなく、オブジェクトの数に比例して伸びる。
- 末尾でない再帰は 11.8 秒で、`grow` より短い。生きている割合が高く、確保 1 回あたりの回収の費用が違う見込みだが、確かめていない。
- 64 MiB 以上では、時間が上限にほぼ比例する(H2 の表)。仮説の読み方を、次のように改める。閾値の方針は、上限に対する比率で決まるので、回収の回数は上限によらず同じ程度になり、1 回の費用が生きている量に比例して、全体が上限に比例する。回収の回数が上限によらず同程度であることは、256 MiB でしか数えていないので、確かめていない。
- 掃除の中では、オブジェクトごとの解放(`Heap.free`)が、一覧をたどる分より大きい(命令数。H2 の表)。

### まだ確かめていないこと(確かめ方つき)

- 1 個あたり約 224 ns が、メモリの参照の局所性の悪さ(一覧が新しい順で、セルが散らばる)によるものか。確かめ方は、キャッシュのミス率の計測(`valgrind --tool=cachegrind` を、上限 16 MiB の ReleaseSafe の `-Dcpu=baseline` 版で走らせる)。ただし、シミュレートされたキャッシュで、この環境の実機のキャッシュではない。
- Debug の回収の割合(時間)。命令数では約 52% だが、時間の割合は取っていない。確かめ方は、`Heap.collect` への時間の計装を Debug で入れて測ること。
- 上限を変えたときの回収の回数。上の読み方の裏づけになる。確かめ方は、上限 64 MiB と 128 MiB で、`Heap.collections` を終了時に出す計装を入れること。
- 16 MiB から 64 MiB の伸びが比例より大きい理由。
- 以前の観測との差(約 14% と約 9%)の原因。
- `grow` の 1 反復で回収の対象になるセル(最初の回収で保持量の約 63% が空く)が、何のセルか。
- 層の時間目標への影響の実測。`0012-gc-scale` の入力の Debug での時間と、層2の中での割合。`tools/test-wasm/main.mjs` の上限と時間。
- 案 B の効果は、H3 の計測で見積もった(上の節)。解放をスラブに替える案は、時間にほとんど効かない見込みになった。B1 の実際の効果は、実装して測るまで確定しない。

## 選択肢(実装はしない)

すべて、設計の判断に関わるので、判断を得てから実装する。

### 案 A: 回収の効き目が薄いときに、早めに誤りにする

最近の回収で空いた量が上限の一定の割合に満たない状態が続いたときに、`heap limit exceeded` を出す(JVM の「GC overhead limit exceeded」と同じ考え方)。

- 長所: 実装が小さい。最悪の待ち時間に、確実に上限をかけられる。
- 短所: 挙動が変わる。上限の 256 MiB を使い切れるプログラムが、使い切る前に誤りになりうる。割合の決め方が新しい設定になる。正しいが生きている量の多いプログラム(大きな表を持つもの)を誤って止める危険がある。
- 影響: `heap limit exceeded` が出る条件は、リファレンスの「実装の上限」、`docs/design/` のヒープの文書、ADR の記述に関わる。

### 案 B: 回収 1 回の費用を下げる(挙動は変えない)

マークと掃除の定数倍を縮める。当初の候補は、掃除でのセルの解放を、種類ごとの固定の大きさのスラブに任せること、マークの先読み(prefetch)、一覧を詰め直すことだった。H3 の計測で、掃除の時間は解放でなく一覧のたどり(メモリ待ち)が決めていると分かったので、候補を、上の「案 B の具体的な手」(B1: 連続走査、B2: アドレス順の確保)に改めた。

- 長所: 挙動を変えない。上限の近くで時間が積み上がる形は残るが、全体が縮む。
- 見込み(H3 の計測から): B1 で、43.5 秒が約 25 秒から 33 秒になる見込み。桁は変わらない。B2 の効果は見積もれない。
- 短所: 効果は、実装して測るまで確定しない。ヒープの構造(セルの確保と一覧)に触れる。`Marker` の再走査の前提と、`large_resident_bytes` の経緯(`heap.zig` の `Why` コメント)に注意が要る(上の節)。過去の案 C(自前のスラブ)は、退けた理由が記録されていない。

### 案 C: 確保の量を減らす

末尾呼び出しのループの 1 反復が、回収されるだけの `Frame`、`Args`、継続のセルを作る分を減らす。たとえば、捕捉されないフレームの再利用。

- 長所: 通常の実行も速くなる。ヒープの方針は変わらない。
- 短所: 評価器の不変条件(ADR-0031、ADR-0040)に触れる。効果は、確保の何割が避けられるかによる。後半の回収の費用は、生きている量が決めるので、避けた分だけ回収の頻度が下がるにとどまる見込みだが、確かめていない。

### 案 D: 世代別回収、または増分回収

- 長所: 上限の近くの全体回収の繰り返しを、根本から避けられる。
- 短所: 大きな設計変更で、移動しないヒープ、ルートの扱い、WASM のサイズに波及する。この問題の大きさに比べて、費用が大きい。

### 案 E: 何も変えず、文書で説明する

[リファレンスの「実装の上限」](../manual/reference/limits.md)に、時間が掛かることはすでに書いてある。

- 長所: リスクがない。
- 短所: 40 秒を超える待ちが残る。

### 勧める案

案 B を、小さく試す形で勧める。理由は、挙動を変えないことと、H2 の計測で、解放と確保とマークに、命令数の上で縮められる余地が見えたことである。B の見込みは、40 秒が半分程度になる、と控えめに見ている。桁を変えて待ち時間を縮めたい場合に限り、案 A を足す。A は挙動を変えるので、B の結果を見てから、あらためて判断を求める。C と D は、この問題だけを理由には勧めない。E は、B の結果が出るまでの現状である。

## 判断を求める点

2026-11-11 に、ユーザーが、次の2点を、勧めた案のとおりに決めた。

1. 案 B(挙動を変えない費用の削減)を、H3 として進める。最初の一手は、案 B の効果の見積りに要る計測(上の「まだ確かめていないこと」)で、効果が小さければそこで止めて報告する。
2. 待ち時間の上限を、挙動の変更(案 A)で設けることは、今はしない。B の結果を見てから決める。A を選ぶ場合は、割合の決め方と、`heap limit exceeded` の条件を書いた文書(リファレンスの「実装の上限」、ヒープの設計文書、ADR)の更新が要る。

この PR は、文書だけである。H3 の実装は、別のブランチで、計測のあとに、結果と案 B の具体的な手を報告してから始める。

## 再現の手順

計測を入れていない通常の実行ファイルで、時間だけを測れる。

1. `zig build -Doptimize=ReleaseSafe --prefix <出力先>` で実行ファイルを作る(Debug は `-Doptimize` を付けない)。
2. 上の2行を、ファイルに書く。
3. `time <出力先>/bin/sucheme <ファイル>` を走らせる。終了コードは 1 で、標準エラーに `error: heap limit exceeded` が出る。

回収ごとの内訳は、`Heap.collect` の前後に `std.posix.system.clock_gettime(.MONOTONIC, ...)` を置き、`self.held()`、`self.count`、`self.rescans` とともに `std.debug.print` で出す一時的な変更で取った(コミットしない)。
