# 0003: 段階1の実装計画 — 通しで動く最小の縦切り

- 対応する決定: [ADR-0018](../adr/0018-incremental-vertical-slices.md), [ADR-0027](../adr/0027-severity-by-consequence-and-a-cost-side-stop.md)
- 段階: 1
- 日付: 2026-10-09

## この計画が解こうとしている問題

[roadmap.md](../roadmap.md) の段階1は14個の作業項目を持ち、完了条件が「階乗の定義と呼び出しがネイティブとブラウザの両方で動く。100万回の末尾再帰が一定のメモリで完了する。未処理例外の経路が動く」である。値表現・ヒープ・GC・リーダ・プリンタ・展開器・CEK機械・プリミティブ・REPL・WASM・Web UI が全部そろう。

これを1つの PR にすると、段階0で起きたことが繰り返される。レビューの対象が大きいほど指摘は増え、修正が次の指摘を生み、どこで止めるかの判断が効かなくなる。段階0の経緯は [review/stage0-findings.md](../review/stage0-findings.md) にある。

そこで段階1を、それぞれ単独でマージできる縦切りに割る。各切片は「通しで動く」ことを保ち、完了条件を1行で書ける大きさにする。

## 切片

各切片は1つの PR になる。前の切片がマージされてから次を始める。

| 切片 | 完了条件 | 新しく入るもの |
| --- | --- | --- |
| 1a | `zig build run` で `(+ 1 2)` と打つと `3` が返る | 値表現(固定長整数のみ)、リーダ(整数・括弧・空白)、プリンタ(整数)、評価器(呼び出しのみ)、プリミティブ `+`、素朴な REPL |
| 1b | `(define x 1)` と `x` が動く。未定義の識別子がエラーになり REPL が止まらない | シンボルのインターン、環境、`define`、未処理エラーの報告経路 |
| 1c | `(if #f 1 2)` と `(quote (1 2))` が動く | 真偽値、空リスト、ペア、`quote`、`if`、リーダのリストと `'` |
| 1d | `((lambda (x) (+ x 1)) 2)` が動く | 手続き値、`lambda`、`begin`、`set!`、引数の束縛。局所変数は名前で引く環境フレームで表し、字句アドレスは使わない |
| 1e | `(define (fact n) (if (= n 0) 1 (* n (fact (- n 1)))))` と `(fact 10)` が動く | 再帰、プリミティブの拡充(比較と算術)、内部定義 |
| 1f | 100万回の末尾再帰が一定のメモリで完了する | CEK機械への移行(明示的な継続)、末尾呼び出し、展開器とコアIRの最小集合、字句アドレス |
| 1g | GC が動く。ヒープを使い切らずに 1f が完了する | GCヒープ、マーク・スイープ、ルート登録 |
| 1h | 文字列・ベクタ・文字が読めて書ける | リーダとプリンタの残り(ドット対 `(1 . 2)` の読み取りを含む。1c のプリンタは書けるが、リーダは `.` を読めない)、`write` と `display` の区別 |
| 1i | ブラウザで `(fact 10)` が動く | WASM のエクスポート、Web UI の最小版、ローカルで開く手段 |
| 1j | リリース v0.1.0 | ファジングのワークフロー、aarch64 の判断と ADR、PR への成果物の添付 |

1a から 1e までは、素朴な再帰下降の評価器で進める。1f で CEK 機械に置き換える。先に CEK を入れないのは、評価器の形を決める前に継続の形を決めると、どちらも推測で書くことになるためである。置き換えのときに 1a から 1e のテストがそのまま通ることが、移行が正しいことの根拠になる。

## 再開の手がかり

コードが正であり、ここには ADR にも設計文書にも無い、実装中の決定と環境の事実だけを書く。

- 実装中の決定: 評価器は 1f まで `Value` を直接解釈する再帰関数で、展開器もコアIRも無い。リーダは `Value` を `Interpreter` の永続アリーナに直接作る(`quote` が定義に渡すため)。このアリーナと、シンボル表と大域環境は 1g の `heap.zig` まで回収されない。特別な形は `src/eval.zig` のキーワード表で扱い、変数にも再定義にも使えない。`define` は最上位だけ(深さ 0)。Scheme のエラーは Zig の error と、`Context` が持つ文言の組で、1f で条件オブジェクトに置き換える。
- 深さの上限: `max_depth` は評価の再帰の深さの上限で、`src/eval.zig` の小さいスタックのテストが 512KiB のスレッドで最深の入力を評価して守る。形を足すか1段のスタックを増やしたら、そのテストが落ちる。落ちたら上限を下げる。
- テストの書式: `tests/scheme/*.txt` は、入力の行、期待する出力の行、空行の順。出力が空のケースは期待する行に `<no output>` と書く。書式は `tools/test-scheme/main.zig` の doc コメントが正。
- レビュー: 切片の PR ごとに、設計の意図を渡さないサブエージェントに `adversarial-review` を1巡させる。機械の検査を壊して確かめるときは `tools/review-harness/harness.py` を使う。
- 環境の事実: 実行環境から ziglang.org に届かないことがある。その場合は `python3 -m venv <dir> && <dir>/bin/pip install ziglang==0.17.0` で入れ、`zig` を PATH に置く(`.zigversion` と一致することを `zig version` で確かめる)。
- ブランチ: 作業用ブランチは1本で、PR がマージされたら `main` から作り直す(`git checkout -B <同じ名前> origin/main`)。マージ済みの履歴しか持たないブランチの強制プッシュは `--force-with-lease` で行う。

GC を 1g まで遅らせるのは、1f までのヒープ使用量が小さく、アリーナで足りるためである。1f で末尾再帰が一定のメモリで回ると、初めて「回収しないと終わらない」状態が作れる。GC の正しさは、回収が必要な状況で初めて検査できる。

## この計画が決めていないこと

[design/open-questions.md](../design/open-questions.md) の「段階1までに決める」の行は、この計画では決めない。各切片で、その切片が必要にした時点で決める。どの切片でどれを決めるかは次のとおりである。

| 切片 | 決める事項 |
| --- | --- |
| 1b | 内部値のうち未束縛の表現。大域環境に名前が無いことで表したので、専用の値は要らなかった。1a で決める予定だったが、1a には束縛が無く使う箇所が無いので 1b に移した |
| 1e | 内部値のうち未初期化の表現。内部 `define` が入る 1e で初めて要る |
| 1f | 字句アドレスの深さと添字のビット幅、または実装制限として報告する閾値。1d は局所変数を名前で引く環境フレームにしたので要らなくなり、展開器とコアIRが入る 1f に移した |
| 1f | フレーム数に上限を設けるかどうか、設けるなら設定手段 |
| 1g | GCの起動の閾値、予約領域の具体的なバイト数、ヒープ外ペイロードと所有者の確保の巻き戻しの単位、作業リストの予約サイズ |
| 1h | Windows の引数と環境変数を UTF-16 から変換したときの不対サロゲートの扱い |
| 1i | WASM の出力バッファの初期サイズと伸ばし方、Web UI をローカルで開く手段と PR の zip を開く手段 |
| 1j | aarch64 を自動テストの対象に加えるか |

検査ツールについての未決事項(`refAllDecls` の到達性、`test_excluded` の理由、CI が表の行を走らせる検査の範囲、フックの判定の機械検査)は、この段階では決めない。段階0の経緯から、検査ツールを育てることが製品を作ることに先立ってはならない([ADR-0026](../adr/0026-verify-facts-about-code-not-prose.md))。製品コードが育って同じ誤りが2回起きたときに決める。

## 各切片の進め方

1. その切片の完了条件を満たす失敗するテストを書く(Red)。
2. 最小の実装で通す(Green)。
3. テストを通したまま整理する(Refactor)。
4. `AGENTS.md` の検証コマンドを全部通す。
5. PR を作り、敵対的レビューを1巡かける。重要度は [ADR-0027](../adr/0027-severity-by-consequence-and-a-cost-side-stop.md) の帯で採点する。
6. 必須が帰結(1)(2)(3)に当たらなくなったらマージを依頼する。
7. 同じ PR で、この計画書の進捗の表と「次にやること」、切片で決めたことの表を更新する。

レビューの対象はその切片の差分に限る。既存の文書の全面再走査はしない。段階の終わりに1回、計画書と帳簿を見る([ADR-0027](../adr/0027-severity-by-consequence-and-a-cost-side-stop.md))。

## 検証コマンドの追加

段階1で `AGENTS.md` の検証コマンド表に次の行が必要になる。追加は、その行が指すものが実在する切片で行う。

| コマンド | 切片 |
| --- | --- |
| `zig build test-scheme` | 1a(Scheme の振る舞いのテストが最初に要るところ) |
| `zig build wasm` | 1i |
| `zig build test-wasm` | 1i |
| `zig build report` | 1e(準拠マトリクスに載る識別子が増え始めるところ) |
| `zig build check-report` | 1e |

1a で `build.zig` の `current_stage` を1に上げたので、段階1の全コミットの行は `zig build check-docs` が CI に要求する。そのため 1a の時点で表にあった `wasm`・`test-wasm`・`report`・`check-report` の4行をいったん外した。上の表の切片で戻す。

戻す行の意味は次のとおり。`zig build test-wasm` は Node.js 上でエクスポートを呼び出す往復テストである([ADR-0010](../adr/0010-ci-cd-and-release-strategy.md))。`zig build check-report` は準拠マトリクスを生成し直して現在のファイルと一致するかを検査する([design/r7rs-coverage.md](../design/r7rs-coverage.md))。`zig build report` は生成するだけで一致を検査しない。

`.github/workflows/ci.yml` の変更を伴うので、各切片でユーザーの承認を得てから行う([AGENTS.md](../../AGENTS.md) のセキュリティの節)。

## 次にやること

切片 1d に入る。完了条件は `((lambda (x) (+ x 1)) 2)` が `3` になること。決定済みの事項は、局所変数を名前で引く環境フレームにすること(ユーザー承認済み)。コアIRと字句アドレスは 1f で入れる。

進め方の案。これは案であり、実装中に見つかったことで変えてよい。

1. Red: `tests/scheme/0006-lambda.txt` に、`lambda` の呼び出し、引数が複数、本体が複数式、クロージャが外側の引数を捕まえること、`begin`、`set!`(局所と大域、未束縛への `set!` はエラー)、引数の個数の違い、手続きでないものの呼び出しを置く。
2. 手続き値: `Value` に、クロージャ(引数名の列、本体、環境フレーム)とプリミティブの変種を足す。プリミティブを大域環境の束縛にして、`+` を変数として参照できるようにし、`VariableReferenceUnsupported` と、プリミティブを名前で探す経路をなくす。`(define + 5)` が `+` を隠す挙動は束縛の置き換えとして自然に残る。
3. 環境フレーム: 記号IDの列と値の列と親への参照を持つ。参照は内側のフレームから探し、無ければ大域環境を見る。
4. 形: `lambda`(引数は記号の列だけ。可変長引数 `(a . rest)` はドット対のリーダが入る 1h 以降)、`begin`(最上位の `begin` の中の `define` を許すかを決める)、`set!`。キーワード表に足す。
5. 手続きの外部表現と、呼び出しごとの深さ: プリンタに手続きの書き方(例: `#<procedure>`)を足す。呼び出しは再帰の深さを1段増やすので、小さいスタックのテストに `lambda` の呼び出しを加え、`max_depth` を測り直す。
6. 検証コマンドを全部通し、新しい判定の変異試験、PR、敵対的レビュー1巡、この計画書の更新の順に進める。
