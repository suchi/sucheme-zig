# 0026: 層2の slow tests を、検査を減らさずに短くする

- 対応する計画: [0007](0007-test-tiers.md)(テストの層)、[0015](0015-ci-minutes-reduction.md)(Actions の分数)、[0022](0022-layer2-measurement.md)(層2の `test-scheme -Dslow=true` の測定)
- 日付: 2026-10-24
- 状態: 合意済み(2026-10-24)。「合意を求める点」の4項目すべてを、勧める案どおりにユーザーが承認した

## 解こうとしている問題

層2(`full.yml`)の `slow tests (ubuntu-latest)` のジョブは、PR を ready にするたびに走り、CI で約 33 分かかる。内訳は、`zig build test -Dslow=true` が約 11 分、`zig build test-scheme -Dslow=true` が約 17 分、`zig build test-wasm -Dslow=true` が約 2 分である(ワークフローの実行の一覧からの概算)。この時間は、マージの判断の待ちになり、private リポジトリの実行分数の枠にも計上される。

この計画は、検査の中身(ケース、モード、規模)を変えずに、同じ検査を速く走らせる案をまとめる。規模を下げる案や、ストレスモードを外す案([0022](0022-layer2-measurement.md) の案 b)は、検査を減らすので採らない。

## 現状の調査

### 親のセッションの測定(2026-10-24)

4 vCPU の VM での測定である。倍率を主に読み、絶対値は参考にとどめる。

- `zig build test -Dslow=true`(既定の Debug)は、壁時計で 558 秒だった。`-Doptimize=ReleaseSafe` を付けると 166 秒で、約 3.4 倍速い。テストの実行だけを比べると、約 590 秒が約 20 秒になり、約 29 倍である。
  - 上位 10 件のテストが、実行の時間の 88.5% を占める。1 位は「ステップ上限なしで 100 万回の呼び出しが終わる」で、Debug で 203 秒、ReleaseSafe で 4.3 秒だった。
  - 2つの最適化の間で、結果に食い違いは無かった。1079 件とも同じテスト名の集合で、全件が通った。
- `test-scheme` と `test-wasm` は、`build.zig` が `ReleaseSafe` に固定している。`-Doptimize` では変わらない。
- `test-scheme -Dslow=true` が時間の大半を占める(手元で約 20 分)。
  - 遅い 4 ファイルが、全 16 ファイルの合計 780 秒の約 75% を占める。内訳は、`0020-list-procedures-scale` が 190 秒、`0013-list-scale` が 145 秒、`0024-higher-order-and-delay-scale` が 139 秒、`0019-apply-values-scale` が 108 秒である。
  - 1 つのプロセスで全部を走らせると 1216 秒だった。ファイルごとに走らせた合計は 780 秒で、層1 の 199 秒と合わせて約 979 秒になる。1 プロセスのほうが、約 240 秒長い。原因は確かめていない。

[0022](0022-layer2-measurement.md) の測定(2026-10-20)では、時間の約 81% が、規模を試すケースを「1ステップごとに GC するモード」で走らせた分だった。今回の測定と、ファイルの順位はほぼ同じである。

### ランナーの作り(`tools/test-scheme/main.zig` を読んで確かめた)

- `main` は、`init.arena` を汎用の確保器(`gpa`)として使う。ファイル名、ファイルの中身、解析したケース、ケースごとの出力の複製は、このアリーナに確保され、実行の終わりまで解放されない。
- ケースごとの `evaluate` は、`evalPrint` の作業用に、`gpa` を親とする `ArenaAllocator` を作り、終わりに `deinit` する。出力も `std.Io.Writer.Allocating.init(gpa)` に書く。親がアリーナなので、子が返したメモリは、親で再利用されない見込みである(推測。std の `ArenaAllocator` が、最後の確保以外の解放を無視することによる。確かめていない)。
- インタプリタのヒープは `std.heap.smp_allocator` に確保する。ヒープの解放はアリーナを通らない。
- ファイルは、ディレクトリごとに名前でソートし、1 つのスレッドで順に走らせる。ケースごとに、既定のモードと「1ステップごとに GC」のモードの2回を走らせる。
- 失敗の報告は、ファイルの順、ケースの順に標準エラーに書く。最後に通った数と落ちた数を書く。

### 確かめられなかったこと

- GitHub の標準ランナーの vCPU の数。private リポジトリでは 2 vCPU だと理解しているが、未確認である。この環境から公式文書(docs.github.com)に届かなかった(名前の解決に失敗した)。並列にする案の見積りは、2 vCPU を仮定している。
- `zig build test` が使う `std.testing.allocator` が、ReleaseSafe でも漏れを報告するか。Zig 0.17.0 の `lib/std/testing.zig` は `std.heap.SafeAllocator` を使う。`lib/std/heap/debug_allocator.zig` の `safety` の既定値は `std.debug.runtime_safety` で、ReleaseSafe でも有効だが、スタックトレースの記録は Debug のときだけである。`SafeAllocator` の振る舞いは、スライス S1 で確かめる。

## 案

### 案1: `zig build test -Dslow=true` を ReleaseSafe で走らせる

ワークフローの行は変えない。`build.zig` で、`-Dslow=true` が指定され、かつ `-Doptimize` が指定されていないときに、単体テストのバイナリの最適化の既定を `ReleaseSafe` にする。ワークフローの行を変えると、`check-docs` が照合する検証コマンド表と `full.yml` の綴りに触れるので、まずこの形を検討する。

- 見積り: CI の `zig build test -Dslow=true` が約 11 分から約 3 分になる(推測)。手元の壁時計の 3.4 倍が CI でも同じと仮定した値で、CI では測っていない。コンパイルの時間は ReleaseSafe のほうが長いので、実行だけの 29 倍は CI の壁時計には出ない。
- 長所:
  - 検査(境界、オーバーフロー、アサーション)は残る。ReleaseSafe は安全検査を外さない。
  - `test-scheme` と `test-wasm` は、すでに ReleaseSafe で走っている。層2の3つのコマンドの最適化がそろう。
  - ワークフローと検証コマンド表を変えない。
- 短所:
  - Debug は、`undefined` のメモリを 0xaa で埋める。ReleaseSafe は埋めない。未初期化のメモリを読む誤りは、Debug では値の食い違いとして表に出やすいが、ReleaseSafe では見えにくくなる。
  - 確保器のスタックトレースが記録されなくなる(上の「確かめられなかったこと」)。漏れが見つかったとき、どこで確保したかが報告に出ない。
  - `-Doptimize` を指定しないときの意味が、`-Dslow` の有無で変わる。指定したときは、指定が優先する。
- 縮小版: 層1の `zig build test` は、規模を試すテストの縮小版を含み、Debug のまま走る。上の短所の2つは、縮小版では残らない。
- 触るファイル: `build.zig`。ADR を1つ足す(層2の単体テストを ReleaseSafe で走らせる決定)。

### 案2: test-scheme のランナーの、1 プロセスでの遅れの原因を調べて直す

1 プロセスで全ファイルを走らせると、ファイルごとの合計より約 240 秒長い。原因を、実測で確かめてから直す。

- 調べる仮説(推測):
  - 仮説 A: `gpa` がアリーナなので、ケースごとの作業用のアリーナと出力の確保が親に積み上がり、メモリが増え続けて遅くなる。
  - 仮説 B: `smp_allocator` が、インタプリタを作っては壊すうちに断片化する。
  - 仮説 C: ページキャッシュや CPU の周波数など、ランナーの外の要因。
- 調べ方: 使い捨ての作業ツリーで、ファイルごとの時間と最大常駐メモリ(`/usr/bin/time -v` の Maximum resident set size)を記録する。仮説 A は、ケースの作業用の確保の親を `smp_allocator` に替えた一時パッチで、時間が戻るかを見る。仮説 B は、ファイルごとに子プロセスに分けた一時パッチで、時間が戻るかを見る。
- 直し方の候補: 仮説 A なら、ケースの作業用のアリーナと出力の親を、解放を返す確保器に替える。数行の変更である。
- 見積り: 1 プロセスの約 1216 秒が、ファイル別の合計の約 979 秒に近づく(約 20% の短縮)。CI では約 17 分が約 13 〜 14 分になる見込み(推測。手元の比を CI に当てはめた値)。仮説が外れたら、効果は無い。
- 長所: 検査の中身と並びを変えない。層1の `zig build test-scheme` にも、同じ割合で効く見込み(推測)。
- 短所: 原因が仮説 A でなければ、直すのに子プロセス化などの大きな変更が要る。そのときは、調べた結果を報告して、案3と合わせて決め直す。
- 触るファイル: `tools/test-scheme/main.zig`。

### 案3: test-scheme のランナーで、ファイルを並列に走らせる

ランナーが、ファイルを複数のスレッドに振り分けて走らせる。各ファイルのケースは、今までどおり順に、両方のモードで走らせる。並列にしても、走らせるケースとモードは同じである。

- 振り分け: 作業の待ち行列にファイルを入れ、スレッドが1つずつ取る。スレッドの数は `std.Thread.getCpuCount()` で決め、上限を設ける。
- 報告: 各ファイルの結果を、ファイルごとのバッファに書き、全部が終わってから、今までの順(ディレクトリごと、名前の順)に標準エラーに出す。報告の順は、並列にしても変わらない。
- スレッドで分けるか、子プロセスで分けるか:
  - スレッド: インタプリタのインスタンスがスレッドの間で状態を共有しないことが前提になる。`src/` のファイル単位の可変の大域変数は、`src/wasm.zig`(WASM の入口だけ)と、`src/heap.zig` の長さ0の配列だけだった(`grep` で確かめた)。ヒープの確保器 `smp_allocator` は、複数のスレッドから使える。
  - 子プロセス: 状態の共有の心配が無いが、ランナーの「引数を取らない」規則(`main` の最初の検査)と、`build.zig` の `checkStepRuns` の前提に触れる。環境変数で渡す形が要る。
  - スレッドを勧める。前提が崩れていたら、子プロセスに切り替える。
- 見積り: 2 vCPU を仮定すると、規模を試す分の実行は、最長のファイル(手元で 190 秒)と、合計の半分(約 390 秒)の大きいほうで決まり、約 390 秒になる(推測)。CI の約 17 分が、約 8 〜 9 分になる見込み(推測)。案2 を先に入れると、さらに縮む。
- 長所:
  - 検査の中身を変えずに、壁時計と計上の分数がともに縮む。
  - 層1の `zig build test-scheme`(手元で約 199 秒)と、層2の windows ジョブの `zig build test-scheme` にも効く。
- 短所:
  - ランナーが大きくなる(待ち行列、スレッド、報告の並べ替え)。
  - 1 vCPU のランナーでは効かない。
  - メモリの使用量が、スレッドの数の倍数で増える。案2 の原因が仮説 A なら、案2 を先に入れないと、メモリが足りなくなるおそれがある。
- 触るファイル: `tools/test-scheme/main.zig`。報告の並べ替えと、結果の集計を、純粋な関数として切り出し、テストを足す。

### 案4(採らない): 重い 4 ファイルの規模を下げる

`0020`、`0013`、`0024`、`0019` の規模を下げれば、時間は大きく縮む。規模を試すテストは、深さや個数に比例して壊れる種類の誤りを見るためのもので([0007](0007-test-tiers.md))、規模を下げることは検査を減らすことになる。この計画では採らない。[0022](0022-layer2-measurement.md) の案 b(規模を試すケースからストレスモードを外す案)も、同じ理由で採らない。

## S2 の調査の結果(2026-10-24)

仮説 A は否定された。ケースの作業用の確保の積み上がりは確かにあるが、1 プロセスでの遅れの原因ではなかった。完了条件のとおり、コードは直していない。

- 環境: 4 コアのコンテナ。`main`(`57d78c1`)から作った使い捨ての作業ツリーに、ファイルごとの時間と最大常駐メモリ(`getrusage` の `maxrss`)を標準エラーに出す一時パッチを当てた。パッチはリポジトリに載せていない。どの実行も1回ずつで、ばらつきは測っていない。
- 1 プロセスで `zig build test-scheme -Dslow=true` を2通り走らせた。

| | 今のランナー | ケースの作業用の確保を `smp_allocator` に替えた版 |
| --- | ---: | ---: |
| 壁時計 | 2470 秒 | 2520 秒 |
| ファイルごとの時間の合計 | 2406 秒 | 2520 秒 |
| 最後の最大常駐メモリ | 755 MB | 297 MB |
| 通った数と落ちた数 | 8700 と 0 | 8700 と 0 |

- `0020-list-procedures-scale` だけを1 プロセスで走らせると、今のランナーで 348 秒、替えた版で 341 秒だった。全ファイルを1 プロセスで走らせたときの同じファイルは、436 秒と 467 秒で、確保器によらず約 2 割から 3 割遅い。
- この環境の時間は、親のセッションの測定(1 プロセスで 1216 秒)の約2倍である。比べるのは同じ環境の値どうしに限る。
- 残る仮説: 仮説 B(`smp_allocator` の状態が、インタプリタを作っては壊すうちに悪くなる)と、仮説 C(長く走るプロセスに対する、ランナーの外の要因)。確かめていない。
- 決め直し(2026-10-24): 仮説 B と C は調べない。S3 は、承認済みの案3-a(スレッドで分ける)のまま進める。スレッドで分ければ、遅れの原因によらず壁時計が縮むからである。積み上がりの修正(上の替えた版)は、時間には効かないが、スレッドの数の倍数で増えるメモリを抑えるので、S3 に含める。1 プロセスの遅れがスレッドでも出るかは、S3 で記録する。

## 残っていること

S3(suchi/sucheme-zig#196)の敵対的レビューで見つかり、直さなかったもの。

- S3 より前からある、単体テストで固定されていない行が2つある。`tools/test-scheme/main.zig` の `main` で、`.txt` でないエントリを1件の失敗にする行と、終了コードが0でないときに `std.process.exit` を呼ぶ行である。どちらも、1行を消すと `zig build test-scheme` が緑のまま失敗を見落とす。
- 報告は、全部のファイルが終わってからまとめて書く。途中でプロセスが落ちたり止まったりすると、直列のランナーと違い、それまでの報告が出ない。
- `tests/scheme-slow` を開けないとき、先に `tests/scheme` の報告が出ない。
- `tests/scheme` が空でも、`checkMutators` の検査が通るので、終了コードが0になる(S3 より前からある)。
- 確保の失敗がスレッドから伝わることと、スレッドの数を `runFiles` に渡す配線は、単体テストで固定していない。失敗を起こす手段が無く、結果にも効かないためである。
- 重いファイルから先に取る順にすると、スレッドの間の偏りが縮む見込みである。計画の外の変更なので入れていない。
