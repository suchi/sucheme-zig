# サブエージェントの生存確認

バックグラウンドのサブエージェントは、完了すると通知を返す。しかし止められたり落ちたりしたときは、通知が来ない。通知が来ないことは「まだ実行中」の根拠にならない。この手順は、止まっているのに気づかないまま待ち続けることを防ぐ。

## どちらで動かすか

サブエージェント(`Agent` ツール)は、起動したセッションの中で動く。セッションの VM が回収されると、動いていたサブエージェントは失われる。出典は公式の文書で、2026-10-09 に確かめた。

- https://code.claude.com/docs/en/claude-code-on-the-web の「Environment expired」の節。原文は「Not restored: background work that was still running when the VM was reclaimed, such as subagents and shell commands」である。
- https://code.claude.com/docs/en/sub-agents の「Subagents work within a single session」。

次の2点は、文書の記述からの推論と観察で、文書の原文ではない。

- セッションのワーカーの再起動でも、サブエージェントは失われうる。ワーカーの世代が何度も進んだセッションで、サブエージェントが止められた。
- ユーザーがターンを中断すると、動いているバックグラウンドのサブエージェントは止められる。これはユーザーの観察で、確かめた範囲の文書には書かれていない。中断のあとに止められた事例が繰り返され、止まったものを実行中と思い込んで待ち続けた。中断を受けたときの手順は、下の「中断を受けたとき」にある。

長く走る用事(目安として10分を超えるもの)は、別セッションで動かすほうが確かである。別セッションは別の VM で独立して動き、このセッションの中断や再起動の影響を受けない。

- 前提: 渡すブランチは、push 済みでなければならない。VM は GitHub のリモートから取得するので、未コミットや未 push の変更は届かない。
- 起動: `create_session` に、リポジトリの `source_url` と `source_revision`、依頼の本文を渡す。親のセッション ID は `get_session` で得る。
- 依頼の本文に書くこと: 結果を `send_message` で親のセッションへ送ること。着手したときに一言送ること。承認の確認が出る操作(`rm`、`rm -rf`、複製の作成、仮想環境の作成、パッケージの導入など)を避けること。避けられない操作は、やめて、読み取りだけで進められる範囲を報告すること。子のセッションが承認待ちで止まると、親からは代わりに承認できない。
- 確認: `get_session` の `status_bucket` と、`list_events` の末尾で、状態を直接見られる。
- 結果: `send_message` で届く。

短い用事は、サブエージェントでよい。数分で終わると分かっている用事は、バックグラウンドにせず前景で実行する。前景なら、止まったことが実行結果として返る。

## 起動するとき

1. 次を会話に書き残す: 起動した時刻、サブエージェントの名前または ID(別セッションならセッション ID)、終わるまでの目安の時間、打ち切りの時刻、手順 3 で得る予約の `trigger_id`。
2. 依頼の本文に、目安の時間を書き、足りなければ途中までの結果を報告して終わるよう頼む。全部を読み切ろうとして時間を使い切るのを避けるためである。
3. 10分後に自分へ通知する予約を入れる(`send_later` に `delay_minutes` を渡す)。返り値の `trigger_id` を手順 1 の書き残しに加える。通知の本文には、確認する対象、確認の手順、打ち切りの時刻を書く。会話が長くなっても、通知だけで手順に戻れるようにする。

## 通知で起きたとき

結果がすでに届いているなら、確認は要らない。予約が残っていれば取り消す(`delete_trigger`)。届いていなければ、次のとおり確かめる。

別セッションの場合は、`get_session` の `status_bucket` で分ける。

| status_bucket | 意味 | すること |
| --- | --- | --- |
| working | 実行中 | `list_events` の末尾で進み具合を見る。打ち切りの時刻より前なら、さらに10分後の予約を入れ直す |
| blocked | 多くは権限の承認待ち | `get_session` の `post_turn_summary` で、待っている操作を確かめる。ユーザーに、待っている操作とセッションへのリンクを報告する。承認は代わりにしない |
| review_ready, completed | 終わっている | 結果の `send_message` が届いていなければ、取りこぼしである。`list_events` の末尾の発言から結果を読み取る |
| failed | 失敗 | 理由を添えて、ユーザーに報告する |

サブエージェントの場合は、次の順に確かめる。

1. `ListAgents` で、そのサブエージェントの行が残っているかを見る。ツールの説明では、起動したサブエージェントは行に出る。行が残っていれば、実行中として扱い、さらに10分後の予約を入れ直す。
2. 行が無ければ、終了したか、止められたか、落ちたかのどれかである。完了通知が届いていないので、`SendMessage` で短い状況報告を求める。返りで分ける。
   - 「停止された。再開しない」という趣旨: 止められた。結果は無い。直前にユーザーの中断があったなら、下の「中断を受けたとき」に従う。そうでなければ、ユーザーが止めたものとして、ユーザーに報告する。
   - 受け取られて返事が来た: 完了していたが通知を取りこぼした。ツールの説明どおり、完了済みへの送信は記録からの再開を起こすので、再開された結果を待つ。
   - エラー: 落ちている。ユーザーに報告する。

止まっていた場合は、ユーザーに報告する。止まった理由が分からなければ、分からないと書く。原因の見当があれば、見当だと書く。中断が原因ではない停止(落ちた、理由が分からない)の再起動は、ユーザーの指示を得てから行う。止めたのはユーザーの操作かもしれないからである。中断が原因の停止は、次の節に従って再起動する。

## 中断を受けたとき

中断を受けたときとは、会話に中断の印(ツールの結果や発言に「中断された」旨が出る)が出たとき、または、ユーザーの発言がターンの途中に割り込んで届いたときである。割り込みの形の発言も止めうるかは、未確認である。次に中断を受けたとき、印の文言と位置を記録して、この節に反映する。

ユーザーの次の発言を読んだうえで、ほかの作業より先に、次を行う。この確認は、「やらないこと」の間隔の制限の例外である。

1. ユーザーの次の発言が、その用事を要らない、やめる、という趣旨なら、再起動せず、報告する。
2. `ListAgents` で、任せていたサブエージェントの行が残っているかを確かめる。
3. 行が無く、結果も届いていないものは、上の「サブエージェントの場合」の手順 2 で見分ける。完了していたものは、再開された結果を待つ。止められたものだけを、手順 4 で再起動する。
4. 再起動の前に、元のサブエージェントが残した副作用を確かめる。確かめるのは、作業ツリーの状態、push 済みのコミット、投稿済みのコメントである。依頼文に、すでに行われた分を明記し、途中から引き継ぐ形にする。同じ返信を二重に投稿しない。
5. 再起動は、1 つの用事につき中断 1 回あたり 1 回までにする。再起動したものがまた止められたら、再起動を重ねず、ユーザーに報告する。再起動は、すでに許可を得た用事の続きなので、承認が要る作業を新しく起動しない規則には当たらない。
6. 再起動したら、生存確認を予約し直す。古い予約は、取り消すか、発火したときに対象が別の ID だと分かる本文に更新する。
7. 報告に、何が止められ、何を再起動したかを一言添える。

別セッションに任せた用事は、このセッションの中断の影響を受けないので、この手順の対象外である。

打ち切りの時刻を過ぎたら、実行中でも、ユーザーに選択肢を示す。待つ、止めて範囲を狭めて再実行する、自分で実施する、の3つが基本である。

## やらないこと

- 出力ファイル(`tasks/*.output`)をシェルで読まない。サブエージェントの記録全体が入っていて、文脈を溢れさせる。
- 出力ファイルの更新時刻や大きさを、生存の根拠にしない。完了まで一度も変わらないことがある。
- `ListAgents` や `SendMessage` を短い間隔で繰り返さない。確認は予約した間隔(10分)ごとに1回にする。中断を受けた直後の確認だけは例外である。
- 確認のために、サブエージェントが読んでいる作業ツリーのファイルを書き換えない。読んでいる最中のファイルが変わると、レビューの結果が壊れる。別の作業は、別の作業ツリーで行う。
- 承認が要る操作を、子のセッションに代わって行ったり、行うよう頼んだりしない。

## ユーザーへの報告

10分以上ユーザーを待たせるときは、状況を報告する([AGENTS.md](../../../AGENTS.md))。報告には、起動からの経過時間、状態(実行中・停止・承認待ち・不明)、判断の根拠(何を確かめたか)、ブロックしている事項、次の確認の時刻を書く。時刻は JST でタイムゾーンを添える(例: 21:30 JST)。`send_later` は `delay_minutes` で相対的に指定でき、`at` で絶対時刻を指定するときは UTC である。報告するときに JST へ直す。
