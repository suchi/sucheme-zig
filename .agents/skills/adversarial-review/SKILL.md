# 敵対的レビュー

成果物の欠陥を、実装前に、具体的な失敗シナリオとともに挙げる。「よく書けている」という感想は成果物ではない。

レビューの土台は、レビュー担当者自身の判断である。成果物が何をしようとしているかを理解し、どこで壊れるかを自分で考える。下の検出器カタログはその判断を置き換えるものではなく、既知の欠陥の類型を取りこぼさないための下限である。

カタログは下限であって上限ではない。全件適用して何も出なかったことは、欠陥がないことを意味しない。カタログの外側で成果物そのものの意味から欠陥を探す段を必ず設ける。カタログに当てはまらない欠陥を見つけたら、それが本来の仕事である。見つけた類型は検出器として追加し、このスキルを更新する。

カタログの各項目に添えた実例は、PR #1 で外部のレビューサービスが挙げた指摘から取った。実例があるのは「少なくともこの類型は実際に起きる」ことの裏付けであり、「この類型だけを探せばよい」という意味ではない。実例との対応表、検出器ごとの件数、パリティ試験の結果は [docs/review/adversarial-review-baseline.md](../../../docs/review/adversarial-review-baseline.md) にある。件数をこちらに書かないのは、検出器1が禁じている真実の源の重複を避けるためである。

欠陥がゼロなら、カタログのどの検出器を適用した結果ゼロだったかと、カタログ外の探索で何を検討したかの両方を示す。

## 原則

- 具体的な失敗シナリオを伴わない指摘は書かない。「不十分かもしれない」は指摘ではない。「入力Xの状態Yで、手順Zを踏むと結果Wになるが、仕様はVを要求している」が指摘である。
- 仕様について書かれていることは、必ず一次情報の原文を開いて照合する。記憶で判断しない。成果物の記述が正しい場合もあるので、両方向に照合する。
- 修正によって新しく書かれた文章を、同じ厳しさで読み直す。PR #1 では指摘の約半分が、前の巡で書かれた修正文の欠陥だった。修正は新しい攻撃面である。
- 著者の意図を忖度しない。「こう書いたのはこういう意図だろう」と補って読むと欠陥が見えない。書かれていることだけを読む。
- 「すべて」「必ず」「1箇所に閉じる」「次に限る」と書かれていたら、その対象集合を自分で数え上げて突き合わせる。主張を信じて数えないことが、最も多い見落としの原因である。数え上げた集合と件数を報告に書く。
- カタログを消化して終わらない。カタログは既知の類型の網であり、新しい種類の欠陥はそこに引っかからない。成果物の目的を理解し、それが達成できない経路を自分で構成する。

## 手順

1. 対象の確定: 差分だけでなく、差分が参照する既存の記述も読む。文書間の矛盾は差分の中には現れない。
2. 事実の棚卸し: 成果物に現れる「主張」を抜き出す。仕様の引用、データ構造の宣言、不変条件、手続きの一覧、件数、状態の列挙、契約。これが照合の対象になる。
3. 網羅主張の数え上げ: 成果物が網羅や単一経路を主張している箇所を全部抜き出し、それぞれの対象集合を独自に数え上げる。「この検証を1つの関数に閉じる」なら、その資源に到達する経路を全部数える。「すべてのXはYを持つ」なら、X を全部数える。「次に限る」なら、他の文書が同じ役割を要求しているものを全部数える。提供されるAPIについては、不変条件が要求する操作の対象型を全部数え、APIがその全部を受け付けるかを確認する。
4. 検出器の適用: 下のカタログを上から順に適用する。各検出器について、適用した範囲と見つけた件数を記録する。思いつきで読むのではなく、カタログを機械的に回す。
5. カタログ外の探索: カタログの類型に当てはまらない欠陥を探す。成果物の目的を1つずつ取り、それが達成できない経路を構成する。設計が解こうとしている問題そのものに対して、別の解き方や見落とされている場合分けがないかを考える。この段で見つけた欠陥は、類型として検出器に追加する候補になる。
6. 反例の構成: 候補が見つかったら、具体的な入力と状態の列を作って失敗を示す。示せなければ指摘にしない。
7. 一次情報の確認: 仕様に関わる指摘は、原文を引用して添える。
8. 報告: 下の形式で出す。

## 検出器カタログ

適用順は効果の高い順である。実例での検出数は基準表にある。

### 1. 真実の源の重複

同じ事実が2箇所以上に書かれていないかを探す。見つけたら、一方を他方から導出する形に変えるか、片方を消す。

問いの形:

- この件数・この一覧・この状態は、他の文書にも書かれていないか。
- 実行時の状態として、同じ事柄を表す変数が2つないか。2つあるなら、同期が崩れる操作列はないか。
- 本文が「保持する」と書いている情報は、データ構造の宣言に実際にフィールドとして存在するか。
- 図・表・本文・コード例の間で食い違いはないか。

PR #1 の実例: 衛生性の検証項目の件数が4つの文書にハードコードされ、項目追加で3箇所がずれた。例外ハンドラの位置を独立レジスタと点の列の両方で表したため、3巡にわたって同期の欠陥が出続けた。`Alias` を `Value` に入れる前提が片方の文書にしかなかった。

状態の重複は特に重い。2つの真実の源を同期させる設計を見つけたら、同期規則を精密にする前に、源を1つにできないかを問う。

### 2. 不変条件の自己違反

成果物が自分で宣言した不変条件を、成果物の別の箇所が破っていないかを探す。

問いの形:

- 宣言された不変条件を1つずつ取り、それが適用されるべき対象を文書全体から数え上げて、全部が従っているか。
- 「すべてのXはYを持つ」と書いたなら、文書に現れるXを全部列挙して確認したか。
- 走査・マーク・列挙の対象に、漏れている保持経路はないか。ヒープ上だけでなく、ローカル変数、作業表、ヒープ外のテーブルも含めたか。
- メタデータを辿ってはいけない経路を、自動化の仕組みが辿らないか。
- 不変条件が「Xを登録せよ」と要求しているとき、設計が提供するAPIは X の全部の型を受け付けるか。不変条件の対象型を数え上げてAPIの引数型と突き合わせたか。`Value` に包めない生のポインタ型が漏れていないか。
- 周期的に消去すべき状態の消去手順が書かれているか。

PR #1 の実例: 全GCオブジェクトはヘッダを持つと宣言しながら、コアIRの節点だけヘッダのない union だった。`Value` の `.symbol` だけをマークし、生の `Symbol` 型フィールドを漏らした。`@typeInfo` による自動走査が `Header.next` を辿れば全オブジェクトが生存扱いになる。

### 3. 機構の経路網羅

機構を1つ取り、通りうる経路を全部列挙して、それぞれに必要な状態が設計されているかを確認する。

経路の列挙軸:

- 正常進入、正常退出、異常退出(例外)、非局所脱出(継続)、再進入、多重起動
- 入れ子、相互に交差する入れ子
- 0回・1回・多数回の繰り返し
- 空、1要素、最大、境界

問いの形:

- 正常経路の状態は設計されているか。異常経路だけ設計して正常経路を忘れていないか(逆も)。
- その経路の途中で、呼び出し先が制御を奪いうるか。奪いうるなら、途中の状態自体が保存される表現になっているか。
- 2つの経路が同じ結果を出すべき場合、本当に同じ値になるか。

PR #1 の実例: 継続起動時の巻き戻しだけを設計し、`dynamic-wind` の通常実行経路のフレームを忘れた。`with-exception-handler` と `parameterize` の通常復帰で動的状態を外すフレームがなかった。`before` と `after` が Scheme 手続きであり継続を捕捉できるため、巻き戻しを同期ループで書けないことを見落としていた。

### 4. 仕様原文との照合

仕様に言及している記述を全部抜き出し、原文を開いて語単位で照合する。

問いの形:

- 列挙の件数は原文と一致するか。原文を数えたか。
- 「〜を除いて」「ただし」の範囲を正しく読んでいるか。除外されるのは何か。何は変わらないのか。
- 仕様が要求する対象の全体を、設計の表現が保持できるか。種類を取りこぼしていないか。
- 節番号は実在するか。引用は原文のままか。

PR #1 の実例: 名前付き文字を8種と書いた(正しくは9種)。例外ハンドラの動的環境について「ハンドラより外側の動的環境を設定する」と書いたが、原文は「現在の例外ハンドラだけを切り替え、残りは raise 時のまま」だった。エクスポート表が変数とマクロしか保持できず、仕様が要求する特殊形式のエクスポートに対応できなかった。

照合は両方向に行う。成果物が正しく、レビュー側の記憶が誤っている場合もある。PR #1 では文字列エスケープ `\|` について外部レビューの指摘が誤りで、原文の生成規則が成果物を支持していた。

### 5. 文書と現実の一致

書かれている状態・時制・件数が、実際の状態と一致するかを確認する。

問いの形:

- 「動作する」「完成した」「対応済み」は現時点で真か。他の文脈を知らない読者が読んで誤解しないか。
- ステータス欄は、この変更が取り込まれた後の状態として正しいか。恒久的に古くなる書き方になっていないか。
- 設計を変えたなら、決定の記録も更新したか。
- PR本文・README・進捗表の記述は、実際の変更範囲と一致するか。

PR #1 の実例: 実装前の README に「動作します」と現在形で書いていた。SOW のステータスがマージ後も恒久的に「合意待ち」になる書き方だった。独立レジスタを追加したのにADRに記録がなかった。

### 6. 敵対的な外部入力

プログラムが受け取るデータから経路・名前・識別子を組み立てる箇所を全部洗い出し、敵対的な入力を考える。

問いの形:

- この文字集合の検証を通る入力のうち、意図しない対象に解決されるものはないか。
- プラットフォーム固有の名前解決の癖はないか。予約名、末尾の文字の除去、大文字小文字の同一視、代替データストリーム。
- 字句的な正規化で足りるか。実体の解決(リンク、再解析ポイント)を経るとどうなるか。
- 検証と使用の間に対象が差し替わる余地はないか。検証は使用する対象そのものに対して行っているか。
- 同じ資源に到達する経路を全部数え上げたか。「検証を1つの関数に閉じる」と書かれていても、別の構文や別のAPIから同じ資源に届く経路があれば、そこは検証を迂回する。利用者が与える文字列・名前・識別子を資源に変換する箇所を、構文の一覧から機械的に拾う。

PR #1 の実例: ライブラリ名の成分をそのままパス成分にしてパストラバーサルが可能だった。字句的な正規化だけではシンボリックリンクと Windows の再解析ポイントがルート外を指す場合を防げなかった。文字集合の検証が Windows の予約デバイス名と末尾のドットを通していた。

### 7. 境界の契約

言語・プロセス・スレッドをまたぐ境界を全部洗い出し、所有権と有効期限を確認する。

問いの形:

- この領域は誰が所有し、誰が解放するか。書かれているか。
- 有効期限はどこまでか。どの操作が無効にするか。無効にしない操作はどれか。
- 通常の呼び出し手順をそのまま辿って、契約違反にならないか。
- 境界の実装詳細(メモリの再配置、ビューの無効化)が契約に影響しないか。

PR #1 の実例: WASM の入力領域の所有権が未定義で、複製するのか引き取るのかが決まっていなかった。出力領域の有効期限を「次の呼び出しまで」と書いたため、ポインタを得てから長さを得るという通常の手順が契約違反になっていた。

### 8. 停止性と循環

再帰・反復を全部洗い出し、停止することを確認する。

問いの形:

- この再帰は何が単調に減るから止まるのか。言えるか。
- 走査する対象のデータは循環しうるか。利用者が循環を作る手段はあるか。
- 委譲・転送の形になっている再帰で、同じ引数が渡っていないか。
- 共有構造を走査するとき、複製によって同一性が変わらないか。

PR #1 の実例: 識別子の解決規則が、別名を同じ引数で再帰させるため停止しなかった。`quote` の別名剥離が、データラベルで作った循環データで停止しなかった。

### 9. 同一性と一意性

等価比較・同一性判定を全部洗い出す。

問いの形:

- 異なる2つのものが等しいと判定されうるか。
- 同じものが等しくないと判定されうるか。
- 比較に使う値は、比較したい対象を一意に決めるか。相対値・再利用される値・再計算される値を使っていないか。

PR #1 の実例: 局所束縛の意味を相対的な深さと添字の組で表したため、別々の字句環境にある無関係な束縛が同一と判定され、マクロの衛生性が壊れた。

### 10. 資源の上限

伸びるデータ構造を全部洗い出す。

問いの形:

- これを無制限に伸ばせる入力はあるか。
- 伸びた分は、宣言した上限に計上されているか。上限の外にあるものはないか。
- 回収される仕組みはあるか。回収されない設計なら、それが許容される根拠は何か。

PR #1 の実例: `string->symbol` が作る名前をGC対象外の永続表に追加する設計で、乱数文字列をシンボル化し続けるとヒープ上限の外側でメモリを増やし続けられた。

### 11. 言語・処理系の前提

言語仕様や標準ライブラリの振る舞いに依存している箇所を洗い出し、固定したバージョンの実機で確認する。

問いの形:

- メモリ配置、フィールド順、サイズ、アラインメントを前提にしていないか。言語がそれを保証しているか。
- 標準ライブラリの関数は、そのバージョンに実在するか。シグネチャは同じか。
- 確認したことと、推測していることを区別して書いたか。

PR #1 の実例: 通常の `struct` のフィールド順が保証されないにもかかわらず、`*Header` を先頭アドレスとみなしてキャストする前提だった。実機で確認すると、宣言を2番目にしたフィールドが実際に offset 0 に配置された。

### 12. 列挙の重複と欠落

一覧・表・列挙を全部取り、重複と欠落を確認する。

問いの形:

- 同じ項目が2回現れていないか。
- 網羅を主張する一覧に、漏れている項目はないか。

PR #1 の実例: 破壊的操作の監査リストに同じ手続きが重複していた。

## 自己レビューのバイアス対策

自分の書いた成果物をレビューするときは、次を守る。これを守らないと、意図を補って読んでしまい欠陥が見えない。

- レビューは、成果物を書いた文脈を持たない別のサブエージェントに実行させる。与えるのは成果物、一次情報の在処、このスキルだけとする。「なぜそう設計したか」を渡さない。外部のレビューサービスが欠陥を見つけられたのは、まさに意図を知らない立場だったからである。
- 検出器カタログを機械的に上から適用する。気になった箇所から読み始めない。
- 「ここは意図的にこうしている」と思った箇所こそ、根拠が文書に書かれているかを確認する。書かれていなければ、それは指摘である。
- 1つの論点で2度以上同じ種類の欠陥を指摘されたら、個別の修正をやめて表現そのものを変える。PR #1 では例外ハンドラの表現で3巡を要し、2つの真実の源という構造が原因だった。

## 指摘の書き方

各指摘に次を含める。

- 重要度: `必須`(準拠性・正しさ・安全性に影響する) / `推奨`(保守性・一貫性に影響する) / `任意`(好みの範囲)
- 場所: ファイルと行
- 何が問題か: 1文
- 失敗シナリオ: 具体的な入力・状態・手順と、そのときの誤った結果、および本来の結果
- 根拠: 仕様の節番号と原文、または実機で確認した結果

同じ原因から生じる複数の箇所は、1つの指摘にまとめて箇所を列挙する。

報告のサマリーには、適用した検出器と検出器ごとの件数、およびカタログ外の探索で検討した対象を書く。これにより、ゼロ件が「調べた結果ゼロ」なのか「調べていない」のかを読者が区別できる。

カタログ外で見つけた欠陥には、どの類型にも当てはまらないことを明記する。その指摘は検出器の追加候補として扱い、スキルの更新に回す。

## 停止規則

次の3つをすべて満たしたときに収束とする。

- 検出器カタログを全件適用して、新規の指摘がゼロである。
- カタログ外の探索でも新規の指摘がゼロである。
- 直前の巡で書いた修正文に対しても、上の2つを満たす。

新規指摘ゼロのルールを緩めない。瑣末な指摘で巡回が終わらない場合は、どの指摘が瑣末でどれが必要だったかを具体的に挙げて検出器を調整する。基準を下げて収束させない。

## 禁止

- 失敗シナリオのない指摘を書く。
- 一次情報を開かずに仕様について断定する。
- 「要検討」「不十分かもしれない」で終わる。どう不十分かを示せないなら書かない。
- 書式・語尾・言い回しの好みを指摘する。プロジェクトの言語ルールに違反している場合を除く。
- 著者の意図を推測して問題を見逃す。
